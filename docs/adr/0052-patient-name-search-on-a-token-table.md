# ADR-0052: Patient name search on a token table

Status: Accepted (the design is the owner's, OD-42 and OD-145, 2026-11-27; written and built in A-03-03, text pending owner confirmation in its PR) · Date: 2026-11-27 · Deciders: product owner (with Claude) · Amends: [ADR-0034](0034-arabic-output-and-name-search.md) (name-search normaliser and search index)

## Context
[ADR-0034](0034-arabic-output-and-name-search.md) chose an application-written name key ranked by `pg_trgm` on a `(tenant_id, name_key gin_trgm_ops)` index, and left open whether that index can serve a search under RLS (OD-42): PostgreSQL does not use it there, because the trigram operator is not `LEAKPROOF` and may not run in an index scan ahead of the tenant policy (spike S3: 7.7 ms at 1,000 patients per clinic, 271 ms by sequential scan at 50,000). The owner refused both the `LEAKPROOF` flag (a superuser change that a restore or an extension update loses) and an extra search service (OD-42, closed 2026-11-27), and asked for a token table under the same RLS (spec [A-03](../specs/patients/A-03-patients.md) criterion 5). Spike S3's review also left gaps in the normaliser (OD-145, closed 2026-11-27).

## Decision
**Normaliser (key version 2; amends ADR-0034's rule list)**
- The function moves from the spike into `@shifa/contracts` (`src/name-key.ts`) and a Dart package `packages/shifa_name_key` for the offline clients. `packages/contracts/vectors/name-search-vectors.json` (version 2) is the contract; both ports run it in `verify`; a SQL port is a drift check in tests only (`packages/db/test/name-key-sql.test.ts`). Spike S3's version-1 file stays with the spike.
- Format characters (Unicode category Cf: bidi controls, ALM U+061C, word joiner U+2060, soft hyphen, Arabic number signs, tags …) are removed like the bidi controls before them, except ZWSP, ZWNJ, ZWJ and BOM, which stay word breaks (OD-145).
- Latin capitals are lower-cased by Unicode's default mapping without locale rules (İ → i) in Basic Latin, Latin-1 Supplement, Latin Extended-A and -B, Latin Extended Additional and full-width Latin; Latin Extended-C and -D stay as typed, because Dart's case tables predate them and the two ports must agree on every character (found by the vector that lists every capital; the owner kept this narrower range, 2026-11-27). Amends OD-40's ASCII-only rule (OD-145); `foldArabic` (UI word-start matching, stored place keys) keeps OD-40's rules.
- `NAME_KEY_VERSION` (2) is stored with every chart's key and token; a rule change edits the vectors first, then every port, and raises the version.

**Tokens and search**
- `patient_name_token (id, tenant_id, patient_id, part, word, token, whole, key_version)`: for every word of the given, father and family names' keys, each prefix of 2 to 24 characters (`nameTokens`). Tenant table, ENABLE + FORCE RLS with the tenant policy, `(tenant_id, patient_id)` foreign key to `patient`, unique `(tenant_id, patient_id, part, word, token)`, an isolation case; `shifa_app` holds SELECT, INSERT and DELETE (tokens are rewritten, never updated).
- A typed word is looked up by **equality** on a `(tenant_id, token, whole, patient_id)` btree: `texteq` is leakproof, so the index serves the query under RLS with no flag, no superuser and no `SECURITY DEFINER` function. Every distinct typed word of two letters or more must match (at most 6 are read): the charts holding all of them come from intersecting each word's index-only scan, and one word alone reads its whole-word holders first. At most 1,000 of them are ranked (a common start such as «ال» then answers `truncated`): by whole-word matches, then `similarity()` of the stored key to the typed key (`pg_trgm`), then file number. Each search statement runs under a transaction-local `statement_timeout` of 2 s.
- **Typos** (owner, 2026-11-27, A-03-03 review): when the tokens find nothing, the candidates are the charts holding every typed word that some chart holds (or, when none does, every word's first three letters); a candidate is kept when each typed word is one of its tokens or has a trigram similarity of 0.25 or more with one of its whole words («احمر» for «احمد»), ranked by similarity of the stored key to the typed key and marked `name_variant`.
- `patient.name_key` and `patient.name_key_version` are written by the chart repository with the tokens, in the transaction that saves the chart: on registration and on every edit of a name part. Charts with an older or no key (the A-03-02 charts, key version 0) are written by the clinic's next searches before they read: at most 3 batches of 200 per request, each in its own short transaction (`SELECT … FOR UPDATE SKIP LOCKED`); a support session's READ ONLY search skips that step and searches the keys already written.
- Phones: `contact_phone_tail` and `second_phone_tail`, generated `right(phone, 7)`, each with a `(tenant_id, …)` index; a term of 7 or more digits matches the tail by equality, then the full suffix on those rows; an accepted phone in any spelling also matches exactly.
- `POST /patients/search` (`patients.view`, a read by POST: `@ReadInBody`, so the term never reaches a URL and a support session may call it). Order: an exact file number, a previous number (any term holding a digit, in either digit system; a merged chart answers the chart it leads to, with `mergedFileNumber`), phones, then names; at most 20, `truncated` when more matched; `matchedBy`, `matchedParts` and the name parts per result. A per-member limit (60 searches a minute, in the API process) answers 429 `rate_limited` and logs the member's ids. Search writes no audit row; the term is never logged, traced or put in an error.

## Consequences
+ Name search uses an index under the tenant's RLS at 50,000 charts per clinic, measured behind PgBouncer as `shifa_app` in two clinics of 50,000 synthetic charts: p95 under 65 ms on every path, common starts («ال» alone, a name and «ال», «ال» typed 33 times) and typos included, against 150 ms allowed (`apps/api/test/patients/search-bench.test.ts`, which also checks the plans and that every hit is the searched clinic's; figures in the [slice file](../slices/A-03-03-normaliser-and-search.md)). OD-42 needs neither `LEAKPROOF` nor another service.
− A typed word start can fold to a particle («آم» → «ام») and join the next word; such a term is looked up again word by word when the joined words find nothing (found by the benchmark).
− A very common start ranks only the first 1,000 charts that hold it, so its 20 results are not the best of the whole clinic; the answer says `truncated` and the screen asks for another word.
− The typo fallback misses a typo in the first letters of every typed word, and with more than 1,000 candidates it ranks only the first 1,000.
+ The server and the offline clients compute the same key, held equal by one vector file and a drift-checked SQL port.
− About 12 token rows per chart (≈ 600,000 at 50,000 charts) and a delete-and-insert of a chart's tokens on every name edit.
− The rate limit lives in one API process; several instances each count their own (revisit with the second instance).
− After a key version change a clinic's keys are rewritten 600 at a time by its searches, so names saved under the old version are found by the old tokens until then; a later version bump should backfill ahead of the release instead.

## Alternatives considered
- `LEAKPROOF` on `similarity_op` with the trigram GIN index: refused by the owner (superuser, lost on restore or extension update; OD-42).
- Meilisearch or another search service: refused (OD-42): another service holding patient names, its own tenancy.
- A `SECURITY DEFINER` search function: needs a BYPASSRLS role or a table without FORCE RLS and a hand-written tenant filter (ADR-0030, `roles.sql`).
- A range scan on the token (`token >= w AND token < w || chr(…)`) instead of stored prefixes: fewer rows, but its comparison operators are collation-aware; equality keeps the index argument trivial.
- A generated key column (SQL normaliser): a third implementation in production and Unicode-version drift in `normalize()` (ADR-0034).
