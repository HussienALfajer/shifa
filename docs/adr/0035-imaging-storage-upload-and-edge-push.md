# ADR-0035: Imaging storage, browser upload and edge push — Garage bucket per tenant, encrypted objects, chunked upload, Transfers through the gateway

Status: Accepted (owner, 2026-11-17) · Date: 2026-11-16 · Deciders: product owner (with Claude) · Amends: [ADR-0019](0019-imaging-orthanc-ohif.md)

## Context
[ADR-0019](0019-imaging-orthanc-ohif.md) chose an unmodified Orthanc per tenant behind our DICOMweb gateway, OHIF as the viewer, browser upload with resume, and an edge box for clinics with X-ray devices. It left open whether Orthanc's S3 plugin works with Garage ([ADR-0021](0021-supporting-services.md)), how buckets are laid out, how the browser uploads, how the edge box pushes, and whether a CBCT can be viewed over a Syrian link. Spike S4 ([spec](../specs/spikes/0.3-s4-imaging.md), [result](../spikes/s4-imaging.md)) ran the official Orthanc image with Garage, PostgreSQL 18 and OHIF behind a throwaway gateway, on synthetic CBCT studies of real size and one public de-identified case, over three link profiles (P1 1/3 Mbit/s with line drops, P2 3/10, P3 8/25). The spike's gateway was throwaway code; the rules below are what the Phase D gateway and edge agent must meet.

## Decision
**Storage**
- Garage (ADR-0021) is the object store for Orthanc through the official AWS S3 storage plugin, path-style addressing (`VirtualAddressing: false`), flat storage structure. Garage and Orthanc stay pinned by version and digest; an upgrade of either runs the spike's storage suite (round trip, delete, encryption, wrong key) before it ships.
- **One bucket and one Garage key per tenant** (amends ADR-0019's "per-tenant bucket prefix"). Garage grants access per bucket, not per prefix: with a shared bucket, tenant A's key read tenant B's objects in the spike. Keys get read and write on their own bucket only, never owner rights.
- **Object encryption on from the first write** with the plugin's `StorageEncryption`. Provisioning refuses an Orthanc configuration with `StorageEncryption.Enable: false`, and a startup check reads one stored object from Garage and confirms it is not plaintext DICOM (no `DICM` marker).
- **Master keys:** one 256-bit key per tenant, generated by the platform, held with the other platform secrets (never in a database, a repository or an image) and mounted into that tenant's Orthanc as a file only. Key backups are kept apart from Garage and from image backups, so one stolen backup never holds both the objects and their key; losing a key makes the tenant's images unreadable. Rotation: a new key id becomes `MasterKey`, the old ones stay in `PreviousMasterKeys` for reading; rotation does not re-encrypt old objects, so a compromised key means rewriting the tenant's objects under a new key. Rotation was not tested in the spike; Phase D tests it (write under key 1, rotate, read old and new, rewrite) before the first tenant goes live.
- What object encryption does not cover: Orthanc's PostgreSQL index holds patient tags (name, ID, birth date) in clear. The index database relies on the database server's own at-rest protection and on TLS between Orthanc and PostgreSQL (`EnableSsl`, off in the spike); both are required in production.
- Studies are stored lossless as received (IMG-06); the spike compared the cloud copy by SHA-256 of each instance.

**Gateway (carried from the 0.3-S4a security review)**
- Audit a STOW-RS attempt before it is forwarded and every study in the response's (0008,1199), not only the RetrieveURL; audit the studies a QIDO-RS returns and a normalised form of its filters (never tag values in logs).
- One network per tenant between the gateway and that tenant's Orthanc; S3 traffic on its own network; Garage's admin and RPC ports unreachable from Orthanc; `pg_hba` per tenant database.
- Tokens signed with asymmetric keys and checked for `iss`, `aud` and `typ` (the spike used one shared HS256 key, so tenant separation rested on that key and the gateway's mapping).
- Per-IP connection limits and a minimum data rate where the gateway meets the internet.
- Orthanc may build RetrieveURLs from the request's `Host`: set `DicomWeb.PublicRoot` (or rewrite in the gateway) so no client-controlled host reaches a response.

**Browser upload (IMG-14)**
- **Our own chunked resumable protocol through the gateway**, not STOW-RS per instance from the browser. A session is keyed by **the tenant (from the credential) and the folder's manifest** (path, size, SHA-256 per file); every lookup is filtered by tenant, and the actor is recorded per chunk and per stored file. A reload with the folder re-selected, a second tab of the same tenant or a line drop resumes from the server's offsets. A chunk (1 MiB by default, at most 4 MiB) is appended only at the current offset after its digest is checked; a complete file is stored in Orthanc by STOW-RS from the gateway. STOW-RS per instance cannot finish a single large multi-frame file between line drops.
- The page uploads a few files at once (the result gives the measured gain); the gateway enforces its own limit of concurrent chunk requests per session and per tenant, and a share of the database pool per tenant, so one busy tenant cannot starve the others.
- Staging of chunks: an encrypted volume or RAM-backed storage (never plaintext on disk), a TTL cleaner and a per-tenant quota. A finished session is checked against the archive (QIDO-RS) before it reports "already uploaded", or expires.
- The upload transaction does not hold a row lock and a connection across hashing and STOW-RS: it commits a `storing` state first and records the outcome in a second transaction; `idle_in_transaction_session_timeout` is set.

**Edge box (IMG-17)**
- The edge Orthanc (SQLite) pushes with the **Transfers plugin through the gateway**: the gateway allows `POST /transfers/push`, `PUT /transfers/push/{id}/{n}`, `POST …/commit` and `DELETE …/{id}` for an edge credential only, and nothing else of Orthanc's REST API. Each transaction id is bound to the box that created it; another box of the same tenant cannot commit or abort it. Bucket size 512 KB, two threads (4 MB buckets never arrived whole between P1 line drops).
- **The edge box needs its own queue that resumes**: a Transfers push job is lost when the edge Orthanc restarts (Orthanc 26.11, Transfers 1.7), although `SaveJobs` is on, and a failed job is pushed again from the start: on P1 a 1 GB push failed once at a line drop and took 3 h 3 min with 1.13 × the study bytes on the wire, against about 1.5 h without the restart. The edge agent records each study to push and, after a restart or a failure, sends only what the cloud does not have yet (per instance, checked by QIDO-RS, or in smaller pushes of a series or a few hundred MB each) until the cloud has it.
- Push audit per study: instance ids from the create body, looked up on commit; create and abort audited as well.
- **Edge credential:** a TLS client certificate bound to the box, its private key in the box's TPM where the hardware has one, revocable; the server maps certificate → box → tenant; one key per credential kind (edge push is never a viewer or uploader token). The edge verifies the gateway's certificate against a pinned CA (`HttpsVerifyPeers`). **Not tested in the spike** (plain HTTP and a bearer header): before Phase D relies on it, check that Transfers presents the peer's `CertificateFile`, and that the TLS terminator (ADR-0022) verifies client certificates, passes the identity to the gateway only on a header it strips from clients, and that the gateway trusts that header only from the terminator. If Transfers cannot present a certificate, the edge agent pushes instead of the plugin.
- **The box itself:** full-disk encryption (it keeps months of studies in clear in SQLite and files); a modality allowlist for the DICOM listener (`DicomModalities` with AET and host, `DicomCheckModalityHost: true`, `DicomAlwaysAllowStore: false`), so another device on the clinic LAN cannot store studies that the box then pushes into the tenant's archive.
- **LAN viewing on the box:** per-user authentication and audit, with audit records forwarded to the cloud audit, not kept only on the box; the spike's edge OHIF used the edge Orthanc's only credential, which production must not.

**Viewing**
- OHIF v3, unmodified release build (ADR-0019's fork is a later step), served from the gateway origin: the gateway proxies OHIF's `/viewer` route and a strict pattern of its static files at the origin root, cookie-gated (the release build has public path `/`). Study data only through the gateway's DICOMweb routes; bulk data URIs off (frames only).
- **Viewer session:** a one-time code, sent by POST and bound to a state value (never in a GET URL), exchanged for a `__Host-` cookie, `Secure`, `HttpOnly`, `SameSite=Strict`, over TLS; a maximum lifetime and an idle timeout (the spike's 8 hours is too long for an unattended reception PC); revocable (jti, logout, deny list); its issue audited.
- The viewer and the upload page get separate origins with a CSP: `connect-src 'self'`, `frame-ancestors` set to the application's origin (or `'none'` where not embedded). The upload page gets its uploader tokens from the application by `postMessage` with a strict origin check, never in a URL.

## Consequences
+ Tenant data is separated by an Orthanc, a database, a bucket and a key per tenant; image objects in Garage are encrypted. Isolation in production also rests on the per-tenant networks, `pg_hba` and asymmetric tokens above, which the spike did not have.
+ The browser upload survives line drops and reloads at the cost of at most one chunk per interruption.
+ Clinics with a CBCT can send studies from the edge box overnight; the browser remains the path for clinics without one.
− One bucket, key and master key per tenant to provision, back up apart and rotate.
− The edge agent (queue, re-push, client certificate, modality allowlist, audit forwarding) is our code beside Orthanc, not inside it (licence boundary, IMG-04).
− The edge credential and TLS were not tested in the spike; Phase D starts with that check.
− OD-18 stays open: the spike measured the link, not the clinics' hardware or a real clinic's uplink.
