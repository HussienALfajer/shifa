# ADR-0035: Imaging storage, browser upload and edge push — Garage bucket per tenant, encrypted objects, chunked upload, Transfers through the gateway

Status: Proposed · Date: 2026-11-16 · Deciders: product owner (with Claude) · Amends: [ADR-0019](0019-imaging-orthanc-ohif.md)

## Context
[ADR-0019](0019-imaging-orthanc-ohif.md) chose an unmodified Orthanc per tenant behind our DICOMweb gateway, OHIF as the viewer, browser upload with resume, and an edge box for clinics with X-ray devices. It left open whether Orthanc's S3 plugin works with Garage ([ADR-0021](0021-supporting-services.md)), how buckets are laid out, how the browser uploads, how the edge box pushes, and whether a CBCT can be viewed over a Syrian link. Spike S4 ([spec](../specs/spikes/0.3-s4-imaging.md), [result](../spikes/s4-imaging.md)) ran the official Orthanc image with Garage, PostgreSQL 18 and OHIF behind a throwaway gateway, on synthetic CBCT studies of real size and one public de-identified case, over three link profiles (P1 1/3 Mbit/s with line drops, P2 3/10, P3 8/25).

## Decision
**Storage**
- Garage (ADR-0021) is the object store for Orthanc through the official AWS S3 storage plugin, path-style addressing (`VirtualAddressing: false`), flat storage structure. Garage and Orthanc stay pinned by version and digest; an upgrade of either runs the spike's storage suite (round trip, delete, encryption, wrong key) before it ships.
- **One bucket and one Garage key per tenant** (amends ADR-0019's "per-tenant bucket prefix"). Garage grants access per bucket, not per prefix: with a shared bucket, tenant A's key reads tenant B's objects. Keys get read and write on their own bucket only, never owner rights.
- **Object encryption on from the first write** with the plugin's `StorageEncryption`. One 256-bit master key per tenant, generated by the platform, held with the other platform secrets (never in a database, a repository or an image) and mounted into that tenant's Orthanc as a file only. Rotation: a new key id becomes `MasterKey`, the old ones stay in `PreviousMasterKeys` for reading. An Orthanc started with a wrong key refuses to read (it never returns wrong bytes). The measured cost is in the result's encryption table.
- Studies are stored lossless as received (IMG-06); the cloud copy is compared by SHA-256 of each instance.

**Browser upload (IMG-14)**
- **Our own chunked resumable protocol through the gateway**, not STOW-RS per instance from the browser. A session is keyed by the folder's manifest (path, size, SHA-256 per file), so a reload with the folder re-selected, a second tab or a line drop resumes from the server's offsets. A chunk (1 MiB by default, at most 4 MiB) is appended only at the current offset after its digest is checked; a complete file is stored in Orthanc by STOW-RS from the gateway. Files go in parallel (three at a time) so the uplink stays full. STOW-RS per instance cannot finish a single large multi-frame file between line drops.
- Staging of chunks: an encrypted or ephemeral volume, a TTL cleaner and a per-tenant quota ("encrypted at rest" covers staging too). A finished session is checked against the archive (QIDO-RS) before it reports "already uploaded", or expires.
- The upload transaction does not hold a row lock and a connection across hashing and STOW-RS: it commits a `storing` state first and records the outcome in a second transaction; `idle_in_transaction_session_timeout` is set.

**Edge box (IMG-17)**
- The edge Orthanc (SQLite) pushes with the **Transfers plugin through the gateway**: the gateway allows `POST /transfers/push`, `PUT /transfers/push/{id}/{n}`, `POST …/commit` and `DELETE …/{id}` for an edge credential only, and nothing else of Orthanc's REST API. Bucket size 512 KB, two threads (4 MB buckets never arrive whole between P1 line drops).
- **The edge box needs its own queue**: a Transfers push job is lost when the edge Orthanc restarts (Orthanc 26.11, Transfers 1.7), although `SaveJobs` is on. The edge agent records each study to push and pushes it again after a restart or a failure until the cloud has it.
- The edge credential: over TLS with a client certificate bound to the box, revocable, one key per credential kind (edge push is not a viewer or uploader token). Orthanc's peer header is fixed at start, so a credential in that header lives as long as the edge process (12 hours in the spike); production uses the client certificate instead.
- Push audit per study: instance ids from the create body, looked up on commit; create and abort audited as well.
- Viewing on the clinic LAN from the edge box needs per-user authentication and audit on the box; the spike's edge OHIF used the edge Orthanc's only credential, which production must not.

**Viewing**
- OHIF v3, unmodified release build (ADR-0019's fork is a later step), served from the gateway origin: the gateway proxies OHIF's `/viewer` route and a strict pattern of its static files at the origin root, cookie-gated (the release build has public path `/`). Study data only through the gateway's DICOMweb routes; bulk data URIs off (frames only).
- The viewer session: a one-time code exchanged by POST (or bound to a state value) for a `__Host-` cookie, `Secure`, `HttpOnly`, `SameSite=Strict`, over TLS; revocable (jti, logout, deny list) and its issue audited. The viewer and the upload page get separate origins with a CSP (`connect-src 'self'`, `frame-ancestors`).

## Consequences
+ Tenant isolation holds at three layers: Orthanc per tenant, database per tenant, bucket and key per tenant; the object store never sees plaintext DICOM.
+ The browser upload survives line drops and reloads at the cost of at most one chunk per interruption.
+ Clinics with a CBCT can send studies from the edge box overnight; the browser remains the path for clinics without one.
− One bucket, key and master key per tenant to provision and rotate; key loss means the tenant's images are unreadable, so master keys are part of the backup plan (ADR-0029).
− The edge agent (queue, re-push, client certificate) is our code beside Orthanc, not inside it (licence boundary, IMG-04).
− OD-18 stays open: the spike measured the link, not the clinics' hardware or a real clinic's uplink.
