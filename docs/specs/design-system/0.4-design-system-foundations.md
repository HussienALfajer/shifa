# Spec 0.4: Design system foundations (tokens, design language, UI SDK components, Flutter theme)

Status: Approved (owner, 2026-11-20; criterion 12 added the same day, OD-58) · Date: 2026-11-20 · Risk tier: T1 (no patient data; synthetic names only in stories and prototypes) · Owner: product owner
Requirements: PLT-41 (brand colours, token side only) · Decisions: [ADR-0039](../../adr/0039-ui-sdk-headless-base.md) amending [ADR-0011](../../adr/0011-design-system-base-ui.md); [ADR-0040](../../adr/0040-design-first-in-claude-design-code-as-source.md); OD-19, OD-48, OD-56, OD-57, OD-58 (closed 2026-11-20); OD-20 (open, both digit styles supported) · Design doc: [design-system](../../architecture/design-system.md)

## Goal
Give Shifa one professional, distinctive and calm visual language that doctors and receptionists can use all day, and the machinery that keeps it consistent: design tokens in one source that generate the web theme and the Flutter theme, a design language chosen by the owner from three directions shown on real screens, a web component library (`packages/ui`) built on UI SDK behaviours with our own styling, a Flutter theme package (`packages/shifa_ui`), and checks in CI (drift, RTL keyboard, accessibility, visual regression). Light and dark themes ship together. No product screen is built here; Phase A builds screens from these parts.

## User stories
- Owner → opens three interactive design directions, each on the same three screens → picks one; it becomes the recorded design language.
- Doctor (later, through Phase A screens) → reads a dense visit screen without strain, works it by keyboard or by touch at the chair, and always knows what is selected, saved or offline.
- Developer or agent → builds a screen from `packages/ui` components and semantic tokens only → RTL, focus, contrast and dark mode are already right.
- Flutter developer → uses `shifa_ui` theme extensions generated from the same tokens → the patient app matches the web.
- Reviewer → opens Storybook → sees every component in Arabic RTL and English LTR, light and dark, with its states.

## Design principles (each direction and each component is judged against these)
1. Calm first: about 70 % neutral surfaces; colour marks meaning (action, state, alert), never decoration. Red is clinical alert only.
2. Glanceable: one primary action per view; status readable in under a second (queue state, saved, offline).
3. Dense but readable: two densities, `comfortable` (touch, 44 px targets) and `compact` (desktop data screens, 32 px rows); data text never below 14 px; tabular digits in numbers.
4. Keyboard and touch equal: every action reachable by keyboard with a visible focus ring; every target usable on a 10-inch tablet.
5. Arabic first: layouts drawn in RTL first; Latin fragments isolated; type scale tuned for Arabic.
6. Honest motion: 120–240 ms, purposeful, off under reduced-motion.
7. Locked clinical meaning: clinical and status colours are not themable and never rely on colour alone (icon or label too).

## Acceptance criteria
1. `packages/tokens` holds DTCG (2025.10) tokens in four layers (primitive, semantic, brand, component) covering colour, typography, spacing, radius, border, elevation, motion, z-index and density. Every semantic colour has a light and a dark value. Clinical and status tokens are marked locked.
2. Style Dictionary v5 generates CSS custom properties (light, dark, both densities), a Tailwind v4 theme and a Dart file. Generated outputs are committed and the `drift` step of `verify` fails when they are stale (closes the Phase 0.2 token drift item).
3. A contrast test computes WCAG 2.2 ratios for every text/surface and icon/surface pair declared in the tokens, in light and dark: body text ≥ 4.5 : 1, large text and UI marks ≥ 3 : 1. The test fails the build.
4. Three design directions exist as interactive prototypes made in Claude Design and stored as static builds, each showing the same three screens with synthetic data: reception queue (desktop), doctor visit (desktop and 10-inch tablet) and patient booking (phone). Each uses the Damascene Jasmine palette, works in RTL, shows light and dark, both densities and the seven principles. The owner picks one; the choice, its rationale and its values (type scale, radius, elevation, motion, icon style) are recorded in the design doc and in the tokens.
5. Fonts are self-hosted and subsetted (IBM Plex Sans Arabic for UI, Noto Naskh Arabic for long text and print), their licences recorded in the repository.
6. `packages/ui` is built on `@ui-sdk/react` and `@ui-sdk/core`, pinned to one exact version, styled with Tailwind v4 logical utilities and semantic tokens only. Lint fails on physical left/right utilities, hard-coded colours, spacing or fonts, any `@ui-sdk/*` import outside `packages/ui`, and any import of the agent bridge (`@ui-sdk/react/agent`).
7. RTL gate, before the rest of the set: Select, Combobox, Menu, Dialog, Popover, Tabs, Date Picker and Number Input pass, in Arabic RTL and English LTR, automated tests for arrow-key direction, popup side and alignment, focus trap and return, typeahead with Arabic letters, Arabic-Indic and Western digit entry, and axe. A component that fails is built on Base UI behind the same `packages/ui` API and listed in the design doc with the upstream issue; the gate result is written to the slice file.
8. Core set, each with the same tests as the gate where they apply: button, icon button, input, textarea, password input, number input, OTP input, select, combobox, checkbox, radio, switch, segmented control, field and form (React Hook Form + Zod), date picker, time input, dialog, alert dialog, drawer, popover, menu, tooltip, tabs, accordion, toast, avatar, badge, card, toolbar, pagination, skeleton, empty state, command palette, data table (TanStack Table + Virtual).
9. Storybook documents every component with RTL and LTR, light and dark, both densities, all states and accessibility notes. Storybook's axe run and Playwright screenshot comparison (in Docker) run in CI and fail the build.
10. `packages/shifa_ui` exposes Flutter `ThemeExtension`s generated from the same tokens (light and dark) and the base widgets: button, text field, card, chip, list item, app bar, bottom sheet, snackbar. Golden tests cover each in RTL, light and dark.
11. A `/ui-component` skill holds the component checklist; the upstream `ui-sdk` agent skill is vendored at a pinned commit after review. `docs/architecture/design-system.md` describes the chosen language and the UI SDK upgrade rule.
12. Design first, code as the source (ADR-0040). A "Shifa" design project exists in Claude: a design system synced from code and read-only (tokens from a generated, drift-checked output of `packages/tokens`; fonts, logo and icons; the components of `packages/ui` pushed with `/design-sync`), a guide page, a proposals canvas and a screens canvas. Every component batch (criteria 7, 8, 10) is coded from a sheet the owner approved, and its real components are synced after its tests pass. Bundling `packages/ui` for the design system is tried on Button first; the result, or the fallback of ADR-0040, is recorded.

## Edge cases
- UI SDK beta release changes behaviour: upgrades are a separate PR that must pass the full RTL, axe and screenshot suites; no automatic updates.
- A component fails the gate: Base UI fallback behind the same API (criterion 7); the public API of `packages/ui` never exposes which library is underneath.
- Clinic brand colour with poor contrast: out of scope here (server side, PLT-41); the tokens define the brand slots and the contrast rule it must meet.
- Mixed-direction text, long Arabic labels, 200 % zoom and reduced motion are states in the stories of every text-bearing component.
- Low-end clinic PCs: no component may need a GPU effect (blur, large shadows) to be readable.
- Offline behaviour: not applicable; the tokens define the offline and syncing status colours. Permissions per role: none.

## Money, abuse and privacy
- Stories, prototypes and screenshots use synthetic names from `@shifa/testing` only.
- The UI SDK agent bridge is not installed or imported anywhere; enabling it needs its own security decision (ADR-0039).
- Fonts and assets are self-hosted; no runtime request to a third-party CDN.
- Design artifacts are private to the owner's account, hold synthetic data only, and their links are not committed (public repository).
- Licences: UI SDK is Apache-2.0, Base UI MIT, fonts OFL; recorded with the dependency.

## Verification contract
| # | Proof |
|---|---|
| 1 | Schema test on the token files: layers, light and dark values present, locked flags. |
| 2 | `verify` drift step: a changed token without regenerated outputs fails (script test). |
| 3 | Contrast unit test over all declared pairs, both themes. |
| 4 | Owner acceptance: opens the three builds, picks one; choice recorded in the design doc and OD-57. |
| 5 | Script test: font files present, subset size budget, licence files present. |
| 6 | ESLint rule tests with failing fixtures for each forbidden pattern; exact-version check in the dependency test. |
| 7 | Vitest browser (Playwright) interaction tests per gate component in both directions, plus axe; results table in the slice file. |
| 8, 9 | Storybook test run (interaction + axe) and Playwright screenshots in Docker, both in CI's `verify (full)`. |
| 10 | Flutter golden tests (alchemist) in `verify`; drift check covers the generated Dart file. |
| 11 | Reviewer check of the skill and the design doc; script test that the vendored skill matches its pinned commit hash. |
| 12 | Drift test for the design-system token output; per batch, the owner's approval of the sheet (date in the slice file) before the first component commit, and the sync recorded after; the Button bundle result in slice 0.4-03. |
