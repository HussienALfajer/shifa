Status: Approved by the owner in [A-03-01](../../slices/A-03-01-design-and-screen-contract.md): reception and chart rows at checkpoint 1, owner tools and settings rows at checkpoint 2 (both 2026-11-27) · Date: 2026-11-27 · Owner: product owner
Companion of [spec A-03](A-03-patients.md) (ADR-0047). Rows come from the drawings. After approval a row changes only in the slice that owns it, with the drawing updated and the owner told.

## How to read and use it
- One row per screen and state. A route used by several screens is listed once per screen, so each screen's needs stay visible.
- **Owner** is the API slice that delivers and tests the row: A-03-02 to A-03-08. An existing route keeps the slice that built it unless it must change; the change is then owned by an A-03 slice.
- Each API slice proves its rows with contract tests: every field present with its type, every error and status answered as listed. The UI code slices (A-03-09 and A-03-10, after the component slice A-03-12) check every row against the built API before they code.
- **Privacy (spec, "Money, abuse and privacy"; criterion 6).** No name, phone, date of birth, previous file number, search term or custom field value or label in a URL, a query string, a log, a span, an error or audit data. Every route that carries one takes it in the request body, so search, the duplicate check and the family preview are `POST`. Paths carry chart ids (UUIDs) only. Search, the duplicate check, the family preview, the recent list and the read log write no `patient.chart_viewed` row; only `GET /patients/:id` does (criterion 18).
- **Shared answers, not repeated per row:** 401 `session_expired` → sign-in with the reason; 403 `forbidden` → the shell's "not allowed" page; 403 `support_read_only` on a write in a support session → the action is not offered there in the first place (A-02); a lost answer (no network) → the screen's own failed state named in its row. Timestamps are ISO date-times (UTC) shown in the device's zone; dates of birth are ISO dates.
- **A chart in an answer** (`PatientCard`, used by search, recent, family and candidates): `id`, `displayName` (given, father, family), `fileNumber` (integer), `sex` (`male`/`female`), `birthDate` (ISO date), `birthDateEstimated` (boolean; the screen writes «~» before the age), `contactPhone` (E.164; shown in the national form, `0930 012 345` or `+90 532 001 23 45`), `state` (`active`/`archived`/`merged`). The age is worked out on the client from `birthDate` and today (Damascus day): years, or months under 2.
- Labels of keys (relations, sexes, match kinds, roles) come from i18n by key on the client; the API sends keys, never Arabic text, except text a person typed (names, custom field labels and values, branch names).

## Existing API met by these screens (checkpoint 1)
1. `GET /team/members` needs `members.view`, which only the owner holds, so reception cannot list the doctors to pick. A narrow `GET /patients/doctors` (names and `active` only) is added in A-03-04 instead of widening the team list.
2. `GET /auth/session` returns roles but not the effective permission keys, and a member's sensitive overrides (OD-102) change them; the screens need them to show «مريض جديد» and the archived switch. It gains `permissions[]` in A-03-07 (moved from A-03-02 at the re-plan); the server still enforces every key.
3. `GET /clinic/settings` needs `clinic.settings.manage` (owner only), so only the owner's settings screen reads `patients.my_patients_only` there; a doctor learns that they are limited from `limitedToMyPatients` in the search and count answers (A-03-07).
4. The support session's write refusal (403) is unchanged; the chart answers `allowed` so the screen never offers a write it would refuse.
