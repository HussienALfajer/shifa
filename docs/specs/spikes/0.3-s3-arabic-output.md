# Spec 0.3-S3: Arabic output — PDF, thermal receipts, name search (spike)

Status: Draft (awaiting owner approval) · Date: 2026-11-16 · Risk tier: T1 (output and search code; no tenancy, auth, money logic or migrations to the real schema) · Owner: product owner
Requirements: PLT-38, BIL-30, SCH-28, SCH-30, CLN-22, PAT-14, PLT-50; "Arabic-normalised search" in [Release 1 scope](../../product/scope-release-1.md) (no requirement ID yet) · Decisions: [ADR-0021](../../adr/0021-supporting-services.md), OD-20 (digit style, stays open), OD-39, OD-40; result in a new ADR-0034 amending ADR-0021

## Goal
ADR-0021 picks three things nobody has run yet: HTML → PDF through Gotenberg (headless Chromium) with self-hosted Arabic fonts, one HTML/CSS template set for browser printing and server PDFs at A5, A4, 80 mm and 58 mm, raster ESC/POS as the fallback for cheap thermal printers, and an application-side Arabic name normaliser shared by the server (generated or stored column, `pg_trgm`) and the offline clients. This spike proves or breaks each claim with throwaway code and golden tests on synthetic data, so Phase A can build receipts, prescriptions, reports, tickets and patient search on a known base. Owner decisions (2026-11-16): no physical printer in the spike, both widths are tested by images (OD-39); all four document types are rendered; the normaliser adds compound-name space folding and word-final ة/ه and ى/ي folding to ADR-0021's list (OD-40). Accepted ADR-0021 is not edited; only its `Status:` line points to ADR-0034.

## User stories
- Owner (المالك) → reads the spike report → knows, with sample PDFs and images, that Arabic prescriptions, receipts, reports and tickets come out shaped, in the right order and at the right size, and which fonts and settings production uses.
- Receptionist (موظف الاستقبال) → types "فاطمه عبدالله" → finds "فاطِمة عبد الله" on the server and on an offline device alike.
- Developer → changes the normaliser in TypeScript or Dart → a shared test-vector file fails both ports if they disagree.

## Acceptance criteria
1. **Gotenberg pinned:** the spike runs Gotenberg (latest stable 8.x) in a container, image pinned by version and digest, with the chosen Arabic fonts installed in a derived image or served with the HTML; no request leaves the container network (no web fonts, no CDN).
2. **Four documents:** one template set (`dir="rtl"`, `lang="ar"`, CSS `@page`) renders, from synthetic data (`@shifa/testing`): (a) prescription A5 with Latin drug names and doses inside Arabic lines; (b) mixed-currency receipt 80 mm and 58 mm with BIL-30's tender, change, rounding, balance and rate-footer lines; (c) report A4 over at least two pages with a repeating header and page numbers; (d) queue ticket 58/80 mm with a QR code (SCH-28). Each document renders with Western and with Arabic-Indic digits (OD-20 stays open).
3. **Text correctness in PDFs:** for every PDF, text extraction returns the expected Arabic strings in logical order (no isolated or reversed letters), the Latin drug names and numbers are intact, every glyph comes from an embedded font (no fallback, no tofu), and page size matches the `@page` size within 1 mm.
4. **Visual goldens:** each PDF page is rasterised and compared with a committed golden image (pixel threshold stated in the slice); the owner reviews the first goldens by eye before they are committed.
5. **Browser print parity:** the same HTML printed through Chromium's print-to-PDF (Playwright) gives the same page size and the same extracted text as the Gotenberg output, so browser printing and server PDFs match (ADR-0021).
6. **Thermal raster:** the receipt and the ticket render to a 1-bit image 576 px wide (80 mm) and 384 px wide (58 mm), dithered or thresholded, and encode to an ESC/POS `GS v 0` byte stream; a decoder in the test turns the stream back into the image and matches the golden. Arabic stays legible at 58 mm at the chosen font size (owner eye check on the goldens).
7. **Normaliser rules:** one function, in TypeScript and in Dart, applies in this order: Unicode NFC; remove diacritics (tashkeel) and tatweel; fold alef forms (أ إ آ ٱ → ا) and hamza carriers (ؤ → و, ئ → ي); word-final ة → ه and word-final ى → ي; Arabic-Indic and Persian digits → Western; collapse whitespace; join a compound-name particle with the next word (عبد، أبو، أبي، أم، ابن، بن، بنت). The stored display name never changes; only the search key does.
8. **Shared test vectors:** a JSON file of at least 200 input → key pairs (every rule, rule interactions, Latin and mixed input, empty and whitespace-only input) passes in both ports; a property test checks the function is idempotent (`n(n(x)) = n(x)`).
9. **Search behaviour in PostgreSQL 18:** on a throwaway table with RLS, a `tenant_id`-leading GIN trigram index on the search key and the `load` preset's synthetic patients, a query with a spelling variant (each rule in criterion 7) finds the intended patient within the top 5, inside `withTenant()`; the spike also records which variants still fail and the false matches the new rules add.
10. **Where the key is computed:** the report compares a stored column written by the application with a SQL `IMMUTABLE` function in a generated column, and recommends one, with the risk of the two drifting apart.
11. **Measurement (report only):** Gotenberg render time p50/p95 per document type and peak container memory under 5 concurrent requests; search p50/p95 at the `load` volume. No threshold.
12. **Result:** `docs/spikes/s3-arabic-output.md` answers each question below with evidence, the versions and fonts tested and the risks left; ADR-0034 (Accepted on owner approval) records the PDF, font, thermal and normaliser decisions; ADR-0021 gets only `Status: … · Amended by ADR-0034`. Roadmap updated.

## Questions the spike must answer
- Does Gotenberg's Chromium shape Arabic, mixed Arabic/Latin lines and Arabic-Indic digits correctly, and which open-licence font (candidates: Noto Naskh Arabic, Amiri, Vazirmatn, Cairo) reads best on A5 and on 58 mm?
- Do `@page` sizes, page breaks, repeating headers and page numbers behave the same in browser printing and in Gotenberg?
- Is 58 mm legible for an Arabic receipt with all BIL-30 lines, and at what font size?
- What render time and memory should a production PDF worker plan for?
- Does the normaliser find realistic variants without too many false matches, and should the key be computed in the application or in SQL?

## Edge cases
- Very long names and drug names wrap without breaking Arabic joining; a receipt longer than one thermal "page" continues without a cut line.
- Mixed text: a Latin drug name, a dose like "500 mg" and a phone number inside an Arabic sentence keep their order.
- Normaliser: input that is only diacritics or tatweel gives an empty key; Latin names pass through lower-cased; a particle at the end of the name is left alone.
- Offline: the Dart port is what offline devices use; this spike proves equality with the TypeScript port, not device storage (S1 covered that).
- Permissions per role: not applicable (no product endpoints).

## Money, abuse and privacy
- Synthetic data only (PLT-50); no real patient names in vectors, goldens or fixtures.
- Gotenberg runs on an internal network only; the spike never sends it a URL to fetch (HTML is uploaded), so it cannot be used to reach other hosts.
- Never logged: rendered document content, patient names or search terms; logs carry document type, size and timings only.
- Receipts show amounts from fixtures only; no money logic is written here.

Spike code is throwaway and its suites run in a manual CI workflow (OD-31). The shared normaliser test vectors and the goldens are kept for Phase A.

## Out of scope
A physical thermal printer and WebUSB/Web Serial/Bluetooth transport (OD-39, Phase A before the first pilot); QZ Tray or a local print agent; Typst or other PDF engines; production print templates, branding and the template editor (PLT-38); PDF storage in Garage and the pg-boss job; Meilisearch; Latin↔Arabic transliteration; the `ال` prefix (not stripped); custom-field search (PLT-36).
