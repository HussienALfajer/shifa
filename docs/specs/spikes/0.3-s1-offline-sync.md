# Spec 0.3-S1: Offline sync engine (spike)

Status: Approved (owner, 2026-11-15) · Date: 2026-11-15 · Risk tier: T0 (money, tenancy, patient data on devices) · Owner: product owner
Requirements: SCH-13, SCH-14, SCH-16, SCH-31, SCH-32, SCH-33, SCH-34, PAT-08, BIL-24, BIL-25, PLT-01, PLT-50 · Decisions: [ADR-0014](../../adr/0014-offline-sync-engine.md) (Proposed), OD-05, OD-29; result in a new ADR-0031 · Builds on: [0.2-05](../../slices/0.2-05-db-test-harness.md), [0.3-S2](0.3-s2-tenant-isolation.md)

## Goal
ADR-0014 leaves the offline sync engine to a spike: (a) PowerSync self-hosted or (b) a custom outbox (local command log + idempotency keys + a pull endpoint). Both engines send writes through the same server command handler, so the spike builds that handler once (idempotency, the three conflict rules, RLS) and compares the two on the parts that differ: download sync, the local store, the upload queue, tenant scoping of what reaches a device, SDK stability on web and Flutter, and the load of running the service. A throwaway reception prototype (web) runs the full offline scenario on both engines; a thin Flutter probe covers the patient app's cached reads and pending writes. Network loss is real: a proxy cuts and degrades the link in automated runs, and the owner runs one 2-hour Wi-Fi-off test on two devices. Owner decisions (2026-11-15): reception on web in full plus a thin Flutter probe; automated cuts plus one manual 2-hour run; prototypes are thrown away but the scenario suite stays (manual CI dispatch, reused in Phase A); offline cash allows sales and refunds only (OD-29).

## User stories
- Owner (المالك) → reads the spike report → knows which engine reception and the patient app use, with evidence from real cuts.
- Receptionist (موظف الاستقبال) → loses internet for two hours → keeps registering walk-ins, printing tickets (provisional number, رقم مؤقت), changing statuses and taking cash; on reconnect sees every remapped number and every conflict.
- Patient (المريض) → opens the app in airplane mode → sees cached appointments and ticket; a cancellation made offline syncs later.
- Developer in Phase A → reruns the scenario suite against the real reception module.

## Acceptance criteria
1. **Shared server side:** a spike-only API (outside `apps/api`) with minimal tables `appointment`, `queue_ticket`, `cash_session`, `cash_movement`, `offline_command`, all with `tenant_id` and FORCE RLS, accessed through `withTenant()`. Writes are commands carrying a client UUID idempotency key; a replayed key returns the stored result (SCH-13).
2. **Conflict rules (server):** (a) queue numbers come from a per-shift sequence; offline tickets carry a provisional number and the device id, and the server assigns the real number in sync order (SCH-16, SCH-32); (b) an overlapping appointment is rejected by the exclusion constraint and returned as a conflict, never silently dropped (SCH-14); (c) cash movements are append-only and always accepted into an open session (BIL-25). Every conflict and remap is returned to the client.
3. **Offline cash (OD-29):** a cash session is opened online. Offline, only `sale` and `refund` movements are allowed, at the last synced exchange rate, and the receipt shows that rate and an "offline" mark. Close, expense, deposit and float adjustment are refused offline with an Arabic message.
4. **Engine (a) PowerSync:** self-hosted service (latest stable, pinned by digest) with PostgreSQL bucket storage (no MongoDB); sync rules or streams scoped by tenant and branch from the JWT; uploads via the shared command handler. Web SDK in the prototype, Flutter SDK (drift integration if usable) in the probe.
5. **Engine (b) custom outbox:** web stores commands and today's data in IndexedDB (or SQLite WASM; the plan picks one); Flutter in drift. Download is a snapshot plus changes since a cursor, served through `withTenant()`.
6. **Scenario suite** (engine-agnostic Playwright tests, run against each engine; Toxiproxy between clients and the server): two reception devices of one branch go offline together; over 2 simulated hours (fake clock) they register 40 walk-ins, change 60 statuses, record 50 sales and 5 refunds in SYP, TRY and USD, and book 2 overlapping appointments; then reconnect. Result: zero lost and zero duplicated commands, no duplicate real number, every remap and the double booking shown to staff, cash totals per currency equal to the sum of commands.
7. **Degraded links:** the same suite passes with 30% packet loss, 2 s latency, and a cut in the middle of an upload; a retried upload never duplicates (idempotency).
8. **Offline banner (SCH-33):** shows time offline and pending count; the count reaches zero after sync.
9. **Session expiry:** a 2-hour outage that outlives the access token neither loses queued commands nor lets them sync without re-authentication.
10. **Tenant scoping:** a device of tenant A never receives tenant B rows through either engine, including when the PowerSync replication role bypasses RLS; a command forged with tenant B's ids from tenant A's token is rejected and logged by id only.
11. **Flutter probe (PAT-08):** cached appointments and ticket readable in airplane mode, local store encrypted (SQLCipher); an offline cancellation syncs once on reconnect, on both engines.
12. **Manual run (owner, OD-05):** two real devices on a clinic-like LAN, Wi-Fi off for 2 real hours, the scripted checklist from criterion 6 by hand, browser restarted and laptop asleep once in between. Results in the report.
13. **Result:** `docs/spikes/s1-offline-sync.md` gives per-engine evidence for each criterion, SDK and service versions, bundle size, setup and operating load, and the choice. ADR-0031 records it (Accepted on owner approval); ADR-0014 gets only its `Status:` line updated; OD-05 closed; SCH-34 updated. If inconclusive, the custom outbox wins (ADR-0014 default).

## Edge cases
- Sync order between the two devices is arrival order at the server; numbers follow it. Printed provisional tickets keep their number visible next to the real one (SCH-32).
- Browser storage evicted or the tab closed mid-outage: the report states which commands survive per engine.
- A refund offline for a sale made online the same day must sync; a refund above the original sale is refused.
- Clock skew between devices: the server timestamps on receipt; client time is stored only as information.
- Permissions: the spike uses one receptionist role; the role matrix is Phase A.

## Money, abuse and privacy
- Synthetic data only (PLT-50, `@shifa/testing` generators); no real devices hold real patient data.
- Amounts are integer minor units per currency; no float. Cash movements are never edited or deleted.
- Local stores keep only today's branch data; logout wipes them.
- Never logged or reported: tokens, passwords, patient names, phone numbers, row values. Logs carry tenant ids, command ids and counts only.
- The PowerSync replication role exists only in the spike containers and is never added to `roles.sql` or migrations.

## Out of scope
Production deployment of the sync service; the real reception, billing and patient-app modules (Phase A); voice calling and printing hardware offline (S3, S6); a local edge server (OD-18); conflict UI design beyond plain lists; ElectricSQL and Zero (no offline writes, ADR-0014).
