# Spec 0.3-S4: Imaging — Garage + Orthanc + OHIF over an Aleppo-like link (spike)

Status: Approved (owner, 2026-11-16) · Date: 2026-11-16 · Risk tier: T0 (tenant isolation at the imaging gateway, infrastructure, encryption; throwaway code, no real schema) · Owner: product owner
Requirements: IMG-01, IMG-02, IMG-03, IMG-04, IMG-06, IMG-08, IMG-09 (2D and CBCT MPR only), IMG-14, IMG-17, IMG-25; "DICOM and patient-CD upload from the browser with resumable uploads" in [Release 1 scope](../../product/scope-release-1.md) §5 · Decisions: [ADR-0019](../../adr/0019-imaging-orthanc-ohif.md), [ADR-0021](../../adr/0021-supporting-services.md) (Garage), ADR-0023, OD-18 (stays open), OD-44; result in a new ADR-0035 amending ADR-0019

## Goal
ADR-0019 rests on claims nobody has run: the unmodified Orthanc S3 plugin works against Garage with encryption on, one Orthanc per tenant behind our gateway keeps tenants apart, a CBCT can reach the cloud from a Syrian clinic either from the browser or from an edge box, and OHIF shows it. This spike runs the whole path with throwaway code on synthetic and public data, over three emulated link profiles, and measures what OD-18 needs: how long a CBCT takes, what survives a link cut, and whether browser upload or the edge box is the realistic path. Owner decisions (2026-11-16, OD-44): generated studies of real size plus one public de-identified CBCT; three link profiles; both browser upload and edge-box push; object encryption on from the first write.

## User stories
- Owner (المالك) → reads the spike report → knows upload and viewing times for a 300 MB and a 1 GB CBCT on each profile, and whether clinics with CBCT need an edge box (صندوق الحافة).
- Assistant (مساعد الطبيب) → drops a CBCT folder in the browser on a bad line → the upload (رفع الصور) survives cuts and a page reload and finishes without sending finished files again.
- Doctor (الطبيب) → opens the study (فتح الدراسة) → sees the first image and then the MPR in OHIF.
- Developer → changes the gateway → isolation tests fail if tenant A can reach tenant B's study or an Orthanc system route.

## Link profiles
All clinic-side traffic (browser, edge Orthanc) reaches the cloud side only through one link shaper (`tc netem` or Toxiproxy; the slice picks).
| Profile | Up | Down | RTT | Loss | Cuts |
|---|---|---|---|---|---|
| P1 fixed-poor | 1 Mbps | 3 Mbps | 150 ms ±30 | 1% | 30 s every 5 min |
| P2 fixed-normal | 3 Mbps | 10 Mbps | 80 ms | 0 | none |
| P3 mobile | 8 Mbps | 25 Mbps | 60 ms ±20 | 0 | none |

## Acceptance criteria
1. **Stack pinned:** Garage, Orthanc (official image with PostgreSQL index, S3 object storage, DICOMweb, Transfers and GDCM plugins), PostgreSQL 18 and OHIF v3 (an unmodified release build) run in containers, every image pinned by version and digest. Orthanc is reachable only from the gateway's network; a test from the clinic side gets no connection to any Orthanc port.
2. **Licence boundary (IMG-04):** a check fails if anything other than Orthanc configuration JSON is mounted into an Orthanc container (no Python/Lua scripts, no extra plugins).
3. **Garage compatibility:** through the S3 plugin, Orthanc stores, reads and deletes instances in Garage; deleting a study leaves no objects for it; files are lossless as received (IMG-06: SHA-256 of each retrieved instance equals the source).
4. **Encryption at rest:** the S3 plugin's encryption is on before the first write; no stored object contains the `DICM` marker or a known pixel run from the source; an Orthanc started with a wrong master key cannot read the study.
5. **Per-tenant storage (IMG-02):** two tenants, each with its own Orthanc and its own database on one PostgreSQL server. The spike tests bucket-per-tenant (tenant A's Garage key gets `AccessDenied` on B's bucket) and records whether a shared bucket with prefixes can give the same guarantee.
6. **Gateway isolation (IMG-03):** the same study (same UIDs) uploaded by both tenants stays two separate studies; a viewer token for A gets nothing of B's through QIDO-RS, WADO-RS or STOW-RS; unknown routes and Orthanc REST routes (`/tools`, `/system`, `/instances`, `/plugins`, `/jobs`) are refused; an expired or forged token is refused. Every allowed access writes one audit line (actor, tenant, study id, action; IMG-25).
7. **Test data (OD-44):** a generator writes synthetic CBCT studies with names from `@shifa/testing`: multi-file 300 MB and 1 GB (16-bit phantom with noise, so compression is realistic) and one single-file multi-frame 300 MB; plus a synthetic panoramic X-ray. One public de-identified dental CBCT under CC0 or CC BY is downloaded by a script pinned by SHA-256 and never committed; a check fails if any patient tag in it holds a value other than an anonymised placeholder.
8. **Browser upload:** a throwaway page uploads a folder through the gateway, comparing STOW-RS per instance with retry and a chunked resumable upload (tus or own chunks, slice decides). On P1 the 300 MB studies (multi-file and single-file) finish; after a cut and after a page reload with the same folder re-selected, upload resumes from server state; the cloud ends with exactly the source instances (count and SHA-256) and the bytes sent again stay under one chunk per interrupted file.
9. **Edge box (IMG-17):** an edge Orthanc (SQLite) receives the studies by C-STORE (`storescu`), then pushes to its tenant's cloud Orthanc with the Transfers plugin through the gateway, which allows the Transfers push routes for an edge credential only. On P1 the push completes after cuts and after an edge Orthanc restart mid-job; the cloud study matches the source (count and SHA-256).
10. **Viewing:** OHIF, served from the gateway origin with a viewer token, opens the panoramic and the 300 MB CBCT through the gateway on P1–P3 and on the edge box over the LAN (no shaping); a Playwright test asserts the first image renders and MPR renders.
11. **Measurement (report only):** per profile, study and method: upload time, effective throughput against link rate, bytes on the wire against study bytes (Transfers gzip vs browser), bytes re-sent after cuts; viewer time to first image and to MPR ready; encryption overhead on upload and retrieval; peak memory of Orthanc and the gateway. The 1 GB study runs on P1 and P3 at least. No thresholds.
12. **Result:** `docs/spikes/s4-imaging.md` answers each question below with evidence and the versions tested; ADR-0035 (Accepted on owner approval) records Garage use, bucket layout, encryption, the upload protocol and Transfers through the gateway; ADR-0019 gets only `Status: … · Amended by ADR-0035`. OD-18 gets the bandwidth evidence and stays open for hardware. Roadmap and imaging domain doc updated.

## Questions the spike must answer
- Does the Orthanc S3 plugin work with Garage, encryption included, and what breaks?
- Bucket per tenant or prefix per tenant?
- On a 1 Mbps uplink, how long do 300 MB and 1 GB CBCTs take, and is browser upload acceptable or is the edge box required for CBCT clinics?
- STOW-RS per instance or chunked resumable upload for the browser?
- How much does Transfers' compression save on CBCT, and does a job survive cuts and an edge restart?
- Is a CBCT viewable in OHIF over each profile, or only on the clinic LAN?

## Edge cases
- One instance larger than a chunk (single-file multi-frame); a folder with a DICOMDIR (uploaded files are those it references, not the DICOMDIR itself); a non-DICOM file in the folder is skipped and listed.
- Upload of a study already complete is a no-op; two tabs uploading the same study end with one copy.
- Offline: the browser keeps upload state on the server only; after a reload the user re-selects the folder (file handles do not survive). The edge box queues while the link is down.
- Permissions per role: not modelled; one spike user per tenant plus one edge credential.

## Money, abuse and privacy
- Synthetic and public de-identified data only (ADR-0023); nothing from a real clinic.
- Never logged by the gateway, the generator or the tests: DICOM tag values (names, IDs, birth dates), tokens, keys. A test searches gateway and Orthanc logs for the synthetic name marker and fails if found.
- Keys and Garage credentials are generated per run, never committed (ADR-0026).
- The gateway refuses by default; Orthanc has no published port.
