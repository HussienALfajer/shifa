## Goal
ADR-0016 and ADR-0017 rest on claims nobody has run: WAHA's free image with the GOWS engine and PostgreSQL session storage holds a linked WhatsApp Business number across restarts, its webhooks give us inbound messages, acks and session states in a usable shape (including `@lid` senders), and our own layer can enforce opt-in, opt-out, per-number pacing, quiet hours, a circuit breaker and the fallback ladder, and verify a phone by a code the patient sends first. This spike builds that layer with throwaway code against a **fake WAHA** for every automated test, then proves the fake honest with **one manual run on real WhatsApp** using two numbers the owner owns. It does not measure ban thresholds: those need weeks of real clinic traffic and stay with the OD-12 pilot. Owner decisions (2026-11-17, OD-45): fake gateway for automated tests plus one manual run; two dedicated numbers (never the owner's personal or a clinic's number); the real run is one day at small volume; the official Cloud API for +90 numbers is out of scope.

## User stories
- Owner (المالك) → reads the spike report → knows whether WAHA GOWS is fit for Phase A, what each clinic must do to link a number (ربط الرقم), and which risks remain for the pilot.
- Patient (المريض) → taps "تحقق عبر واتساب" and sends the prefilled message → the phone is verified (تم التحقق) without any code sent to them.
- Patient → sends "إيقاف" to the clinic → gets no more WhatsApp messages from that clinic.
- Receptionist (موظف الاستقبال) → the clinic's number is paused or unlinked → sees a "send manually" task (إرسال يدوي) with the prepared text instead of a silent failure.
- Developer → changes the pacing or the matcher → tests with fake timers and the fake gateway fail on any breach.

## Acceptance criteria
1. **Stack pinned:** WAHA (latest 2026.x free image at slice start, `devlikeapro/waha`) runs with the GOWS engine, PostgreSQL 18 session storage and an API key, image pinned by version and digest, on a private network with no published port; webhooks reach the spike service only, signed with WAHA's HMAC option, and an unsigned or wrongly signed webhook is refused.
2. **Fake gateway:** a fake WAHA serves the endpoints the spike uses (session start, status, QR, send text, seen, typing, LID lookup) and emits `message`, `message.ack` and `session.status` webhooks with WAHA's shapes; it can inject 463, 475 and its warnings, `FAILED`/`STOPPED`/`SCAN_QR`, timeouts, duplicate and out-of-order webhooks and `@lid` senders. Fixtures captured in the manual run (criterion 11, numbers scrubbed) replay through the spike's parsers with the same result as the fake's own events.
3. **One send interface (MSG-11, MSG-32):** all sends go through `sendWhatsApp(clinicId, patientId, templateKey, vars)`; outside production it delivers only to numbers on an allowlist and drops the rest with a log line that has no phone number.
4. **Opt-in and opt-out (MSG-13, MSG-14):** an inbound message stores the last inbound time per (clinic, patient); a send to a patient without one is refused before it is queued; "إيقاف", "ايقاف", "STOP" and "stop" (trimmed, any case, Arabic-Indic digits and tashkeel ignored) opt the patient out at once, the next queued message is dropped, and one confirmation is sent; a new inbound message other than the keyword opts back in.
5. **Pacing (MSG-15, MSG-19):** per session one send at a time from a pg-boss queue; a random 20–60 s gap; seen and typing before each send, typing time proportional to length; a cap per rolling 60 minutes (default 30, configurable; OD-46); quiet hours 21:00–08:00 in the clinic's time zone, with sends deferred to 08:00 plus a random spread rather than released at once; one of 3–5 wording variants per send. Fake-timer tests over a simulated day with 200 queued messages show no overlap, no gap under 20 s, no rolling 60 minutes over the cap and no send in quiet hours. Two sessions in different containers do not block each other (MSG-10).
6. **Circuit breaker and fallbacks (MSG-01, MSG-02, MSG-16):** on 463, 475 or a warning the session stops sending for 24 h, every pending message becomes an inbox record plus a manual-send task with a prefilled `wa.me` link, and the clinic admin gets one alert; the session is never re-paired automatically, and after the 24 h it stays paused until the clinic admin confirms resumption (OD-46). Gateway down, timeouts and `FAILED`/`STOPPED` take the same fallback without the 24 h pause, and sending resumes when the session is `WORKING` again (OD-46); a send whose outcome is unknown after a timeout is never retried automatically (at most one copy reaches the patient) and becomes a manual task marked "maybe sent".
7. **Health (MSG-17):** a job every 5 minutes maps session states to a clinic-visible state and alerts on unlinked sessions; the report states what signal, if any, WAHA GOWS gives for "phone not seen", and the job warns at 10 days from that signal or from the last successful send or inbound message.
8. **Acks (MSG-18):** delivered and read acks update the delivery attempt; duplicate and out-of-order acks never move the state backwards.
9. **Reverse verification (MSG-12, MSG-20, MSG-22, MSG-24):** a device asks for a nonce (10 minutes, bound to the device and the claimed number) and gets a `wa.me/<platform number>?text=<code + phrase>` link; the webhook matches the code and the sender's phone (an `@lid` sender is resolved first; if it cannot be resolved, verification fails closed); the device learns the result by polling or websocket; the platform replies "verified" in the same chat. Failures: expired nonce, wrong device, sender differs from the claimed number, code reused, code sent by a third number, more than 5 attempts per device or per number per hour. The platform session never sends a message that is not a reply to an inbound message in the last 10 minutes (a test asserts this for every outbound on that session).
10. **Tenant and role separation (MSG-09):** two clinic sessions and one platform session on the fake gateway; an inbound message on clinic A's session never changes clinic B's opt-in, never verifies a phone, and a verification code sent to a clinic number is ignored; a webhook naming an unknown session is refused. The platform session runs in its own container.
11. **Manual run (OD-45, one day):** with the owner's two dedicated numbers — gateway number G (WhatsApp Business app on its own phone) and patient phone P — the owner links G by QR, P verifies by reverse code, P opts in, G sends 20–40 paced messages through the interface over the day with all controls on, acks are seen, P opts out and back in, WAHA restarts and the session resumes from PostgreSQL without a new QR, G's phone goes offline for an hour while sending continues, and G is unlinked and re-linked. G plays the platform role and then the clinic role in turn. The owner follows a checklist (`docs/spikes/s5-manual-checklist.md`) and records every warning or error code.
12. **Measurement (report only):** memory and CPU of the WAHA container idle and with one live session; webhook latency from send to ack; time to resume after restart; queue latency under the pacing rules. No thresholds.
13. **Result:** `docs/spikes/s5-whatsapp.md` answers each question below with evidence and the versions tested; ADR-0036 (Accepted on owner approval) records the gateway, engine, storage, webhook, queue and verification decisions; ADR-0016 and ADR-0017 get only `Status: … · Amended by ADR-0036`. OD-12 gets the run's evidence and stays open for the pilot thresholds. Roadmap and messaging domain doc updated.

## Questions the spike must answer
- What licence covers the WAHA image we run, including the GOWS engine, and may a multi-tenant SaaS use it?
- Does a GOWS session survive a container restart from PostgreSQL storage, and what forces a new QR?
- How do `@lid` senders arrive on GOWS, and can WAHA always resolve them to a phone number for verification?
- Are seen, typing, acks and session events all available on GOWS? What does switching to NOWEB cost (re-link)?
- Is a pg-boss queue per session the right pacing engine, or does it need Valkey?
- Which signals warn before a ban or cap, and how early can the platform see them?
- How many sessions per container is a safe start (MSG-10), from the measured memory of one?

## Edge cases
- Code sent with extra text, Arabic-Indic digits or tashkeel; sent twice; sent after the nonce expired; sent from a group, a broadcast list or a status reply (ignored).
- Edited, deleted, media and reaction messages: never count as a code; any of them counts as inbound for opt-in.
- Inbound while the session is paused still records opt-in and opt-out; WAHA restart mid-send; webhook arriving before the send call returns.
- Quiet-hours boundary at 21:00 and 08:00; hourly cap reached mid-batch; a bulk delay notice to 60 patients is spread, not burst.
- Offline: the gateway or the link is down → fallbacks as in criterion 6; the patient app is not built here.
- Permissions per role: one admin user per clinic for linking; not otherwise modelled.

## Money, abuse and privacy
- No real patient data (ADR-0023). The manual run uses only the owner's two numbers; both are on the allowlist and in an untracked local env file, never committed (ADR-0026). Fixtures are scrubbed of numbers, names and message text before commit, and a check fails on any `+963`/`+90` number that is not synthetic (OD-23).
- Never logged: phone numbers, message bodies, verification codes, QR payloads, API keys, HMAC secrets. A test searches spike and WAHA logs for the run's markers and fails if found.
- The QR equals account takeover: shown only to the clinic admin in the spike page, never stored or logged.
- Abuse: brute force of codes (rate limits, single use, short TTL); a clinic number used to spam (opt-in gate, cap, no free-form bulk); the platform number never initiates (criterion 9).
- Money: none.
