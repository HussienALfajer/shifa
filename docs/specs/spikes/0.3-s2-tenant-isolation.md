# Spec 0.3-S2: Tenant isolation behind PgBouncer (spike)

Status: Approved (owner, 2026-11-12) · Date: 2026-11-12 · Risk tier: T0 (tenancy, RLS, patient-data isolation) · Owner: product owner
Requirements: PLT-01, PLT-50 · Decisions: [ADR-0004](../../adr/0004-postgresql-pooled-tenancy-rls.md), [ADR-0005](../../adr/0005-drizzle-withtenant.md); result in a new ADR-0030 · Builds on: [0.2-05](../../slices/0.2-05-db-test-harness.md), [0.2-06b](../../slices/0.2-06b-rls-isolation-suite.md)

## Goal
ADR-0004 claims that transaction-scoped tenant context (`set_config(..., true)` inside `withTenant()`) is safe behind PgBouncer in transaction mode, where many clients share few server connections. Nothing has proven it yet: today's tests connect to PostgreSQL directly. This spike puts PgBouncer (latest stable, transaction mode) between `shifa_app` and PostgreSQL 18 in the test harness and attacks the claim with leak tests: context left behind on a reused server connection, session-level settings, errors and dropped clients mid-transaction, named prepared statements, and heavy concurrency. It also takes one report-only measurement of RLS cost. Owner decisions (2026-11-12): the leak tests are not throwaway; they stay in CI on every PR. PgBouncer is the only pooler tested. Performance is measured but does not gate the spike. The result goes into a written spike report and ADR-0030, which amends ADR-0004/0005. Accepted ADRs are never edited; only their `Status:` line points to ADR-0030.

## User stories
- Owner (المالك) → reads the spike report → knows, with evidence, whether one clinic's patients can ever appear to another clinic behind the pooler, and which PgBouncer settings production must use.
- Developer → runs `pnpm --filter @shifa/db test` → the isolation suite runs both directly and through PgBouncer, and fails if any path leaks.
- Future operator → copies the PgBouncer settings from ADR-0030 into deployment → gets the configuration the tests proved.

## Acceptance criteria
1. The test harness starts a PgBouncer container next to the PostgreSQL container: image pinned by version and digest in `test-harness/image.ts`, `pool_mode = transaction`, `max_prepared_statements` > 0, a userlist generated per run (no committed password), and a server pool small enough (`default_pool_size = 2`) that server connections are reused all the time. The guard accepts only the PgBouncer host and port the harness created.
2. `@shifa/db/testing` gains `pooledTestDb()`: the same `createDb()` as `testDb()`, connected as `shifa_app` through PgBouncer. `createDb()`'s role check passes through PgBouncer and still refuses an unsafe role behind it.
3. Every case in `test/isolation/cases/` runs twice in CI: direct and through PgBouncer. A tenant table without a case still fails the suite.
4. **Context reuse:** after a `withTenant()` that commits, one that rolls back, and one whose statement fails, the next transaction on the same server connection (forced by a pool of 1) sees empty `app.tenant_id`, `app.branch_id` and `app.user_id`, and zero rows of the probe table.
5. **Session-level leftovers:** a raw `shifa_app` client through PgBouncer runs a session-level `SET app.tenant_id` / `set_config(..., false)` for tenant A and disconnects. Later, on that server connection, `withTenant(B)` sees only B's rows and `withPlatformAdmin` sees no tenant rows. The report says whether production needs `server_reset_query_always` (with its measured cost) or whether the wrapper's local override is enough, and why.
6. **Broken clients:** a client killed mid-transaction (socket destroyed after `set_config`, before COMMIT) leaves no context and no open transaction on the server connection that the next client gets; the same holds after `idle_in_transaction_session_timeout` fires.
7. **Prepared statements:** a Drizzle named prepared statement (`.prepare(name)`) executed for tenant A, then for tenant B on shared server connections, returns only the current tenant's rows each time, including after enough executions for PostgreSQL to switch to a generic plan.
8. **Concurrency:** at least 50 concurrent `withTenant()` calls over 20 rounds, spread across at least 3 synthetic tenants (from `@shifa/testing`), on 2 server connections; each call checks that `current_setting('app.tenant_id')` equals its own tenant and that every row it reads has that tenant's id. Zero mismatches.
9. **Session features:** the report lists what breaks in transaction mode (session advisory locks, `LISTEN`, `SET` outside a transaction, session temp tables, `WITH HOLD` cursors). One test proves the transaction-scoped forms (`pg_advisory_xact_lock`, `ON COMMIT DROP`) work. `.claude/rules/db.md` and `packages/db/CLAUDE.md` forbid the session forms.
10. **Plan check (CI):** on a test-only probe table with a `tenant_id`-leading index and the `load` preset's volume, `EXPLAIN` of a typical tenant query as `shifa_app` uses that index and is not a sequential scan.
11. **Measurement (report only):** `pnpm --filter @shifa/db bench:rls` measures p50/p95 latency of the same query (a) through PgBouncer with RLS as `shifa_app` and (b) through PgBouncer without RLS (a bench-only BYPASSRLS role inside the throwaway container), and writes `.verify/s2-bench/report.json`. Its numbers, versions and machine go into the report. No threshold.
12. **Result:** `docs/spikes/s2-tenant-isolation.md` gives the answer (safe / safe with these settings / not safe), the evidence per criterion, the PgBouncer, PostgreSQL and Drizzle versions tested, and the risks left. ADR-0030 (Accepted on owner approval) records the pooler decision and the required PgBouncer settings. ADR-0004 and ADR-0005 get only `Status: … · Amended by ADR-0030`. Roadmap updated.

## Edge cases
- A leak found by the spike is a result, not a reason to drop the test. The fix (code or PgBouncer setting) ships in this slice with the test that proves it. If no fix is possible, the report says "not safe", and ADR-0030 proposes the alternative (for example session mode, or no pooler) for the owner to decide.
- Drizzle 1.0 RC (ADR-0005 caveat): the spike tests the pinned version and does not upgrade it. The report names the version so a later upgrade reruns the same tests.
- PgBouncer restarts or reloads mid-run: out of scope for correctness; the report notes the expected behaviour.
- Offline behaviour and per-role permissions: not applicable (database layer; there are no product endpoints yet).

## Money, abuse and privacy
- Synthetic data only (PLT-50); tests connect only to the containers the harness created.
- The bench-only BYPASSRLS role exists only inside the bench container and is never added to `roles.sql` or migrations. The RLS presence check still rejects any such role in the real schema.
- Never logged or reported: passwords, the userlist, connection strings with credentials, row values. Test failures report tenant ids and row counts only.

## Out of scope
Other poolers (PgCat, Supavisor); production PgBouncer deployment, TLS between pooler and database, and HA (with `/release` and ADR-0022); load testing with a threshold; the `tenant_deployment` routing table and real tenant tables (Phase A); a Drizzle upgrade; the audited admin role for `withPlatformAdmin`.

## Amendments
- 2026-11-12, owner (OD-27), criterion 9: temporary tables stay refused to `shifa_app`, `ON COMMIT DROP` included (the baseline revokes TEMPORARY). The test proves the refusal; `pg_advisory_xact_lock` is the transaction-scoped form that must work.
- 2026-11-12, owner (OD-28), criterion 5: production uses `server_reset_query = DISCARD ALL` with `server_reset_query_always = 1`, because the wrappers reset only the `app.*` settings and other session state (a WITH HOLD cursor, a session advisory lock) was shown to reach the next tenant.
