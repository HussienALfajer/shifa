# Spec 0.3-S7: Push — FCM delivery on Android (spike)

Status: Approved (owner, 2026-11-19) · Date: 2026-11-19 · Risk tier: T1 (Firebase service-account key and app config in a public repository; no patient data, no schema; throwaway code) · Owner: product owner
Requirements: MSG-01 (steps 1–2 only), MSG-26, MSG-27, MSG-29, MSG-30, PAT-20 (push part), PAT-21, PAT-29 · Decisions: [ADR-0017](../../adr/0017-notifications-push-whatsapp.md), [ADR-0012](../../adr/0012-flutter-patient-app.md), OD-52; result in a new ADR-0038 amending ADR-0017

## Goal
ADR-0017 makes FCM push plus the in-app inbox the primary patient channel, on the owner's word that Firebase works in Syria and Azaz and on research that lists the rules but never ran them [RN-10 §6]. This spike builds a throwaway Flutter probe app and a small sender that apply those rules (own high-importance channel "مواعيد", Android 13+ permission after a meaningful action, visible high-priority messages, `collapse_key` per appointment, TTL, `analyticsLabel`, inbox fetched on open) and measures delivery on Android emulators across app and device states, then in a one-day run. Owner decisions (2026-11-19, OD-52): emulators only now, real phones in Aleppo and Azaz before the first pilot; the one-day run replaces a multi-day field test; the pass mark is 95% of pushes shown within 60 s in the states where Android allows delivery, and no message lost without an inbox record; the production Firebase project is used, with a separate spike Android app inside it.

## User stories
- Patient (المريض) → books, then allows notifications when asked ("لنذكّرك بموعدك") → receives "دورك قريب" and "تفضّل إلى العيادة ٢" while the phone sleeps.
- Patient → opens the app after being offline → sees every missed message in the inbox (صندوق الإشعارات), even if the push never arrived.
- Backend, later → knows a device's permission and channel state → falls back to WhatsApp or the manual task instead of trusting a dead push.
- Owner → reads one report → keeps, amends or replaces FCM as the primary channel.

## Acceptance criteria
1. **Probe app:** a Flutter app under `spikes/s7-push/` (Flutter from `.fvmrc`, `firebase_messaging`, spike package id) creates the channels "مواعيد" (high importance) and "عام" (default) at first launch, asks POST_NOTIFICATIONS only after a "book" button (MSG-26), refreshes and reports its FCM token, permission and channel state on every open, and logs each received message (id, label, sent time, received time, app state) locally and to the spike receiver when online.
2. **Sender:** a Node script sends through FCM HTTP v1 with a service account limited to FCM sending: visible high-priority notifications for appointment events (MSG-27), normal priority for silent sync, `collapse_key` per synthetic appointment, a TTL ending at the appointment time, and an `analyticsLabel` on every send prefixed `s7_` (MSG-29). It records send time, message id and the FCM response; `UNREGISTERED` tokens are marked dead.
3. **Inbox (MSG-01, PAT-29, MSG-30):** every send first writes an inbox record in the spike receiver; the probe fetches the inbox on open and while open polls it, so the live queue view does not depend on push. A message is "lost" only if it is neither shown as a push nor in the inbox.
4. **State matrix on an emulator:** each of these, 20 sends per state, latency from send to shown recorded: foreground; background; swiped from recents; screen off; Doze forced (`dumpsys deviceidle force-idle`); App Standby buckets `rare` and `restricted`; after a reboot before the app is opened; force-stopped (expected: no delivery until opened); network off for 10 minutes then on (with and without TTL expiry; collapse leaves one message per appointment); emulated slow link (emulator network speed and delay set to a recorded profile); permission denied; channel "مواعيد" turned off.
5. **Deprioritisation:** a run that sends high-priority messages which the app does not show (on a second app instance) is compared with the compliant instance, to check whether FCM lowers priority; result recorded, not required.
6. **Pending limit:** 120 non-collapsible messages to an offline emulator, then reconnect; the outcome is recorded against FCM's documented limit of 100 pending messages, and the collapsed variant is shown to avoid it.
7. **One-day run:** on two emulator images (API 33 and the newest stable API, versions recorded) one push every 15 minutes from 08:00 to 21:00 with Doze cycles between sends; latency per message, Firebase Aggregated Delivery Data pulled once before the report closes (it lags up to 5 days; an empty answer is recorded as such). The machine's network and its country, as stated by the owner, are recorded.
8. **Pass mark (OD-52):** FCM stays primary if, in the states of criterion 4 where Android allows delivery (all but force-stopped, `restricted`, permission denied and channel off) and in the one-day run, at least 95% of pushes are shown within 60 s and no message is lost (criterion 3). The other states must be detectable by the backend from the reported device state.
9. **Battery guide draft (MSG-28, PAT-30):** the report carries a short Arabic guide per brand (Samsung, Xiaomi/Redmi/POCO, Oppo/Realme, Tecno/Infinix, Huawei) from public sources, with links and dates, marked unverified until the real-phone run (OD-52).
10. **Result:** `docs/spikes/s7-push.md` answers the questions below with versions; ADR-0038 (Accepted on owner approval) records the send policy, device-state reporting, inbox rule and pass mark; ADR-0017 gets only `Status: … · Amended by ADR-0038`. Roadmap and messaging domain doc updated.

## Questions the spike must answer
- Does a visible high-priority push reach a dozing or idle Android within 60 s, and which states lose it?
- What must the backend know (token, permission, channel, last seen) to fall back in time?
- Do collapse keys and TTL keep an offline phone from a pile of stale reminders?
- What remains to check on real phones in Aleppo and Azaz before the pilot?

## Edge cases
- Token rotates mid-run, or the app is reinstalled: old token returns `UNREGISTERED` and is dropped.
- A message arrives twice (retry): the probe dedupes by message id.
- Clock skew between machine and emulator: latency uses one clock (the receiver's) where possible, otherwise the skew is measured and recorded.
- Offline: the probe shows the cached inbox; sends queue at FCM until TTL.
- Permissions per role: not modelled (single synthetic patient; no login in the spike).

## Money, abuse and privacy
- No patient data (ADR-0023): synthetic names, clinics and appointment times only; push bodies hold no diagnosis or specialty.
- Production Firebase project (OD-52): the spike uses its own Android app id and the `s7_` label prefix, so its data can be told apart and deleted; the spike app is removed from the project after the result.
- `google-services.json` and the service-account key live in untracked files, never committed (ADR-0026) or logged; a check fails if a key pattern or the config appears in the spike folder, logs or reports. FCM tokens are not committed either; reports show a short hash.
- Money: FCM is free; no paid Firebase product is enabled.
