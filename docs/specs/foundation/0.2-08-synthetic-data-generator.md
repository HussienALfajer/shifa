# Spec 0.2-08: Synthetic multi-clinic data generator

Status: Approved (owner, 2026-11-11) · Date: 2026-11-11 · Risk tier: T1 · Owner: product owner
Requirements: PLT-50, CLN-38, MSG-32 (new) · Decisions: ADR-0023, OD-23 · Policy: [data handling §1](../../compliance/data-handling.md)

## Goal
Give every test, demo and Claude Code session realistic data that is never real: a deterministic generator in `packages/testing` (`@shifa/testing`) that builds in-memory, typed records for several clinics in Aleppo and Azaz (tenants, organizations, branches, resources, practitioners and their roles, patient accounts with family dependents, patient charts, Syrian Arabic names, +963/+90 phones and money in SYP, TRY and USD). The same seed always gives the same data. No domain tables exist yet, so this slice writes nothing to a database; each Phase A slice that adds a table adds the matching insert helper. Dental charts, fractures, PROM answers and DICOM join the generator with Phases B, C and D. TypeScript only; the Flutter app gets its data through the API later.

## User stories
- Developer or Claude session → calls `generateDataset({ seed, preset })` → gets the same clinics, doctors and patients every run, so failing tests are reproducible.
- Isolation-suite author → takes the `minimal` preset → gets two tenants whose rows never share an id.
- Scheduling, search or messaging slice author → finds the hard cases already in the data: duplicate full names, Arabic spelling variants (همزة, ة/ه, ى/ي), several family members on one phone, Turkish-format names in Azaz.
- Owner (المالك) → shows a demo with the `demo` preset → sees a solo doctor (طبيب منفرد), a multi-doctor clinic and a multi-branch group with believable Arabic names.

## Acceptance criteria
1. `generateDataset({ seed, preset })` is exported from `@shifa/testing`; it takes no I/O and needs no network, database or environment variable.
2. Determinism: the same `seed` and `preset` give deep-equal output in two calls and on every machine; a different seed gives different output. Dates derive from a `Clock` argument (default `FixedClock` at 2026-01-01T00:00:00Z), never the system time.
3. Presets: `minimal` (exactly 2 tenants, 1 branch and 1 practitioner each, ≥ 5 patients each), `demo` (≥ 4 tenants covering solo, multi-doctor and multi-branch; at least one in Aleppo and one in Azaz) and `load` (counts from parameters, default 50 tenants × 1,000 patients).
4. Shape follows the tenancy model (PLT-01 to PLT-07): every tenant-scoped record carries `tenantId`; each organization belongs to one tenant, each branch to one organization, each resource to one branch; a practitioner is global and has one role per organization/branch it works in; a patient account is global and links to at most one chart per organization; a chart's MRN is unique within its organization.
5. Referential integrity: every foreign key in the output points at a record in the same dataset and, for tenant-scoped records, in the same tenant. Ids are UUID-format strings, unique across the whole dataset.
6. Solo tenant (PLT-03): one organization, one branch, one practitioner. At least one practitioner in `demo` holds roles in two different tenants (PLT-05).
7. Names: each person has given, father and family name (plus grandfather and mother's given name on adults), in Arabic, drawn from hand-written lists of common Syrian given and family names in the package. Sex matches the given-name list. Azaz tenants include Turkmen/Turkish-format family names.
8. Name edge cases in `demo` and `minimal`: at least one pair of patients in one organization with identical full names, and at least one name in each variant class: hamza forms (أ/إ/ا), ة vs ه ending, ى vs ي ending, a compound name (عبد ال…), a name with the article ال.
9. Phones: E.164 strings; Aleppo patients mostly `+9639…`, Azaz patients a mix of `+9639…` and `+905…`, both on real operator prefixes listed in the code with their source. Every number is a well-formed mobile number (`+963` then 9 digits starting with 9; `+90` then 10 digits starting with 5). No phone schema exists in `packages/contracts` yet, so the generator exports its own format regexes; the first Phase A slice with a phone field reuses them. At least one account in `demo` carries two or more dependents on one phone (PLT-07).
10. Synthetic-phone marker: the subscriber digits after the operator prefix always start with a fixed marker (`00`), and `isSyntheticPhone(e164)` returns true for every number the generator can produce for any seed and false for a number without the marker. The marker only helps tests; it does not prove a number is unassigned. The messaging doc states MSG-32: non-production environments send messages only to an explicit allowlist (OD-23).
11. Money (BIL-01 to BIL-04): amounts are `{ amountMinor: bigint, currency: 'SYP' | 'TRY' | 'USD' }`, never `number`; each branch enables the currencies of its city (Aleppo: SYP + USD; Azaz: TRY + USD, some also SYP); each tenant has base currency USD; generated price-list amounts are whole multiples of the currency's cash unit (SYP 10.00, TRY 1.00, USD 1.00) and on new-pound scale (no ×100 old-pound values, BIL-05).
12. Ages and dates: birth dates give a spread of children, adults and over-65s; no birth date after the clock's now; dependents under 18 are linked to an adult account.
13. Performance: the default `load` preset generates in under 10 s in CI.
14. No real data: the package contains no real clinic, doctor or patient records; clinic names come from patterns (e.g. "مركز {family} لطب الأسنان"); names are only list combinations. A check (`no-real-data` test) fails if any generated phone is not synthetic or any money amount is a float.

## Edge cases
- Seed `0`, negative and very large seeds work; non-integer seeds are rejected with a typed error.
- `load` parameters of 0 or above a cap (10,000 tenants, 1,000,000 patients) are rejected.
- Name collisions across tenants are allowed and expected; MRN collisions inside one organization never happen.
- Offline behaviour: not applicable (pure library). Permissions per role: not applicable (no endpoints).

## Money, abuse and privacy
- No real person or clinic is ever copied in; chance matches of a list-combined name with a real person are accepted.
- Synthetic phones can match real people. Mitigation (OD-23): the messaging slice must refuse to send outside production unless the number is on an explicit allowlist (MSG-32); `isSyntheticPhone` helps tests assert it.
- Tenant scoping: tenant-scoped records always carry `tenantId`, so seeding later goes through `withTenant` and the isolation suite can reuse the data.
- Logging: the generator logs nothing. Generated names and phones count as patient data in log-scrubbing tests (data handling §1).

## Verification contract
| # | Proof |
|---|---|
| 1 | Unit test imports from `@shifa/testing`; a test runs with network and env access absent (no `process.env` read, checked by a test that freezes `process.env`). |
| 2 | Unit test: two calls deep-equal; golden test pins a SHA-256 of the canonical JSON of `minimal` seed 1; different seeds differ. |
| 3 | Unit test per preset counting tenants, types, cities, branches, patients. |
| 4, 5, 6 | Integrity test walks every record across seeds 1–50 for all presets except `load`: unique ids, valid FKs, same-tenant FKs, MRN uniqueness, solo shape, cross-tenant practitioner. |
| 7, 8 | Unit tests on names: parts present, sex matches list, each variant class present, duplicate full-name pair present. |
| 9, 10 | Unit tests over seeds 1–50: E.164 format and operator prefixes, the exported format regexes match, `isSyntheticPhone` true for all and false for unmarked numbers; dependents on one phone present. Docs check: MSG-32 in the messaging doc and OD-23 closed. |
| 11 | Unit tests: `typeof amountMinor === 'bigint'`, cash-unit multiples, branch currencies by city, base currency USD, no amount over the old-pound threshold. |
| 12 | Unit test on age buckets and dependent links with a `FixedClock`. |
| 13 | Timed unit test of the default `load` preset (< 10 s, run in `verify:full`). |
| 14 | `no-real-data` test as stated, plus reviewer check of the name and pattern lists. |

## Out of scope
Database seeding and insert helpers (each Phase A slice adds its own); a demo-seed CLI; Dart generator or JSON fixtures; dental charts, fractures, PROM answers, synthetic DICOM (Phases B–D); appointments, invoices, receipts and exchange rates (their Phase A slices); de-identification pipeline for staging.

## Open questions
None. OD-23 closed 2026-11-11 (realistic prefixes + non-production send allowlist).
