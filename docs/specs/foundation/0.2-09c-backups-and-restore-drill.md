# Spec 0.2-09c: pgBackRest backups and a restore drill

Status: Approved (owner, 2026-11-11) · Date: 2026-11-11 · Risk tier: T0 (backups of patient data, encryption keys, infrastructure) · Owner: product owner
Requirements: PLT-51 (new), PLT-50 · Decisions: ADR-0022 (proposed), [ADR-0029](../../adr/0029-backup-targets-and-local-operations-stack.md), ADR-0021 (Garage), ADR-0004 (RLS) · Siblings: [0.2-09a](0.2-09a-wsl2-move.md), [0.2-09b](0.2-09b-observability-skeleton.md)

## Goal
Prove, before any real data exists, that Shifa's PostgreSQL can be backed up and restored to a point in time within the targets the owner set (ADR-0029, 2026-11-11): data loss at most 5 minutes (RPO), restore within 4 hours (RTO). The slice delivers a local stack (PostgreSQL 18 with pgBackRest, Garage as an S3 repository), backup and restore scripts with the production schedule as configuration, and a restore drill that CI runs every week on synthetic data and that fails when the restored database differs from what was written. Production hosting and the off-site second provider wait for OD-01; the scripts already take a second repository by configuration.

## User stories
- Developer → runs `pnpm backup:up` and `pnpm backup:full` → has an encrypted backup of the local database in Garage.
- Developer → runs `pnpm backup:restore --target-time <ISO time>` → gets a fresh PostgreSQL restored to that moment, without touching the source.
- Owner (المالك) → gets a red CI run if the weekly restore drill fails, and reads the drill report (date, duration, backup label, checks passed).
- Future operator → follows `docs/process/backup-restore.md` → can restore production at 3 a.m. from the same scripts that CI exercises.

## Acceptance criteria
1. `infra/backup/compose.yml`: PostgreSQL 18 with pgBackRest installed, and a single-node Garage with one bucket and a key limited to that bucket; images pinned by version and digest; ports bound to `127.0.0.1`. `pnpm backup:up`, `backup:down`, `backup:reset`.
2. pgBackRest config (template in the repository, secrets from env): repository type `s3` on Garage, `repo1-cipher-type=aes-256-cbc` with the passphrase from `PGBACKREST_REPO1_CIPHER_PASS`, compression `zst`, `archive_mode=on`, `archive_command` = `pgbackrest archive-push`, `archive_timeout=60s` so WAL ships at least every minute under low traffic (RPO ≤ 5 min).
3. Schedule and retention as configuration, with the commands the scheduler calls: full backup weekly, differential daily, WAL continuous; retention 30 days (`repo1-retention-full-type=time`, 30). In this slice the schedule is documented and scripted (`backup:full`, `backup:diff`), not run by a local cron.
4. `backup:check` runs `pgbackrest check` and `pgbackrest info`, exits non-zero when WAL archiving is broken or the newest backup is older than the schedule allows, and prints the backup set labels and the newest archived WAL time, nothing else.
5. `backup:restore` restores into a new, empty PostgreSQL container (never over the source), with `--target-time` for point-in-time recovery or the latest point by default, then promotes it and prints its connection port. It refuses to run if the target data directory is not empty.
6. Restore drill `pnpm backup:drill` on a fresh stack: runs the repository's migrations; inserts synthetic rows from `@shifa/testing` into a drill table in a `drill` schema; takes a full backup; inserts batch A; records time T; inserts batch B; forces a WAL switch; restores to T in a new container; then asserts: the baseline and batch A are present with equal row counts and an equal checksum of their canonical rows, batch B is absent, the migration journal matches the source, and every tenant table still has RLS enabled and forced with its policies and the app's non-owner role (the 0.2-06b presence check run against the restored database).
7. The drill writes a report (`.verify/backup-drill/report.json` and a short Markdown summary): date, PostgreSQL and pgBackRest versions, backup label, restore target time, restore duration, each check's pass/fail. No row values.
8. The drill fails (exit 1) if any check fails or the restore takes longer than 15 minutes in CI. The report also shows the measured restore rate (MB/min), and the backup doc explains how that rate is used to check the 4-hour RTO at production size.
9. CI: `.github/workflows/backup-drill.yml` runs the drill every week and on manual dispatch, with pinned actions, a passphrase generated per run (never stored), and the report uploaded as an artifact. It is not a required PR check; `verify:full` does not run it.
10. A wrong passphrase, a missing WAL segment or an unreachable Garage each make the drill fail with a clear message; the drill has a self-test mode for each of the three faults.
11. `docs/process/backup-restore.md`: architecture, schedule and retention, how to back up, check, restore to a time, rotate the passphrase, add the second off-site repository (`repo2`, blocked by OD-01), and the quarterly production drill. PLT-51 added to the platform domain doc; data handling §3 links it.

## Edge cases
- Backup while migrations run: pgBackRest backups are online and consistent; the drill includes a migration before the backup.
- Restore target before the oldest backup or after the newest WAL: the script refuses with the valid range.
- Garage full or down: `archive-push` fails, PostgreSQL keeps the WAL locally and retries; `backup:check` fails.
- Losing the passphrase loses the backups: the doc says where production keeps it (Infisical, later) and that a copy is held offline by the owner.
- Object storage (Garage attachments) and Orthanc backups: not in this slice; listed in the doc as later work.
- Offline behaviour and permissions per role: not applicable (operations tooling, no product endpoints).

## Money, abuse and privacy
- In development and CI, backups contain synthetic data only (PLT-50); the drill never connects to anything but its own containers.
- Backups are encrypted at rest by pgBackRest before they reach the repository; the bucket key can read and write only that bucket.
- A restore must not weaken tenant isolation: the drill checks RLS, forced RLS, policies and roles after restore (criterion 6).
- Never logged or reported: the passphrase, S3 keys, connection strings with passwords, row values. pgBackRest log level stays at `info` (no SQL).

## Verification contract
| # | Proof |
|---|---|
| 1, 2 | Script tests on the compose file and config template: pinned images with digests, `127.0.0.1` bindings, cipher and archive settings present, no secret literal. |
| 3, 4 | Script tests with a stub `pgbackrest` binary: retention flags, schedule commands, `check` exit codes for broken archiving and stale backups, output contains no secret. |
| 5 | Drill step: restore into a new container; script test that a non-empty target directory is refused and an out-of-range target time is refused. |
| 6, 7, 8 | `pnpm backup:drill` passing locally (owner acceptance in WSL2, report in the slice file) and in the first CI run; report schema test. |
| 9 | Workflow lint (pinned actions check from 0.2-02) and one manual dispatch run that passes. |
| 10 | Drill self-test mode run in CI for the three faults, each expected to fail with its message. |
| 11 | Reviewer check of the docs and PLT-51 text; `security-reviewer` on the whole slice. |

## Out of scope
Production and staging backup deployment and the off-site provider (OD-01); a hot standby or replica; object storage and Orthanc backups; per-tenant restore or export (PLT-49 is separate); backup monitoring alerts (with 0.2-09b's later alerting); Infisical.
