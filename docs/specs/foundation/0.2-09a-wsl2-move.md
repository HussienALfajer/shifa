# Spec 0.2-09a: Development environment in WSL2

Status: Approved (owner, 2026-11-11) · Date: 2026-11-11 · Risk tier: T0 (development environment, sandbox) · Owner: product owner
Requirements: PLT-50 · Decisions: ADR-0023, ADR-0025, ADR-0027, ADR-0028, [ADR-0029](../../adr/0029-backup-targets-and-local-operations-stack.md) · Siblings: [0.2-09b](0.2-09b-observability-skeleton.md), [0.2-09c](0.2-09c-backups-and-restore-drill.md)

## Goal
Make WSL2 with Ubuntu 26.04 LTS the primary development environment, so the Claude Code sandbox (filesystem and network isolation) finally runs and local commands match CI (Linux). The owner installs Ubuntu; the slice delivers a step-by-step setup guide, an environment check (`pnpm env:check`) and the doc updates. The repository lives on the Linux filesystem (`~/src/shifa`), not on `/mnt/d`. The Windows checkout (`D:\shifa`) stays supported as a fallback without the sandbox (owner, 2026-11-11). Docker keeps running through Docker Desktop with WSL integration, which Testcontainers already uses.

## User stories
- Owner (المالك) → follows `docs/process/wsl2-setup.md` once → has Ubuntu 26.04, Node 24, pnpm 12, FVM Flutter and Docker working in WSL2 and the repository cloned there.
- Developer or Claude session → runs `pnpm env:check` → sees in a short table what is ready and what to fix, before any `verify`.
- Claude session in WSL2 → runs with the sandbox on → cannot reach domains outside the allowlist or write outside the project.
- Developer on Windows → keeps working in `D:\shifa` → every script and hook still works; `pnpm env:check` warns that the sandbox is off.

## Acceptance criteria
1. `docs/process/wsl2-setup.md` lists the exact steps: `wsl --install -d Ubuntu-26.04`, WSL2 settings (memory limit, `systemd=true`), Docker Desktop WSL integration, Node 24 and pnpm 12 by the pinned method the repository already uses, `fvm 4.3.2` + `fvm install`, the sandbox packages Claude Code needs on Linux (`bubblewrap`, `socat`), git identity and `core.autocrlf=false`, cloning into `~/src/shifa`, creating `.env` files from `.env.example` (never copied from Windows, never production values), opening the folder in the Claude desktop app and VS Code (Remote - WSL).
2. `pnpm env:check` (`scripts/env-check.mjs`; `pnpm doctor` is a built-in pnpm command, so the name differs) checks and prints one line per item with `ok`, `warn` or `fail`: Node major 24, pnpm version equal to `packageManager`, FVM Flutter equal to `.fvmrc`, Docker daemon reachable, git `core.autocrlf` not `true`, no CRLF in tracked text files (`git ls-files --eol`), on Linux: repository not under `/mnt/` and `bwrap` and `socat` on PATH; on Windows: `warn` "sandbox unavailable on Windows". Exit code 1 on any `fail`, 0 otherwise. It reads no `.env` value and prints no secret.
3. In WSL2, `pnpm install`, `pnpm verify:full` and `node scripts/run-script-tests.mjs` pass on a fresh clone with no change to tracked files (`git status` clean afterwards).
4. In WSL2, the Claude Code hooks run (node on PATH of the shell Claude uses), and `.claude/settings.json` keeps `sandbox.enabled: true`; the network allowlist covers what `pnpm install`, `fvm`, `pub get` and `gh` need, and nothing broader than domains named in the file.
5. Sandbox proof in WSL2: inside a Claude session, a request to a non-allowlisted domain (for example `curl https://example.com`) is refused, and a write outside the project folder is refused; an allowlisted fetch (`pnpm view zod version`) works.
6. Windows fallback: `pnpm verify` and the script tests still pass on Windows (CI keeps no Windows job; the owner's machine is the check). Scripts touched by this slice use `node:path` and no shell-specific syntax.
7. Docs: root `CLAUDE.md` Gotchas, `docs/process/development-workflow.md` §10, `docs/compliance/data-handling.md` §1 and the roadmap say WSL2 is primary and Windows is the unsandboxed fallback; the roadmap's WSL2 line is checked.

## Edge cases
- Repository cloned under `/mnt/d` by mistake: `env:check` fails with the reason (slow I/O, file watching, permissions) and the fix.
- Docker Desktop stopped or WSL integration off: `env:check` fails on Docker with the setting to enable.
- Two checkouts (Windows and WSL2) on one machine: both are independent git clones; the guide says to push from one and pull in the other, never to share one working tree across both.
- Different line endings in a file created on Windows: `env:check` reports the file; `.gitattributes` already normalises on commit.
- Offline behaviour and permissions per role: not applicable (developer tooling, no product endpoints).

## Money, abuse and privacy
- No real patient data in either checkout (PLT-50, ADR-0023); `.env` files are created fresh in WSL2, with development values only.
- The sandbox is the control ADR-0027 deferred to this slice: with the allowlist, a session cannot send repository content or secrets to an arbitrary host.
- `env:check` never prints environment values, tokens or paths outside the repository and the tool locations.

## Out of scope
Docker Engine installed directly in WSL2 (Docker Desktop stays); a dev container; Linux or macOS machines other than WSL2; a Windows CI job; moving off Docker Desktop licensing; the observability and backup stacks (0.2-09b, 0.2-09c).
