# Spec 0.2-09b: Observability skeleton (OpenTelemetry, GlitchTip)

Status: Approved (owner, 2026-11-11) · Date: 2026-11-11 · Risk tier: T0 (patient data in logs, traces and error reports) · Owner: product owner
Requirements: PLT-52 (new), PLT-50 · Decisions: ADR-0022 (proposed), [ADR-0029](../../adr/0029-backup-targets-and-local-operations-stack.md), ADR-0023 · Policy: [data handling §1](../../compliance/data-handling.md) · Siblings: [0.2-09a](0.2-09a-wsl2-move.md), [0.2-09c](0.2-09c-backups-and-restore-drill.md)

## Goal
Give `apps/api` traces, metrics, correlated logs and error reports from day one, and a local stack to look at them, so every later slice is observable without new plumbing. The API exports OpenTelemetry (OTLP) to an OpenTelemetry Collector; the Collector forwards to a Grafana stack (logs, metrics, traces) and errors go to GlitchTip through the Sentry SDK. Everything runs locally in Docker Compose, bound to `127.0.0.1` (owner, 2026-11-11); staging and production deployment wait for OD-01. The hard rule (PLT-52): no personal or clinical data ever leaves the API in a span, metric, log or error event, proven by a test with synthetic patient data.

## User stories
- Developer → runs `pnpm obs:up` → opens Grafana and GlitchTip on localhost and sees the API's requests, latency, logs and errors.
- Developer debugging a failure → takes the `requestId` from an error response → finds the matching log lines and trace in Grafana and the event in GlitchTip.
- Reviewer → reads one test → knows that a synthetic name, phone, note or token sent in a request never appears in exported telemetry.
- Developer without the stack → runs the API and tests as before; telemetry is off and nothing fails.

## Acceptance criteria
1. Telemetry setup in `apps/api` starts before Nest and is off unless configured: with `OTEL_EXPORTER_OTLP_ENDPOINT` unset no exporter is created; with `SENTRY_DSN` unset the Sentry SDK is not initialised. Both variables are validated in `config/env.ts` and listed in `.env.example` with local values only. The boot check passes in both states.
2. Traces: one server span per HTTP request named by method and route template (`GET /v1/health`, never the raw URL); child spans for PostgreSQL queries without statement parameters or values; resource attributes `service.name=shifa-api`, `service.version`, `deployment.environment`. Incoming `traceparent` is honoured.
3. Metrics: request count and duration histogram by method, route template and status class; process metrics (event-loop lag, memory). No label holds an id, a tenant name or user input.
4. Logs: every pino line inside a request carries `trace_id`, `span_id` and the existing `requestId`; logs reach Loki through the Collector when it is configured and stay on stdout otherwise. The existing redaction paths in `platform/logging.ts` stay.
5. Errors: unhandled exceptions and 5xx responses are sent to GlitchTip with the route template, status, `requestId`, `trace_id` and release; 4xx responses are not sent. The error response body is unchanged.
6. Scrubbing, layer one (in the API): span attributes, metric labels and error events pass an allowlist. Allowed: route template, method, status, durations, `requestId`, `trace_id`, opaque UUIDs (`tenant.id`, `user.id`), error class and stack frames (file, function, line). Dropped: request and response bodies, query strings, cookies, all headers except `user-agent` and `content-type`, IP addresses, database statements' values, exception messages from validation, local variables, breadcrumbs with data.
7. Scrubbing, layer two (in the Collector): an attributes/redaction processor deletes the same denied keys again, so a mistake in the API is caught before storage.
8. Local stack: `infra/observability/compose.yml` with the OpenTelemetry Collector, a Grafana all-in-one image (Loki, Tempo, Prometheus) and GlitchTip (web, worker, its own PostgreSQL and Valkey); images pinned by version and digest; every port bound to `127.0.0.1`; GlitchTip admin password and secret key generated on first `obs:up` into a git-ignored `.env`, never committed. `pnpm obs:up`, `obs:down`, `obs:reset`.
9. One starter Grafana dashboard (request rate, error rate, p95 latency by route) provisioned from a file in the repository.
10. Smoke check `pnpm obs:smoke`: with the stack up, boots the API, calls a health route and a test-only failing route, then asserts within 60 s that a trace is in Tempo, a log line with the same `trace_id` is in Loki, the metric is in Prometheus and one event is in GlitchTip. The failing route exists only when `NODE_ENV=test`, is absent from the OpenAPI document and the route matrix marks it test-only.
11. Docs: `docs/process/observability.md` (how to run, where to look, the scrubbing rules and how to add an attribute safely); PLT-52 added to the platform domain doc; data handling §1 links it.

## Edge cases
- Collector or GlitchTip down: the API keeps serving; exporters drop data after a bounded queue and log one warning per minute, never per request.
- High request rate: the exporter queue is bounded (spans dropped, never memory growth); sampling is 100 % in development and set by env (`OTEL_TRACES_SAMPLER_ARG`) elsewhere.
- An exception whose message contains user input (for example a database error quoting a value): the message is replaced by the error class and code before sending.
- Tests: unit and integration tests run with telemetry off unless a test opts in with in-memory exporters.
- Offline behaviour: not applicable to the API skeleton (clinic offline sync is OD-05). Permissions per role: the local stack has no product roles; GlitchTip has one local admin account.

## Money, abuse and privacy
- PLT-52 is the reason this slice is T0: telemetry is the most common path for patient data to leak to a third system. Allowlist, not denylist, in the API; denylist again in the Collector.
- `tenant.id` is allowed as an opaque UUID for per-tenant debugging; tenant, clinic, doctor and patient names never are.
- No telemetry leaves the machine in this slice: no SaaS endpoint, no Sentry.io; only local containers.
- Secrets for the stack live in git-ignored `.env` files; the CI secret scan covers `infra/`.

## Verification contract
| # | Proof |
|---|---|
| 1 | Unit tests on env parsing; boot check run with and without both variables. |
| 2, 3 | Integration test with in-memory span and metric exporters: span names use route templates, PostgreSQL spans have no values, metric labels are only the listed ones, `traceparent` is continued. |
| 4 | Integration test: a request's log lines carry `trace_id` equal to the span's trace id and the `requestId`. |
| 5 | Integration test with a stub Sentry transport: a 500 sends one event with the listed fields; a 400 and a 404 send none. |
| 6 | **Leak test**: requests carrying synthetic patient data from `@shifa/testing` (name, phone, note text, an auth token) in body, query, headers and cookie, to a route that throws; asserts none of those strings appear in any exported span, metric, log line or error event (serialised and searched). |
| 7 | Collector config test: a script runs the Collector image against a fixture batch containing denied keys and asserts they are gone (runs in `verify:full` when Docker is available, else in CI). |
| 8, 9 | Script tests on the compose file: pinned images with digests, only `127.0.0.1` port bindings, no secret literal; dashboard file parses. |
| 10 | Owner acceptance: `pnpm obs:up` then `pnpm obs:smoke` passes in WSL2; output in the slice file. Route matrix test covers the test-only route. |
| 11 | Reviewer check of the docs and PLT-52 text. |

## Out of scope
Staging and production deployment of the stack (OD-01); alerting rules and on-call; Flutter (`sentry_flutter`) and web app instrumentation (when those apps exist); real user monitoring; log retention policy beyond local defaults; Infisical.
