# Configurable Multi-Tenant B2B SaaS Architecture for a Clinic Management Platform (solo doctor / multi-doctor clinic / multi-branch group)

Research date: 2026-11-07. All prices and limits are "as retrieved on this date" unless a page date is given. Sources marked "(vendor)" are vendor-authored and not neutral. Sources marked "(blog)" are individual or community posts whose measurements were not independently reproduced.

## 1. Multi-tenancy data models (pool / bridge / silo / hybrid), PostgreSQL RLS, and moving a large tenant to a dedicated DB

### Takeaway
Every authoritative guide (AWS SaaS Lens, Azure Architecture Center) treats isolation as a spectrum and recommends a shared ("pool") default with the ability to place specific tenants on dedicated resources ("silo"/vertically partitioned) later. For a clinic platform whose tenants are mostly small, the best default is a pooled PostgreSQL database with `tenant_id` on every row, enforced by Row-Level Security that is set per transaction (`set_config(..., true)`), plus a tenant→deployment ("stamp"/cell) mapping table from day one so a large medical group can later be moved to its own database.

### Cited Findings

**Definitions and official guidance**
- AWS SaaS Lens: the **silo model** gives tenants dedicated resources (e.g., a separate database), but "a silo environment still relies on a shared identity, onboarding, and operational experience"; this distinguishes SaaS from a managed-service model where customers run separate versions with separate onboarding/operations. — [AWS SaaS Lens: Silo, Pool, and Bridge Models](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html)
- AWS SaaS Lens: the **pool model** is "the more classic notion of multi-tenancy where tenants rely on shared, scalable infrastructure"; the **bridge model** is a *mixed mode* where "some of the system is implemented in a silo model and some is in a pooled model", e.g. per microservice, steered by the regulatory profile and noisy-neighbor attributes of each service's data. Note: in the current SaaS Lens "bridge" means mixed silo/pool, not specifically "schema-per-tenant" (the schema-per-tenant meaning comes from older AWS storage guidance). — [AWS SaaS Lens](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html)
- Azure (page metadata updated 2026-10-11): "Selecting a tenancy model isn't only a technical decision. It's also a commercial decision." Decision inputs: business objectives, compliance, scale, automation/ops team size, SLAs. — [Azure: Tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)
- Azure: automated single-tenant deployments: "If a single tenant requires a specific infrastructure cost, 100 tenants probably require 100 times that cost"; maintenance (config, updates) is time-consuming and cross-fleet reporting must be planned. Benefits: isolation, no noisy neighbor, progressive rollout. — [Azure: Tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)
- Azure: fully multitenant deployments are cheapest; moving data between tenants may only require updating tenant identifiers; risks are data leakage, a heavy tenant affecting others, one change affecting the entire customer base, and non-linear scaling cost of one big shared database. — [Azure: Tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)
- Azure: **vertically partitioned** = mix of single-tenant and multitenant deployments (e.g., single-tenant for customers needing higher performance/isolation; you "can even charge customers a higher rate to use a single-tenant deployment"). Risk: "Your codebase needs to be designed to support both multitenant and single-tenant deployments" and you must plan migration from shared to dedicated. **Horizontally partitioned** = shared app tier + per-tenant databases, which mitigates DB noisy-neighbor. — [Azure: Tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)
- Azure: distinguish logical tenants from deployments ("stamps"/"supertenants"); keep a tenant mapping table (tenant ID → deployment ID) so requests route to the right deployment and "you can move tenants between deployments at your discretion"; tenants can be bin-packed into deployments. — [Azure: Tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)
- Azure: test isolation explicitly (cross-tenant leak tests, noisy-neighbor tests, chaos testing). — [Azure: Tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)

**PostgreSQL RLS: pattern and pitfalls**
- AWS Database blog pattern: enable RLS per table; policy compares `tenant_id` with `current_setting('app.current_tenant')::UUID`; set the variable with `SET`/`set_config` each time a connection is handed out; variable names must be prefixed (`prefix.variable`); avoid per-tenant DB roles (`current_user` approach) because it is hard to maintain at scale. — [AWS: Multi-tenant data isolation with PostgreSQL RLS](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/)
- Superusers and roles with `BYPASSRLS` are never subject to policies; the table owner bypasses RLS "unless the table is altered with `FORCE ROW LEVEL SECURITY`"; the app should connect as a role that does not own the objects. — [AWS blog](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/)
- AWS warns: "Using session variables may be incompatible with server-side connection pooling such as pgBouncer" — test whether the pooler shares session state, as a leaked variable could expose another tenant's data. Also: RLS filters reads silently (empty result, no error); inserts that violate policy error; when SELECT and modify policies differ you must include `WITH CHECK`. — [AWS blog](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/)
- Session-level `SET` (or `set_config(..., false)`) under PgBouncer transaction pooling leaks tenant context to the next client; one measured test showed a client with no tenant set could see the largest tenant's 267,023 invoices. Fix: `SET LOCAL` / `set_config($1,$2,true)` inside an explicit transaction (`SET LOCAL` cannot take bind parameters, so use `set_config`). `SET LOCAL` outside an explicit transaction silently does nothing. (blog) — [now-next.nl: PostgreSQL RLS for SaaS, what we measured](https://now-next.nl/en/insights/postgresql-row-level-security-multi-tenant-saas/); [daily.dev: PgBouncer and RLS](https://daily.dev/posts/pgbouncer-and-rls-tenant-context-set-local-shared-plans-wvpn1fj2i)
- Unique / primary-key / foreign-key checks bypass RLS: a line item could be attached to another tenant's invoice, and constraint errors can reveal existence of another tenant's row; views owned by a bypassing role leak all tenants unless `security_invoker=true`; `WITH CHECK (true)` lets one tenant insert rows for another. (blog) — [Bytebase: Postgres RLS footguns](https://www.bytebase.com/blog/postgres-row-level-security-footguns/); [now-next.nl](https://now-next.nl/en/insights/postgresql-row-level-security-multi-tenant-saas/)
- Performance: without `tenant_id` as the leading column of composite indexes RLS queries fell to sequential scans (~120 ms vs ~1 ms in one benchmark); shared prepared-statement plans behind PgBouncer reused a large tenant's plan for a small tenant (7.6 ms vs 0.62 ms, ~10x); per-request ORM hooks that set/reset the tenant can land on three different backend connections; a single batch sending `set_config(..., true)` with the query stayed correct (~0.06 ms overhead). (blog; single-source numbers) — [dev.to: RLS without the performance tax](https://dev.to/software_mvp-factory/postgresql-row-level-security-without-the-performance-tax-436g); [daily.dev: Go, pgx and RLS measured](https://daily.dev/posts/go-pgx-and-postgresql-row-level-security-measured-alrbtv31s); [daily.dev: PgBouncer and RLS](https://daily.dev/posts/pgbouncer-and-rls-tenant-context-set-local-shared-plans-wvpn1fj2i)
- Supabase RLS guidance: index every column used in policies (only the *leading* column of a btree counts as indexed); wrap functions as `(select auth.uid())` so Postgres caches the result per statement (initPlan) instead of per row; use `security definer` functions (with `search_path = ''`, never in exposed schemas) to avoid nested RLS checks; always specify roles with `TO authenticated`; the `service_role`/secret key has `bypassrls` and must never reach a browser. — [Supabase: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)
- Consensus best practice from these sources: transaction-scoped `set_config`, `FORCE ROW LEVEL SECURITY` with a non-owner, non-BYPASSRLS app role, `tenant_id`-leading indexes, and fail closed when no tenant is set. (blog) — [dev.to: PostgreSQL RLS for multi-tenant SaaS](https://dev.to/software_mvp-factory/postgresql-row-level-security-for-multi-tenant-saas-1lgp); [patotski.com: RLS pattern and footguns](https://patotski.com/blog/postgres-row-level-security-multi-tenant/)

**Citus / moving a big tenant**
- Citus row-based sharding: `isolate_tenant_to_new_shard` splits one tenant's hash value into its own shard; then move it to a dedicated node with `citus_move_shard_placement` (formerly `master_move_shard_placement`). Since Citus 11.1 the isolation lets writes continue until the end (earlier versions blocked writes). Co-located tables require `CASCADE`. — [Citus: A look at isolating tenants](https://www.citusdata.com/blog/2017/03/15/a-look-at-isolating-tenants/); [Citus 11.1 shards without interruption](https://www.citusdata.com/blog/2022/09/19/citus-11-1-shards-postgres-tables-without-interruption/)
- Citus schema-based sharding (Citus 12+): every tenant schema is its own shard group by definition, so the question becomes moving that shard group to another node. — [Azure Cosmos DB for PostgreSQL: Sharding models](https://learn.microsoft.com/azure/cosmos-db/postgresql/concepts-sharding-models)
- Older Citus docs say tenant isolation was an Enterprise/Cloud feature; current licensing (Citus has been fully open source since 11.0) was not re-verified this session. — [Citus cluster management v7 docs](https://docs.citusdata.com/en/v7.0/admin_guide/cluster_management.html)
- Crunchy Data has a design overview of Postgres multi-tenancy options (not fully read this session). — [Crunchy Data: Designing your Postgres database for multi-tenancy](https://crunchydata.com/blog/designing-your-postgres-database-for-multi-tenancy)

**Framework support for hybrid**
- ABP Framework supports single shared DB, DB-per-tenant and hybrid: "If a tenant has a separate database it uses that tenant's database, otherwise it filters the tenant data by the TenantId field in shared tables"; per-tenant connection strings via the Tenant Management module; no built-in cross-database query for host-wide reporting. — [ABP: Multi-Tenancy](https://abp.io/docs/latest/framework/architecture/multi-tenancy/index); [ABP community: separate databases](https://abp.io/community/articles/multitenancy-with-separate-databases-in-dotnet-and-abp-51nvl4u9)
- Tenancy for Laravel (stancl/tenancy) v4 defaults to multi-database tenancy; single-database via `BelongsToTenant` trait; v4 adds PostgreSQL RLS-based single-DB tenancy marked **experimental**; parallel migrations. A third-party page says v4 had no stable Packagist tag (verify). — [Tenancy for Laravel v4](https://v4.tenancyforlaravel.com/version-4); [v4 single-database tenancy](https://v4.tenancyforlaravel.com/single-database-tenancy)

### Inferences
- **Scale trade-offs (engineering judgment, synthesized from the above, no single source gives numeric thresholds):**
  - *100 tenants:* any model works. DB-per-tenant is operationally tolerable (100 migrations per release, 100 backup jobs), and per-tenant restore/export is trivial. Pool+RLS is still simpler.
  - *1,000 tenants:* DB-per-tenant needs fully automated, parallel, resumable migrations and fleet monitoring. Schema-per-tenant in one Postgres cluster multiplies catalog objects (tables × schemas). Migrations run N times, `pg_dump` and autovacuum work over very large catalogs, and connection pools are per schema/DB. Pool+RLS keeps one migration and one backup but makes per-tenant restore a logical operation (export rows by `tenant_id`).
  - *10,000 tenants (most of them solo doctors):* pool is the only cost-effective default. Silo only for a small number of premium/large groups (vertical partitioning). Scale out with multiple pooled "cells/stamps" (bin-packing) or Citus row-based sharding on `tenant_id`.
- **Per-tenant restore and export in pool:** design for it up front: every table carries `tenant_id` (including join tables), soft-delete plus audit log, and a tested "export tenant" job (JSON/CSV/SQL) that also serves data-portability requests and migration to a dedicated DB. Point-in-time recovery of the whole cluster cannot restore one tenant without a side-restore and selective copy.
- **Moving a large tenant to a dedicated DB:** with the same schema in pooled and dedicated DBs (keeping `tenant_id` even in dedicated DBs), the move is: (1) create the target DB from the same migrations; (2) bulk copy that tenant's rows (or PostgreSQL logical replication with publication row filters `WHERE (tenant_id = X)`, available since PostgreSQL 15, from background knowledge and not re-verified this session); (3) brief write-freeze; (4) flip the tenant→deployment mapping; (5) delete the rows from the pool after verification. This only works if IDs are globally unique (UUIDv7/ULID rather than per-DB sequences). Note that AWS suggests sequences for performance, which is a trade-off to weigh.
- **For a clinic platform specifically:** medical data raises compliance expectations, so offer "dedicated database" as a premium tier for multi-branch groups (Azure's "charge a higher rate") and keep everyone else pooled.
- Use RLS as **defense in depth**, not the only control: the application layer also scopes by tenant (ORM global scopes or repository filters), and RLS catches mistakes. Add automated cross-tenant leak tests in CI.

### Gaps
- No primary source found with quantitative operational limits for schema-per-tenant in PostgreSQL (e.g., catalog bloat at N thousand schemas); the thresholds above are judgment.
- AWS SaaS Factory's newer (2025–2026) material on cell-based SaaS architecture was not fetched.
- Real-world clinic or health SaaS case studies on tenancy models were not found.

## 2. Organization hierarchy, memberships/roles, cross-tenant practitioner identity, global patient identity, and auth options

### Takeaway
Model a **global identity layer** (users: practitioners, staff, patients, each with one login by phone/email) separate from **tenant-scoped membership/role records** (user × organization/branch × role) and **tenant-scoped clinical records** (patient chart per tenant linked to the global person). Modern IdPs support this "one user, many organizations" model natively (Keycloak 26 Organizations, Zitadel Organizations, Better Auth organization plugin, WorkOS/Clerk organizations). Branch-level scoping usually lives in your own authorization tables, not the IdP.

### Cited Findings
- Keycloak Organizations became fully supported in **26.0.0** (preview in 25.0.0) and target B2B identity: one realm holds many organizations, a user can belong to several, and membership is included as an organization claim in tokens. — [Keycloak GitHub epic #30180](https://github.com/keycloak/keycloak/issues/30180); [CNCF blog: Keycloak 26 organizations](https://cncf.io/blog/2024/11/13/scalable-authentication-across-organizations-with-keycloak-26)
- Third-party guides recommend realm-per-tenant only when a tenant needs its own admins, themes or configuration; realm count increases whole-cluster operational cost. (vendor-adjacent blog) — [Skycloak: Keycloak multi-tenancy guide](https://skycloak.io/blog/the-ultimate-best-guide-on-keycloak-multi-tenancy-part-1/)
- Zitadel: "An Organization is comparable to a tenant in a SaaS system"; hierarchy Instance → Organization → Project; project grants let one org share a project with another and delegate role management; native pattern is one org per customer managing its own users. — [Zitadel docs: Organizations](https://zitadel.com/docs/concepts/structure/organizations); [Zitadel B2B scenario](https://zitadel.com/docs/guides/solution-scenarios/b2b); [Zitadel blog: multi-tenancy with organizations](https://zitadel.com/blog/multi-tenancy-with-organizations)
- A Zitadel community thread shows users trying to model "Client Org → Dept → User" hierarchies, i.e., deeper hierarchies are not first-class and must be modeled in the app or via roles. — [Zitadel Q&A: modeling hierarchy](https://questions.zitadel.com/m/1442515753558474893)
- Better Auth: the organization plugin supports members belonging to multiple teams since v1.3 (breaking change: `teamId` removed from member table, new `teamMembers` table). — [Better Auth 1.3 release](https://better-auth.com/blog/1-3)
- Better Auth phone-number plugin: `sendOtp`/`verify` endpoints, requires a `sendOTP` callback wired to an SMS provider (Twilio, Vonage, etc.), lets logged-in users change their number, and limits verification attempts per OTP against brute force. — [Better Auth: Phone Number plugin](https://better-auth.com/docs/plugins/phone-number)
- WorkOS pricing (from WorkOS blog and third-party summaries, 2026): SSO $125/connection/month for connections 1–15, $100 (16–30), $80 (31–50), $65 (51–100), $50 (101–200), custom above; Directory Sync billed separately on the same tiers; custom domain $99/month; audit logs priced separately; organizations are not the metered unit. (vendor and third-party) — [WorkOS: estimate SSO/SCIM costs](https://workos.com/blog/estimate-sso-scim-costs); [Activepieces: WorkOS pricing 2026](https://www.activepieces.com/blog/workos-pricing-what-each-connection-costs-2026)
- Clerk: plans reported as Hobby (free), Pro ~$25/month (includes one enterprise SSO connection), Business ~$300/month; "first 100 organizations included" with ~$1 per extra org is reported by third parties but not confirmed on Clerk's page; Clerk Billing added per-seat plans for Organizations on 2026-06-10. Sources disagree on prices. — [Clerk changelog 2026-06-10 per-seat plans](https://clerk.com/changelog/2026-06-10-per-seat-plans); [Clerk: pricing explained](https://clerk.com/articles/clerk-pricing-explained); [Activepieces: Clerk pricing 2026](https://www.activepieces.com/blog/clerk-pricing-2026-free-pro-and-business-plans)
- Supabase Auth plus RLS: policies run as `authenticated`/`anon`; tenant/org membership checks typically go in `security definer` helper functions. — [Supabase: RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)
- Azure: in B2B, map tenants to customers but consider sub-groups (divisions, multiple countries); a customer may need multiple tenants for different requirements; consider both tenant and user identity in authorization. — [Azure: Tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)

### Inferences
- **Recommended data model (synthesis):**
  - `account` (billing/contract tenant) → `organization` (legal clinic or medical group; for a solo doctor, account = org = one implicit branch) → `branch/location` → `resource` (room, chair, device) and `schedule`.
  - `person`/`user` (global: phone E.164, email, auth identities) → `membership(user_id, org_id, branch_id NULLABLE, role_id, status)`. A null branch means org-wide. A practitioner working in 3 clinics has one user and 3 memberships, and the UI includes an org switcher.
  - `practitioner_profile` (global: name, specialty, license number, verified flag) + `practitioner_org_profile` (tenant-specific: fees, schedule templates, room assignments, signature/stamp image).
  - Patients: `patient_identity` (global, phone-based login for booking/portal) ↔ `patient_record` (per tenant, owned by the clinic: MRN, chart, consents). Link via a consented `patient_link`. Never let one clinic see another clinic's chart without explicit sharing consent.
- Keep **coarse claims** in the token (user ID, active org ID, roles) and do branch-level and resource-level authorization in the app (RBAC + attribute checks, or a policy engine), because no IdP surveyed models org → branch → room natively.
- **Phone-OTP:** Better Auth (self-hosted, TypeScript) has first-party phone OTP. Keycloak and Zitadel need SMS integration or extensions (not verified in detail this session). Cost and deliverability of SMS/WhatsApp OTP in the target market (Syria) is a separate concern. Consider WhatsApp OTP as a fallback.
- **Choice heuristic:** TypeScript stack → Better Auth (in-process, DB-native, no per-MAU fees). Need standards-heavy SSO/SAML for large hospital groups → Keycloak or Zitadel self-hosted. Hosted SaaS IdPs (WorkOS, Clerk, Auth0) charge per connection or MAU in USD and may be unavailable or awkward for Syrian billing (see Gaps).

### Gaps
- Not verified: Keycloak and Zitadel native SMS OTP support in current versions; Auth0 Organizations current pricing; Supabase phone auth providers available in Syria.
- Vendor availability, sanctions and payment constraints for US identity vendors serving Syria were not researched here.
- No source found describing a production healthcare SaaS "global patient identity with per-clinic charts" design. The model above is synthesis.

## 3. Feature management: entitlements vs feature flags vs configuration/settings, tools, and resolution/cascading patterns

### Takeaway
Treat three things separately: **entitlements** (commercial: what the plan, add-ons and contract grant, including numeric limits), **feature flags** (engineering: release, rollout, kill-switch, experiments, usually short-lived), and **settings/configuration** (behavioral preferences resolved through a hierarchy). Entitlement services (Stigg, Schematic) resolve plan → add-on → override with explicit "increment vs override" and "most generous wins" rules. Flags should go through OpenFeature so the vendor (Unleash, Flagsmith, GrowthBook, LaunchDarkly) can be swapped.

### Cited Findings
- Schematic (vendor): "Feature flags are typically used for gradual rollouts and A/B testing; entitlements are about what a customer has paid for." — [Schematic: Billing vs entitlements](https://schematichq.com/blog/billing-vs-entitlements-whats-the-difference)
- Stigg (vendor): flags are limited for usage limits, plan versioning and pricing-logic enforcement. — [Stigg: Engineer's guide to entitlements](https://www.stigg.io/blog-posts/the-engineers-guide-to-entitlements-what-they-are-and-why-your-current-setup-isnt-enough)
- Stigg entitlement calculation: a customer's entitlement can come from the active plan, a parent plan (plan inheritance), or add-ons. An add-on set to **increment** adds to the plan limit, while **override** replaces it. With conflicting overrides "the maximum override value will be used", and the customer gets the maximum value across sources. — [Stigg docs: Entitlement calculation](https://docs.stigg.io/documentation/managing-customers-and-subscriptions/entitlements/entitlement-calculation.md)
- Schematic: feature checks combine the company's plan entitlement with company-specific overrides and take the most generous value. Policies include add-ons, overrides and individual targeting. — [Schematic docs: Feature management overview](https://docs.schematichq.com/feature-management/overview)
- OpenFeature evaluation context: optional `targeting key` plus arbitrary custom fields (string keys; boolean/string/number/datetime/structure values). Merge order "API (global; lowest precedence) -> transaction -> client -> invocation -> before hooks (highest precedence)". Transaction-context propagation is experimental. The spec mentions "user organization membership" as example context. Tenant/org IDs would be custom fields. — [OpenFeature spec: Evaluation Context](https://openfeature.dev/specification/sections/evaluation-context)
- Licenses (third-party comparisons): Unleash open-source core AGPL-3.0 (sources vary; verify), free self-host with unlimited flags; Flagsmith mostly BSD-3-Clause with paid Enterprise; GrowthBook mostly MIT with enterprise directories under a GrowthBook Enterprise License; LaunchDarkly, Unleash, Flagsmith and GrowthBook each have OpenFeature providers. — [DeployHQ: Feature flag tools compared](https://www.deployhq.com/blog/feature-flag-tools-compared); [PostHog: best open-source feature flag tools](https://posthog.com/blog/best-open-source-feature-flag-tools.md); [FeatBit: OSS feature flag tools guide](https://www.featbit.co/blogs/open-source-feature-flag-tools-2027)
- Unleash's own blog says it is "built to run single-tenant" and positions self-hosting as avoiding shared evaluation infrastructure. (vendor marketing) — [Unleash: alternatives to LaunchDarkly](https://www.getunleash.io/blog/alternatives-to-launchdarkly)

### Inferences
- **Concrete layering for the clinic platform:**
  1. *Entitlements* (DB tables you own, or Stigg/Schematic): `plan` (Solo, Clinic, Group) → `plan_feature(feature_key, enabled, limit)` → `addon` (e.g., "SMS reminders pack", "lab module", "extra branch") with `mode: increment|override` → `tenant_override` (sales/contract exceptions, with expiry and reason) → resolved `effective_entitlement` cached per tenant (invalidate on subscription change). Resolution rule: explicit tenant override > max(override add-ons) > plan + Σ(increment add-ons) > parent plan > default deny.
  2. *Feature flags* (OpenFeature SDK + self-hosted Unleash/Flagsmith/GrowthBook, or an in-house table at first): release toggles evaluated with context `{targetingKey: user_id, tenant_id, org_id, branch_id, plan, specialty, country, app_version}`. Rule: a feature is visible only if `entitled AND flag_on`.
  3. *Settings* (own `settings` table with `scope_type` + `scope_id` + `key` + JSON value + schema version): cascade platform → plan → specialty template → organization → branch → practitioner → user. Resolution = nearest scope that defines the key wins, with per-key metadata: `overridable_by` (which scopes may override), `locked` (an org admin can lock a value so branches cannot change it), `type`/JSON Schema for validation, and `sensitivity` (who can view). Show the "inherited from" source in the admin UI.
- Specialty templates (dentistry vs pediatrics vs dermatology) are best modeled as **settings + form/field presets** applied at org creation (copy-on-create or inherit-by-reference), not as entitlements.
- Keep flags short-lived. Anything that differs by customer permanently belongs in entitlements or settings, not in a flag. Otherwise flags become hidden `if (tenant == X)`.
- For 1–5 engineers, an in-house entitlements table plus OpenFeature with a simple provider is likely enough. Introduce Stigg/Schematic only if pricing experiments, usage metering and billing integration become heavy (both are USD-billed SaaS, which may matter for a Syrian business).

### Gaps
- Current (Nov 2026) pricing for LaunchDarkly, Unleash Enterprise, Flagsmith, GrowthBook Cloud, Stigg, Schematic, Orb was not retrieved.
- No neutral benchmark of entitlement services found. All comparisons found are vendor-authored.
- Unleash's exact license (Apache-2.0 vs AGPL-3.0) conflicts between sources and should be checked on GitHub.

## 4. Per-tenant custom features without forking (build for one, sell to many)

### Takeaway
The proven pattern is "**one codebase, one deployment; customer-specific behavior expressed as (a) a generic feature gated by an entitlement, (b) configuration, or (c) an extension at a well-defined extension point**" (webhooks/events, workflow/rules, sandboxed functions, plugin manifests). Shopify Functions shows the extreme end: customer or partner logic compiled to WebAssembly and invoked only at platform-defined "targets" with a typed input query and output schema.

### Cited Findings
- Shopify Functions: logic is injected at **targets** (defined points in Shopify's backend logic). Each function gets a JSON input produced by a developer-defined GraphQL input query, is compiled to WebAssembly ("any language that can compile a WebAssembly module"; Rust recommended for performance on large carts), returns a JSON document of operations, and cannot be called by URL. Shopify alone invokes it within the customer journey. — [Shopify: Functions](https://shopify.dev/docs/apps/build/functions)
- Salesforce: fields installed from publicly posted AppExchange managed packages generally don't count against per-object custom field limits (except on the Activity object). This is an example of a platform separating "extension package" metadata from tenant-defined metadata. — [Salesforce limits cheat sheet (docs PDF)](https://resources.docs.salesforce.com/208/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf)
- Transactional outbox (enables reliable webhooks/events as extension points): store outgoing messages in an outbox table in the same DB transaction as business data, then relay via polling or log tailing. Delivery is at-least-once, so "a message consumer must be idempotent". Ordering is preserved per send order. — [microservices.io: Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)
- Azure: designing for both multitenant and single-tenant deployments requires a codebase that supports both modes. This argues against per-customer forks or deployments of different code versions. — [Azure: Tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)
- AWS: even silo tenants share "identity, onboarding, and operational experience". Separate versions per customer is the managed-service model, not SaaS. — [AWS SaaS Lens](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html)

### Inferences
- **Playbook ("build once for X, generalize, then sell"):**
  1. Requirement from tenant X → write it as a generic capability with a `feature_key` and settings (no tenant IDs in code).
  2. Gate it: entitlement `feature_key` granted to X via `tenant_override` (contract), flag for rollout.
  3. Harden and productize: add to an add-on or higher plan and grant to others.
  4. If logic is truly bespoke (e.g., a specific insurer's claim export), implement as an **integration module** behind an extension interface (`ClaimExporter`, `InvoiceNumberingStrategy`, `NotificationChannel`) with a module manifest `{key, version, required_entitlements, settings_schema, event_subscriptions, permissions}`, and select the implementation per tenant via settings.
  5. For customer-authored logic: start with **webhooks + outbound events** (outbox) and a **declarative rules/workflow engine** (JSON conditions → actions: e.g., "if appointment type = surgery then require consent form + deposit"). Defer arbitrary scripting. If needed later, use a WASM or isolated-JS sandbox with CPU/memory/time limits (Shopify Functions model).
- **Anti-patterns:** long-lived customer branches; `if (tenantId === 'X')` in code; per-tenant DB schema divergence; flags used as permanent per-customer config; one-off SQL patches in production for a tenant. Each multiplies regression testing and blocks upgrades.
- **Contract/IP (general SaaS practice, not legal advice):** the MSA/order form should state that customer-funded development ("NRE"/professional services) results in vendor-owned platform IP that may be offered to other customers, with optional exclusivity windows (e.g., 6–12 months) priced explicitly. Customer data and customer-specific configuration remain the customer's. Customer-provided materials (forms, letterheads, logos) are licensed to the vendor only to provide the service.

## 5. Custom fields / user-defined fields: storage models, PostgreSQL indexing, limits in major platforms, governance

### Takeaway
For PostgreSQL in 2026 the pragmatic default is **metadata-driven field definitions** (a `field_definition` table with immutable API key, type, validation and permissions) plus **values stored in a JSONB column** on the owning entity, validated against the definition/JSON Schema in the app. Hot fields get expression indexes or generated columns, and broad search uses GIN. EAV is reserved for very sparse or heavily versioned attributes, and typed extension tables for fields the platform itself promotes to first class. Big platforms cap fields per object (Salesforce 500/800, Jira 700 per space), use immutable API names with suffix or prefix conventions (`__c`, `x_`), and soft-delete with a recovery window.

### Cited Findings
- Heap (2016, still widely cited): PostgreSQL keeps no statistics on values inside JSONB, so the planner uses "a hardcoded estimate of 0.1%". In Heap's test, misestimation picked nested loops: 584 s vs ~300 ms for the column-based version. JSONB stores keys in every row (164 MB vs 79 MB for the column table). Moving 45 common fields from JSONB to columns saved ~30% disk. Advice: keep values that occur in most rows as columns, and use JSONB for sparse optional attributes. — [Heap: When to avoid JSONB in a PostgreSQL schema](https://www.heap.io/blog/when-to-avoid-jsonb-in-a-postgresql-schema)
- Salesforce custom fields per object by edition (from Salesforce limits cheat sheet; doc versions ~v198–v210, so possibly dated): Enterprise and Developer 500, Unlimited and Performance 800, smaller editions 100 or 255. Custom relationship fields capped at 40 per object. Active lookup filters 5. Managed-package fields generally excluded from the count. — [Salesforce app limits cheat sheet](https://resources.docs.salesforce.com/208/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf); [Salesforce limits & limitations PDF](https://resources.docs.salesforce.com/210/latest/en-us/sfdc/pdf/limits_limitations.pdf)
- Salesforce soft delete: deleted custom fields and their data are kept until permanently deleted or **15 days** elapse. They still count against custom-field limits until hard-deleted. Deleted field names/API names get `_del` / `_del__c` suffixes. Undelete does not restore package membership or field dependencies, and the unique attribute is removed. — [Salesforce: unused package components](https://developer.salesforce.com/docs/platform/pkg1-dev/guide/unused-package-components.html); [Salesforce Ben: restore deleted fields](https://www.salesforceben.com/how-to-restore-deleted-salesforce-fields/)
- Jira Cloud data limits: **700 fields per space** (enforced since March 2026; trashed fields don't count; no site-wide cap on custom fields), 150 work types per space (enforced March 2026), **20,000 options per field**, 150 workflows per scheme, 200 statuses per workflow, 50 security levels per space, 100 priorities per space (all progressive from September 2026). Guardrails: 30M work items, 30,000 spaces per site. Migrations at ≥90% of a limit get a 3-month exemption. — [Atlassian: Data limits and guardrails](https://support.atlassian.com/jira-cloud-administration/docs/data-limits-and-guardrails/)
- Jira custom field descriptions are limited to 255 characters. — [Atlassian KB: description can't exceed 255 characters](https://support.atlassian.com/jira/kb/jira-custom-field-description-cant-exceed-255-characters)
- HubSpot (KB updated 2026-06-20): custom properties are capped per object by subscription tier. Exact numbers are in the Product & Services Catalog and the account's Data Model → Limits tab. Calculated properties are Professional+ only, custom objects Enterprise only. The limits API reports an overall cap distinct from per-object caps (docs example shows an overall limit of 10,000). — [HubSpot KB: Track CRM data limits](https://knowledge.hubspot.com/data-management/track-crm-data-limits); [HubSpot developer docs: limits tracking](https://developers.hubspot.com/docs/api-reference/legacy/crm/limits-tracking/guide)
- Odoo: fields created outside code (UI/Studio) carry the `x_` prefix (Studio uses `x_studio_`). Odoo's external API docs state "Custom model names must start with x_". The convention is debated and not uniformly applied by community modules. — [Odoo Community mailing list on x_ prefix](https://odoo-community.org/groups/contributors-15/contributors-1937630)

### Inferences
- **Recommended design:**
  - `custom_field_definition(id, tenant_id, entity_type, api_key IMMUTABLE, label_i18n JSONB {ar,en}, type ENUM(text, long_text, number, decimal, date, datetime, boolean, single_select, multi_select, phone, email, file, user_ref, patient_ref), options JSONB, validation JSONB (required, min/max, regex, JSON Schema), default, display (section, order, width, visible_in_print, visible_in_booking), permissions JSONB (view_roles, edit_roles), is_phi BOOLEAN, status (active/archived/deleted_at), version INT, created_by)`.
  - Values: `entity.custom JSONB` keyed by `api_key` (not label). The app validates on write against the current definition, and definitions are versioned so historic records keep meaning. For clinical forms (intake, exam templates), store the `form_version_id` with each submission.
  - Indexing: `CREATE INDEX ... USING GIN (custom jsonb_path_ops)` for containment (`@>`) queries. Use expression indexes `((custom->>'insurance_no'))` or `GENERATED ALWAYS AS ((custom->>'x')::date) STORED` columns plus a btree for fields marked "searchable/sortable". Use `CREATE STATISTICS` or promote to generated columns for fields used in heavy reporting (works around the 0.1% selectivity problem). Index creation per tenant field should be gated by an admin flag and limits.
  - Limits to enforce (borrowing from platforms): e.g., ≤100–200 custom fields per entity per tenant, ≤500–1,000 options per select (Jira allows 20,000; far fewer are needed in clinics), label ≤255 chars, immutable `api_key` with a namespace prefix (`cf_`), soft-delete with a 15–30-day restore window during which the key cannot be reused, and deleted fields count against the limit until purged.
  - Reporting: expose custom fields in reports through a per-tenant "semantic layer" (definition-aware query builder) or by syncing to an analytics store where definitions become typed columns.
  - Permissions per field: enforce in the API serializer (strip fields the role cannot view) and mark PHI fields for audit logging.
- EAV only if fields need per-value history, per-value provenance or very high cardinality. It makes queries and reporting painful. Typed extension tables (`patient_ext_dental`) are best for specialty modules the platform owns.

- Current (2026) Salesforce per-object custom-field numbers were not confirmed on a live help page (only older limits PDFs). Treat 500/800 as long-standing but verify.
- HubSpot per-object numbers per tier were not retrievable (catalog-based).
- No 2025–2026 benchmark comparing JSONB+GIN vs generated columns vs EAV at multi-tenant scale was fetched.

## 6. Custom domains and tenant subdomains (Cloudflare for SaaS, Caddy on-demand TLS, Let's Encrypt limits, Vercel, Approximated)

### Takeaway
Two production-grade paths: (1) **Cloudflare for SaaS** custom hostnames (100 included, then $0.10 per hostname per month, up to 50,000 on Free/Pro/Business; apex proxying only as an Enterprise add-on), with Cloudflare handling DCV, certificates and renewal; or (2) **self-hosted Caddy on-demand TLS** gated by an `ask` endpoint that returns 2xx only for verified, active tenant domains, backed by shared certificate storage and Let's Encrypt/ZeroSSL. Tenant subdomains (`clinic.platform.com`) should use one wildcard certificate via DNS-01, not per-subdomain certificates. Let's Encrypt is moving to shorter certificate lifetimes (45 days by Feb 2028), so automated renewal (ARI) is mandatory.

### Cited Findings
**Cloudflare for SaaS (page last updated 2026-08-14)**
- Available on Free, Pro, Business (Enterprise: contact). **100 custom hostnames included**, **$0.10 per additional hostname** (per month), **max 50,000** hostnames on Free/Pro/Business (Enterprise unlimited; contact sales above 50,000). **Apex proxying/BYOIP: Enterprise paid add-on only.** Custom metadata: Enterprise add-on. Custom certificates, CSR, selectable CA, wildcard custom hostnames and mTLS: Enterprise only. Non-SNI support: Pro and above. Custom origin and analytics on all plans. WAF for SaaS follows the zone plan, and Enterprise gets custom rulesets. — [Cloudflare for SaaS: Plans](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/plans/)
- Hostname validation: **pre-validation** (minimize downtime, `ownership_verification` TXT or `ownership_verification_http` token) or **real-time validation** (easiest for customers, via the CNAME). Certificate DCV via `ssl.validation_records` (TXT or Delegated DCV). Production requires `status: active`, `ssl.status: active`, and the customer's DNS pointing (CNAME) at your SaaS target. Other CDNs that obscure DNS can break validation. Zero-downtime migration from another SaaS provider is supported, and multiple providers can hold an active hostname for the same domain simultaneously. — [Cloudflare: Hostname validation](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/domain-support/hostname-validation/); [Cloudflare for SaaS: domain support](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/domain-support/)

**Caddy on-demand TLS**
- On-demand TLS is for when you "are not in control of the domain names (e.g. they are customer domains)". It "must be both enabled and restricted to prevent abuse". Restrictions are global, not per site. — [Caddy: Automatic HTTPS](https://caddyserver.com/docs/automatic-https)
- `ask` endpoint: Caddy sends a GET with query string `?domain=<name>`. "If the endpoint returns a 2xx status code, Caddy will be authorized to obtain a certificate". Any other status cancels issuance and fails the handshake. The endpoint should be fast (indexed lookup, no DNS or network calls). The legacy `interval`/`burst` rate-limit options are "NOT recommended". The `permission` module interface (`caddytls.OnDemandPermission`) allows custom checks. — [Caddy: Global options (on_demand_tls)](https://caddyserver.com/docs/caddyfile/options)
- Caddy instances sharing storage "automatically share those resources and coordinate certificate management as a cluster". Default issuers: Let's Encrypt with ZeroSSL fallback. Internal rate limit 10 attempts per ACME account per 10 seconds. — [Caddy: Automatic HTTPS](https://caddyserver.com/docs/automatic-https)

**Let's Encrypt (rate-limits page last updated 2026-08-05)**
- New orders per account: **300 per 3 hours** (overridable on request). Certificates per registered domain: **50 per 7 days** (overridable). Duplicate certificates (exact identifier set): **5 per 7 days**. Authorization failures per identifier per account: **5 per hour**. New accounts per IP: 10 per 3 hours. ARI renewals are "exempt from all rate limits", and non-ARI renewals with an identical identifier set are exempt from the new-orders and registered-domain limits. — [Let's Encrypt: Rate limits](https://letsencrypt.org/docs/rate-limits/)
- Lifetimes: 90 days remains default. 6-day short-lived certificates are optional. Maximum lifetime will drop to **45 days by February 2028** (industry rule caps lifetimes at 47 days from 2029-03-15). Reported steps: opt-in 45-day profile 2026-05-13; default 64 days from 2027-02-10; 45 days from 2028-02-16 (the intermediate dates come from a secondary source). DNS-PERSIST-01 validation is expected in 2026. — [Let's Encrypt: Certificate lifetimes](https://letsencrypt.org/docs/cert-lifetimes/); [Gigazine summary](https://gigazine.net/gsc_news/en/20251203-lets-encrypt-decreasing-certificate-lifetimes-45-days)

**Vercel / Approximated**
- Vercel multi-tenant: Hobby up to 50 custom domains per project. Pro and Enterprise "unlimited" subject to soft limits (reported 100,000 per project on Pro, 1,000,000 on Enterprise, raisable via support). **Wildcard SSL requires Vercel nameservers.** Pro is $20 per developer seat per month (third-party, July 2026). — [Vercel: Multi-tenant limits](https://vercel.com/docs/multi-tenant/limits); [Vercel docs mirror](https://examples.vercel.com/docs/multi-tenant/limits); [MassiveGrid: Vercel pricing 2026](https://massivegrid.com/blog/vercel-pricing-explained-2026/)
- Approximated (custom-domain proxy as a service): **$0.20 per custom domain per month** on the cloud plan, with discounts increasing by 5 percentage points per 1,000 domains up to 50%, 400 GB/month bandwidth included, then $0.05/GB. A monthly minimum (~$20/month for <100 domains, per a marketing page) applies. A hybrid self-hosted option exists. — [Approximated pricing](https://approximated.app/pricing/); [Approximated for marketplaces](https://approximated.app/for/marketplaces)
- SaaS Custom Domains (competitor): from $0.20 per domain per month, minimum 100 domains. — [SaaS Custom Domains](https://saascustomdomains.com/)

### Inferences
- **Recommended flow (both paths):** tenant enters domain → app stores `custom_domain(status=pending, verification_token)` → show DNS instructions: `CNAME booking.clinic.com → custom.platform.com` plus `TXT _platform-verify.booking.clinic.com = token` → background job verifies DNS (and CAA records allow the CA) → mark `verified` → (Cloudflare: create custom hostname via API and poll `status`/`ssl.status`) or (Caddy: `ask` endpoint starts returning 200) → `active`. Re-verify periodically and auto-disable on DNS removal.
- **Routing:** an edge/middleware lookup `Host header → tenant_id` (cached in Redis/in-memory, invalidated on domain changes), using a `tenant_hostnames` table holding both `slug.platform.com` and custom domains, with one marked canonical (others 301 to it).
- **Apex domains:** customers' apex (`clinic.com`) cannot be a standard CNAME. On Cloudflare Free/Pro/Business, apex proxying is Enterprise-only, so recommend `www`/`booking` subdomains plus registrar-level redirect from apex, or customers whose DNS supports CNAME flattening/ALIAS. Self-hosted Caddy on a static IP can accept apex via an A record.
- **Let's Encrypt math for self-hosting:** each custom domain is a different registered domain, so the binding limits are 300 new orders per 3 hours per account (onboarding bursts; use multiple ACME accounts or ZeroSSL fallback) and 5 failed authorizations per hour per identifier (the `ask` gate prevents attempts on unverified domains). Renewals via ARI are exempt. For `*.platform.com` use **one wildcard certificate via DNS-01**, since issuing per-subdomain certificates would hit 50 certs/registered domain/week fast.
- **Cost at scale (Cloudflare, list prices):** 1,000 custom domains ≈ (1,000 − 100) × $0.10 = $90/month; 10,000 ≈ $990/month (plus zone plan cost). Approximated at 1,000 ≈ $190/month (with 5% discount); self-hosted Caddy ≈ server costs only but adds ops burden.
- Most solo doctors will use `name.platform.com` and only a minority of groups will buy custom domains, so start with Caddy or Cloudflare SaaS Free tier (100 included) and charge custom domains as an add-on entitlement.

- Netlify domain API limits not researched.

## 7. White-labeling: per-tenant theming, branded booking pages/PWA, and white-label native mobile apps (Apple 4.2.6, Google Play)

### Takeaway
Web white-labeling (logo, colors, letterhead/print templates, branded booking page on a subdomain or custom domain, per-tenant PWA manifest) is cheap and policy-free. **Per-clinic native apps are expensive and policy-constrained:** Apple 4.2.6 rejects template-generated apps unless "submitted directly by the provider of the app's content" (i.e., the clinic's own developer account) and explicitly endorses a single aggregated "picker" app. Google recommends decentralized (client-owned or client-specific) developer accounts with unique listings, and warns that in a centralized account one app's violation can take down all apps. Best fit: one platform-branded patient app (picker model) + one staff app + per-tenant PWA/booking pages, with fully branded native apps offered only to large groups that own their developer accounts.

### Cited Findings
- Apple App Review Guideline **4.2.6**: "Apps created from a commercialized template or app generation service will be rejected unless they are submitted directly by the provider of the app's content. These services should not submit apps on behalf of their clients… Another acceptable option for template providers is to create a single binary to host all client content in an aggregated or 'picker' model, for example as a restaurant finder app with separate customized entries or pages for each client restaurant." — [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- Apple **4.3(a)**: "Don't create multiple Bundle IDs of the same app… If your app has different versions for specific locations, sports teams, universities, etc., consider submitting a single app and providing the variations using in-app purchase." — [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- Google Play white-label best practices: **decentralized** account management recommended (each client or group of clients has its own developer account; "unmanaged" = client controls it, "managed" = white-label developer retains admin access, typical in regulated sectors). **Centralized** (all apps under one developer account) should be very limited because "policy issues with one app can negatively impact all other apps within the same account". "Policy violations on a single account can lead to the removal of all associated apps." In centralized accounts the developer name shown is the same for all apps. — [Google Play: Best practices for white label developers](https://support.google.com/googleplay/android-developer/answer/15884185)
- Google Play: "Each app – even if it is a branded template app – should have its own compelling store listing" (unique description, icons, graphics, screenshots). Reusing descriptions, screenshots or feature graphics is a common violation under the Repetitive Content policy. Screenshots must match the actual app. Avoid keyword stuffing. Announcement dated 2025-02-10. — [Google Play white-label best practices](https://support.google.com/googleplay/android-developer/answer/15884185); [Google Play: Helpful tips for white label developers (Feb 10, 2025)](https://support.google.com/googleplay/android-developer/answer/15931448?hl=en)
- A Play Console community thread reports that the repetitive-content policy applies across accounts, so separate accounts don't automatically avoid it. (unofficial) — [Play Console community thread](https://support.google.com/googleplay/android-developer/thread/229341536/white-label-apps-same-functionality-different-branding?hl=en)
- An older Google policy wording (as quoted by IBTimes) allowed template-generated apps only if published by an individually registered developer account belonging to the tool's user, not the service operator. Current wording was not confirmed. — [IBTimes](https://www.ibtimes.com/google-follows-apples-app-store-cleanup-updated-developer-policy-2703490)

### Inferences
- **Web theming model:** `tenant_brand(logo_light, logo_dark, favicon, primary/secondary colors → generated CSS variables / design tokens, font choice limited to Arabic-capable fonts, letterhead_header_html, footer, stamp/signature images, print_template_ids, booking_page_config, pwa_manifest{name, short_name, icons, theme_color})`. Serve `manifest.webmanifest` dynamically per host. Generate prescription/invoice/report PDFs from HTML templates (RTL-aware) with tenant tokens. Version templates and keep the version used on each printed document for medico-legal reproducibility.
- **Native app options, cheapest to most expensive:**
  1. One patient app "Platform Health" (picker model, explicitly allowed by 4.2.6) plus deep links from each clinic's booking page. In-app branding per clinic after selection.
  2. PWA per tenant (installable from the clinic's domain, its own icon and name). No store review, no developer accounts. iOS PWA push notifications exist for home-screen web apps since iOS 16.4 (background knowledge, not re-verified here).
  3. Fully branded native apps per large group, built from one codebase with build-time variants (e.g., Expo app variants/EAS or Flutter flavors), **published under the client's own Apple and Google developer accounts** (Apple Developer Program fee historically $99/year, not re-verified this session). Each needs unique listings and screenshots, its own signing keys and push credentials, and every release multiplies by N apps (review time, policy changes, SDK target-API updates). Price this as a premium add-on with a setup fee and an annual maintenance fee.
- For Syrian clinics, Apple and Google developer-account registration and payment may be practically difficult for clients (sanctions history, card payments). This strengthens the PWA plus single-picker-app approach (see Gaps).

## 8. Architecture style and recommended stacks for a small team (2026)

### Takeaway
For a small team, sources converge on a **modular monolith** (one deployable, strict internal module boundaries aligned to bounded contexts such as Identity & Tenancy, Scheduling, Patients/EMR, Billing, Notifications, Configuration/Entitlements), with a transactional outbox for reliable events and webhooks, a background-job system, and an append-only audit log. Stack choice is mostly about team skills: TypeScript (NestJS/Next.js + PostgreSQL + Redis + Better Auth) gives one language across web and React Native. Laravel + stancl/tenancy gives the fastest multi-tenant CRUD but its RLS mode is experimental and v4 stability should be checked. .NET + ABP gives the most complete built-in multi-tenancy (hybrid DB-per-tenant, features, settings), with some tooling gated behind commercial licenses.

### Cited Findings
- Multiple 2026 sources recommend a monolith or modular monolith for small teams: one guide says "under about 15 engineers, default to a monolith"; another: "if you can't afford a platform team, you can't afford microservices"; a decision table maps 1–8 engineers to a modular monolith and 12+ with clear bounded contexts toward microservices. Thresholds vary across sources (15/30/50). A widely repeated "42% of teams leaving microservices" statistic could not be traced to a primary study. (blogs) — [Encore: Monolith vs microservices (updated Oct 2026)](https://encore.dev/articles/monolith-vs-microservices); [Milan Jovanović: Modular monolith vs microservices](https://milanjovanovic.tech/blog/modular-monolith-vs-microservices.md); [DevX: How to choose in 2026](https://www.devx.com/development/microservices-vs-monolith-how-to-choose-2026/)
- Transactional outbox: atomic DB update plus message publish without 2PC via an outbox table in the same transaction and a relay (polling or log tailing). Consumers must be idempotent. Order is preserved. — [microservices.io: Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)
- ABP: built-in multi-tenancy with shared DB, DB-per-tenant and hybrid, per-tenant connection strings, and the tenant management module pre-installed in startup templates. One ABP community article says ABP Studio's "separate database per tenant" option is available only for commercial licenses (not confirmed in official licensing docs). — [ABP: Multi-tenancy](https://abp.io/docs/latest/framework/architecture/multi-tenancy/index); [ABP community article](https://abp.io/community/articles/multitenancy-with-separate-databases-in-.net-and-abp-framework-51nvl4u9)
- Tenancy for Laravel v4: multi-DB default, single-DB with `BelongsToTenant`, experimental PostgreSQL RLS, parallel migrations, Scout bootstrapper. Stable-release status should be verified. — [Tenancy for Laravel v4](https://v4.tenancyforlaravel.com/version-4)
- React Native / Expo RTL: `I18nManager.forceRTL(true)` sets a native flag that takes effect only after app reload (no way around it on Android). Recommended UX: let the user pick Arabic, explain a restart, then reload (e.g., via `expo-updates`). Amazon's RN Vega docs (May 2026) confirm changes apply on next start and advise against forcing RTL in production. — [vp0.com: React Native RTL layout](https://vp0.com/blogs/react-native-rtl-flexbox-layout-fix-ai/); [Amazon RN Vega: I18nManager](https://developer.amazon.com/zh/docs/react-native-vega/0.83/i18nmanager.html); [GeekyAnts: RTL in Expo without restarting](https://geekyants.com/blog/implementing-right-to-left-rtl-support-in-expo-without-restarting-the-app)

### Inferences
- **Bounded contexts (proposed):** Platform (tenants, plans, entitlements, domains, branding), Identity & Access (users, memberships, roles, OTP), Organization (orgs, branches, rooms/resources, practitioners), Scheduling (calendars, slots, appointments, waitlists), Patients & Clinical (records, encounters, forms, prescriptions, attachments), Billing (invoices, payments, insurance), Communication (SMS/WhatsApp/push, templates), Configuration (settings cascade, custom fields, forms), Reporting, Audit. Enforce boundaries with module-level public APIs and lint rules (e.g., `dependency-cruiser`/Nx boundaries in TypeScript, Deptrac in PHP, ArchUnitNET in .NET). Cross-module communication goes through in-process domain events written to the outbox.
- **Background jobs:** BullMQ (Redis) for NestJS, Laravel Queues/Horizon, Hangfire or ABP background jobs for .NET. Every job payload carries `tenant_id`, and the worker sets the RLS context per job transaction. Alternatively, Postgres-native queues (pg-boss/graphile-worker) avoid a Redis dependency and can be enqueued in the same transaction (an outbox for free).
- **Audit log:** append-only `audit_event(tenant_id, actor_user_id, actor_membership_id, action, entity_type, entity_id, before/after diff or hash, ip, user_agent, at)`, partitioned by month, never updated, with PHI-access reads (who viewed which patient chart) logged too.
- **Stack comparison for this use case (judgment):**
  - *TypeScript (NestJS or Fastify + Next.js + PostgreSQL + Redis, Better Auth, Drizzle/Prisma/Kysely):* one language across web, API and React Native/Expo. Good RTL in web (CSS logical properties; Tailwind has `rtl:`/`ltr:` variants). Shared validation (Zod) for custom-field schemas. Cons: multi-tenancy, settings and entitlements must be assembled from libraries or written in-house. ORM plus RLS needs care (transaction-scoped `set_config`).
  - *Laravel + stancl/tenancy (+ Filament admin):* fastest CRUD/admin delivery and a large regional developer pool (common in MENA). Cons: the RLS mode is experimental, v4 stability needs checking, and a separate mobile stack is needed.
  - *.NET + ABP:* most "batteries included" (multi-tenancy, feature/entitlement system, settings with hierarchical providers, audit logging, background jobs, localization incl. RTL themes). Cons: heavier framework, commercial license for some modules and tooling, smaller local talent pool in some markets.
  - *Mobile:* Expo/React Native shares TypeScript, types and validation with the backend, but RTL switching requires an app reload, so pick direction at first launch. Flutter has strong RTL via `Directionality`/localizations (from background knowledge, not verified in this session) but adds Dart as a second language. For an Arabic-first product where users rarely switch language, either works. Code sharing favors Expo for a TypeScript team.
