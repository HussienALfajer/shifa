# 0.3-S2b Leak tests behind PgBouncer

Status: In review · Tier: T0 (tenant context, RLS, patient-data isolation) · Branch: `chore/0.3-s2b-pooling-leak-tests`
Spec: [0.3-S2 tenant isolation](../specs/spikes/0.3-s2-tenant-isolation.md) criteria 4–9 · Requirements: PLT-01, PLT-50 · After 0.3-S2a

## Goal
Attack ADR-0004's claim through the real PgBouncer from 0.3-S2a: context left on a reused server connection, session-level settings, killed clients, named prepared statements, heavy concurrency, and session-only features. The tests stay in CI on every PR. A leak found here is fixed in this slice (code or PgBouncer setting) with the test that proves it; if no fix is possible, record it for the S2c report as "not safe".

## Plan
1. **Contracts:** none.
2. **Database tests** (`packages/db/test/pooling/`, all against PostgreSQL + PgBouncer):
   - `probe.ts`: a test-only `pool_probe` table (`tenant_id uuid`, `label`, FORCE RLS, policy on `current_tenant_id()`, index led by `tenant_id`), created by the owner with `create table if not exists`; seed helpers through `withTenant()`; a `serverPid(tx)` helper (`pg_backend_pid()`) so every reuse test first asserts it really got the same server connection (a test that never reused a connection proves nothing). Failure messages name tenant ids and row counts only.
   - `context-reuse.test.ts` (criterion 4): on `shifa_test_9994` (`POOLING_DATABASE`; 9996 belongs to the backup drill) (pool size 1), after a committed, a rolled-back and a failed-statement `withTenant()`, the next transaction on the same server pid sees empty `app.tenant_id`, `app.branch_id`, `app.user_id` and zero probe rows.
   - `session-leftovers.test.ts` (criterion 5): a raw `shifa_app` client through PgBouncer runs `SET app.tenant_id` and `set_config(..., false)` for tenant A, disconnects; on the same server pid `withTenant(B)` sees only B, `withPlatformAdmin` sees no tenant rows. A second variant runs with `server_reset_query_always = 1` (separate PgBouncer config or admin `SET` on a dedicated instance) and records the p50 overhead per transaction for the report. Write down which is enough and why (the wrapper overrides all three settings locally in every transaction; a raw session `SET` only survives where no wrapper runs).
   - `broken-clients.test.ts` (criterion 6): a client whose socket is destroyed after `set_config` and before COMMIT; the next client on that pool sees no context and `pg_stat_activity` shows no `idle in transaction` backend for `shifa_app`. Repeat with `idle_in_transaction_session_timeout` (set on the pooling database by the owner) firing.
   - `prepared-statements.test.ts` (criterion 7): a Drizzle `.prepare(name)` query on the probe, executed alternately for tenants A and B on the 2-connection pool, more than 5 executions per server connection (PostgreSQL's generic-plan switch; also with `plan_cache_mode = force_generic_plan` in a variant), returns only the current tenant's rows every time. This exercises PgBouncer's `max_prepared_statements` tracking.
   - `concurrency.test.ts` (criterion 8): 3+ synthetic tenants from `@shifa/testing` (`generateDataset` with the `load` preset, small params), 20 rounds of 50 concurrent `withTenant()` calls on the default 2-connection pool; each call checks `current_setting('app.tenant_id')` and every row's `tenant_id`; zero mismatches, mismatch count reported.
   - `session-features.test.ts` (criterion 9): `pg_advisory_xact_lock` blocks a second transaction and is released at COMMIT; `create temp table ... on commit drop` works inside `withTenant()`.
3. **Fixes (only if a test is red):** in `src/tenant.ts`, `src/admin.ts`, `src/transaction.ts` or the PgBouncer config from S2a; each with the red test kept.
4. **Rules:** `.claude/rules/db.md` and `packages/db/CLAUDE.md` forbid session advisory locks, `LISTEN`/`NOTIFY` listeners on the app pool, `SET` outside a transaction, session temp tables and `WITH HOLD` cursors; name the transaction-scoped forms. Stay inside the byte budgets.
5. **Findings for the report:** every criterion's result, server pids observed, the `server_reset_query_always` cost and the session-feature list go into this file's "As built" for S2c to compile.
6. **API / Web / Flutter / end-to-end:** not applicable.

## As built
**Result: no leak through the wrappers for the `app.*` context.** Every criterion 4–9 passed on the first green run. One defence-in-depth fix in `src/tenant.ts` after the security review: `withTenant()` also clears `app.admin_reason` (only `withPlatformAdmin()` did), so a session value can never make a tenant transaction look like admin work once the audit slice reads it. **But other session state does leak across tenants on the shared pooler:** a `WITH HOLD` cursor opened inside `withTenant(A)` was fetched inside `withTenant(B)` on the same backend and returned A's row (the rows are materialised at A's COMMIT; RLS is not checked again), and a session advisory lock taken inside `withTenant()` outlives COMMIT. The `server_reset_query_always = 1` pooler clears both. Owner decision OD-28: production requires it. Versions: PostgreSQL 18.6 (`postgres:18.6-trixie`), PgBouncer 1.26.1 (`edoburu/pgbouncer:v1.26.1-p0`), Drizzle 1.0.0-rc.5, `pg` 8.23.1. Each test writes what it observed to `.verify/s2-pooling/<test>.json` (git-ignored) for S2c.

- **Harness:** a second PgBouncer, same config plus `server_reset_query = DISCARD ALL` and `server_reset_query_always = 1` (`pgbouncerIni({ resetAlways })`), started next to the shared one; its address is `info.resetPooler`, the guard accepts it exactly like the shared one (clones and console only), `Via` gains `'reset-pooler'`. New in `@shifa/db/testing`: `PoolerName` (`'shared' | 'reset'`) on `pooledHarnessUrl()` and `showPooler()`; `rawPooledSession()` (one `pg` Client: `query`, `kill()` destroys the socket, `end()`); `holdPoolingDatabase()`, a session advisory lock on a direct superuser connection that serialises the files using `shifa_test_9994` across workers (the six pooling files and the routing test's pool-of-1 check) and runs `RESET ALL` on its server connection first.
- **Probe** (`test/pooling/probe.ts`): `pool_probe (tenant_id, label)`, FORCE RLS on `current_tenant_id()`, index `(tenant_id, label)`; created on the worker database or `shifa_test_9994` by the owner. `nextTransactionView()` is the "next client without the wrapper": one raw statement through PgBouncer returning pid, the three settings and the visible probe row count.
- **Criterion 4 (context reuse):** after a committed, a rolled-back and a failed-statement `withTenant()`, the next transaction ran on the same pid (327 in the recorded run) and saw `''` for all three settings and 0 rows.
- **Criterion 5 (session leftovers):** on the shared pooler a raw `SET app.tenant_id` + `set_config(…, false)` **survives the client** (the next raw client sees tenant A and A's row on the same pid). `withTenant(B)` without a branch on that pid sees `{B, '', userB}`, `app.admin_reason` `''` and only B's rows; `withPlatformAdmin` sees no tenant settings, its own reason and no rows; after them the raw value is back (the override is transaction-local). With `server_reset_query_always = 1` the next client on the same pid sees nothing. **What the wrapper covers:** it neutralises the `app.*` settings only. Everything else a session can hold (WITH HOLD cursors, session advisory locks, `LISTEN`, other settings such as `search_path` or `statement_timeout`) is guarded by rule text alone, and can be created inside `withTenant()` through `tx.execute`. Hence OD-28: `server_reset_query = DISCARD ALL` + `server_reset_query_always = 1` is required in production. Cost (report only, Windows + Docker Desktop, both poolers on the pool-of-1 database so each transaction waits for the previous reset; a request is `withTenant` + a named prepared select): 200 interleaved sequential transactions after 20 warm-up, p50 2.89 ms shared vs 3.03 ms reset-always (+0.14 ms, about 5%); 8 concurrent clients × 25 requests, 412 vs 380 transactions/s (about 8% lower). A first measurement on a 2-connection pool showed no difference because the reset overlapped the other idle server connection (reviewer B2).
- **Criterion 6 (broken clients):** a socket destroyed after `set_config` and before COMMIT: PgBouncer drops the server connection (killed pid 290, the next client got 300), no `idle in transaction` backend remains for `shifa_app`, the next client sees no context and no rows. With `idle_in_transaction_session_timeout = '1s'` (`ALTER DATABASE … SET` as the owner, then a fresh backend forced by one kill so the setting applies; asserted as `1s` inside the transaction): the server ends the backend, the client's next query fails, the next client gets a new pid with no context. The test resets the setting and retires that backend afterwards.
- **Criterion 7 (prepared statements):** `tx.select(…).where(eq(label, placeholder)).prepare(name)`, A and B concurrently for 12 rounds on 2 server connections: 12 executions per server pid, 0 wrong results. PostgreSQL switched to a generic plan even with the default plan cache (`generic_plans` of that statement reached 7), and with `plan_cache_mode = force_generic_plan` (12). Each variant carries a constant marker in its SQL text and counts only its own statement in `pg_prepared_statements` (reviewer N3). A third variant behind the `server_reset_query_always = 1` pooler: 12 executions per pid, 0 wrong; `DISCARD ALL` deallocates the server statements after each transaction and PgBouncer prepares them again (generic plans stay at 0 there, as expected). `current_tenant_id()` is STABLE, so it is evaluated per execution and never folded into the cached plan.
- **Criterion 8 (concurrency):** 3 tenants from `generateDataset({ preset: 'load', load: { tenants: 3, patientsPerTenant: 4 } })`, chart ids as probe labels; 20 rounds × 50 concurrent `withTenant()` on a 50-connection client pool over 2 server pids: 1000 calls, 0 mismatches, about 2 s.
- **Criterion 9 (session features):** `pg_advisory_xact_lock` held by one transaction makes `pg_try_advisory_xact_lock` false in a second one (other server pid), and `pg_locks` shows no holder after COMMIT (a try-lock on the holder's own backend would succeed even if it leaked: advisory locks are re-entrant). On the pool-of-1 database: a session `pg_advisory_lock` taken inside `withTenant()` is still held after COMMIT, and a `WITH HOLD` cursor declared in `withTenant(A)` returns A's row when fetched in `withTenant(B)` (same pid); behind the reset pooler the lock is released and the cursor is gone (`does not exist`) before the next client. **Deviation (owner OD-27, spec amended):** `create temp table … on commit drop` is *refused* to `shifa_app` (permission denied), because the baseline migration revokes `TEMPORARY` (PostgreSQL cannot limit TEMP to ON COMMIT DROP, and a temp table lives with the pooled backend, owned by `shifa_app`); the test asserts the refusal. Session forms forbidden in `.claude/rules/db.md` (and pointed to from `packages/db/CLAUDE.md`): `SET`/`set_config(…, false)`, session advisory locks, `LISTEN`, temp tables, `WITH HOLD` cursors, SQL `PREPARE`; Drizzle `.prepare()` only with `max_prepared_statements > 0`. `LISTEN` and SQL `PREPARE` are listed from PgBouncer's documented transaction-mode limits, not tested.
- **Locked test changes (owner-approved, 2026-11-12):** first `session-features.test.ts` lint only (no behaviour change); then the review fixes, all stricter: the cost measurement moved to the pool of 1 with a prepared statement and a concurrent figure (B2), `app.admin_reason` added to the session leftovers, the xact-lock release checked in `pg_locks` with the holder always released (N2, N4), the pool-of-1 lock taken in a `beforeAll` (N5), WITH HOLD and reset-pooler session tests, per-statement generic-plan counting and a reset-pooler variant (N3, N6), and a non-empty tenant guard in concurrency (N7).

## Notes for the next session
- Tests share the fixed pooling database `shifa_test_9994` (`POOLING_DATABASE`; 9996 belongs to the backup drill); serialise them (one file or a lock) so pool-of-1 reuse is deterministic.
- Killing a client: destroy the `pg` client's socket (`client.connection.stream.destroy()`), never kill PgBouncer.
- From the 0.3-S2a build and reviews (2026-11-12): the pooling database is `shifa_test_9994` (`POOLING_DATABASE`), created at harness start and never truncated by `setup.ts`; clean it up in the tests that use it.
- The shared PgBouncer is read-only from tests (`stats_users`; `SET` is refused). A `server_reset_query_always = 1` variant needs its own PgBouncer: today `pgbouncerIni()` takes no overrides and workers never get the `StartedNetwork`. Plan the harness change (for example a second pooler started in `globalSetup` with the variant config, its address in `HarnessInfo`).
- `idle_in_transaction_session_timeout` set with `ALTER DATABASE … SET` only reaches new backends, and PgBouncer keeps server connections up to `server_idle_timeout` (600 s). Set it before the first connection to the database under test, or use a database no earlier test touched.
- `rawPooledAppDb()` shares the server pool with `pooledTestDb()` on the worker database: a session-level `SET` through it survives across files. Session-leftover tests use `POOLING_DATABASE` or their own pooler.
- `max_client_conn = 1000` is set (shared by every worker).
