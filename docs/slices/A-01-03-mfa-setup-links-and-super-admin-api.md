# A-01-03 MFA, setup links and the super-admin API

Status: Built, in review · Tier: T0 · Branch: `feat/A-01-03-mfa-setup-links-super-admin-api` (built on the cloud session branch `claude/youthful-pasteur-c19sod`, [cloud sessions](../process/cloud-sessions.md) §4)

## Goal
The super admin creates a clinic and its owner and gets the owner's one-time setup link; the owner sets a password and enrols TOTP before anything else; TOTP and recovery codes protect owners and super admins; the super admin can reset an owner's password, MFA and sessions, all audited.

## Plan
1. **Contracts** — `CreateClinicRequest`, `ClinicSummary`, `ClinicDetail`, `UpdateClinicRequest`, `SetupLinkIssued` (URL shown once), `SetupLinkView` (clinic name, person's name and role, expiry; one `link_invalid` code for used, expired or replaced), `SetPasswordRequest`, `TotpEnrolStart` (otpauth URI + manual key), `TotpEnrolConfirm`, `RecoveryCodes`, `TotpChallenge`; codes `mfa_enrolment_required`, `mfa_locked` (`until`), `invalid_code`.
2. **Database** — no schema change expected (tables from A-01-01); if the gate in A-01-02 changed the two-factor table, a new migration here.
3. **API**
   - Access: a fourth annotation `@PlatformAdmin()` (exactly one of `@Public`, `@SignedIn` (A-01-02), `@RequirePermission`, `@PlatformAdmin`; `AccessCheck`, the guard, OpenAPI and the matrix learn it); the principal carries `mfa: 'none' | 'pending' | 'verified'`; the guard refuses every route but those marked `@BeforeMfa()` with 403 `mfa_enrolment_required` for owners and platform admins until enrolled, and until the challenge is passed in a session.
   - `modules/identity/setup-links`: issue (256-bit token, sha-256 stored, 72 h, re-issue replaces the earlier link), view and consume through `withSetupLink(tokenHashHex)` (`shifa_auth` reads that one link and may only set `used_at` on an unused link; issuing and re-issuing, which sets `replaced_at`, run in `withTenant()`; setting `membership.user_id` on consumption needs a privilege this slice adds, see A-01-01 notes); consuming an owner link sets the password (rules from A-01-02), signs in and leaves the session at `mfa: 'none'`; `wa.me` share URL carries only the link text.
   - `modules/identity/mfa`: enrol start and confirm (±1 step, never the same code twice: last accepted step stored), 10 single-use recovery codes shown once, challenge with code or recovery code, 5 wrong codes → 15 min lock; clock-skew hint code when a code matches outside ±1 but within ±10 steps (enrolment only). Session rotated after MFA.
   - `modules/platform/clinics` (`@PlatformAdmin`, `withPlatformAdmin({ actorId, event, requestId }, …)` on `createPlatformDb()`; the owner membership, role assignment and setup link need `shifa_platform` INSERT grants and the existing-phone check needs a way to look up `user`, both added by this slice's migration with `roleAccess` reasons, see A-01-01 notes): list (search by name), create (tenant + organization + main branch + route via `createClinic`, owner membership pending + `owner_role` assignment + owner setup link, one transaction; an existing phone gets an invitation link instead of a second account), detail (no clinic data), update status and end date, owner reset: new setup link (password reset), reset MFA, end all sessions; each ends the owner's sessions and writes one audit row.
   - Seed command `pnpm --filter @shifa/api seed:super-admin` (phone from an argument, prints a setup link once; refuses in `NODE_ENV=production` without an explicit flag); no route creates super admins.
4. **Web, Flutter** — none (screens in A-01-07).
5. **End-to-end** — API journey test: seed super admin → enrol → create clinic → owner link → password → TOTP → principal with owner role.

Tests written first: link single use, 72 h expiry with fake clock, re-issue invalidates, stored hashed, ≥ 128 bits, one message for used/expired/replaced with no clinic name (4); one-transaction creation with owner (2, 3); status and end date edits audited, end date with no effect (3); owner forced to TOTP before any other route (5, 11); ±1 step, replay refused, 5 wrong → lock, recovery code single use (12); each owner reset ends sessions and is audited; super admin sees no tenant rows (13); platform rows invisible to `shifa_app` (14); leak test over link and MFA flows (no token, secret, code or phone).

## As built (differences from the plan)
- **Own TOTP, no two-factor plugin** ([ADR-0045](../adr/0045-own-totp-and-platform-admins.md), proposed, amends ADR-0044): RFC 6238 in `modules/identity/totp.ts`, key sealed with AES-256-GCM in Better Auth's `two_factor` table, `last_used_step` stored, recovery codes as HMACs with `AUTH_HMAC_KEY`. Sign-in always gives a session; `session.mfa_verified_at` gives the principal's `mfa`. The session is rotated (new token, same clinic and absolute limit) after enrolment and after the challenge.
- **Access:** `@PlatformAdmin()` is the fourth annotation; `@BeforeMfa()` (with `@SignedIn()` only) marks `GET /auth/session`, `POST /auth/sign-out` and the three MFA routes. Owners (owner role in the active clinic) and super admins without TOTP get 403 `mfa_enrolment_required`; any enrolled person whose session has not passed gets 403 `mfa_challenge_required` (a second code, beyond the plan's one, so the client knows which screen to show). OpenAPI: `x-platform-admin`, `x-before-mfa`; every authenticated route but `@BeforeMfa` ones now lists 403. `SessionView` gains `platformAdmin`, `mfa`, `mfaRequired`.
- **Super admins:** a new global `platform_admin` table (read by `shifa_auth`, written by `shifa_platform` only under `platform.admin_created`). Their setup link is a Better Auth `verification` row (`setup_link` needs a tenant membership). Seed: `pnpm --filter @shifa/api seed:super-admin --phone … --name … [--allow-production]`; never takes over an existing account.
- **Setup links:** token in the URL fragment (`<CLINIC_WEB_URL>/setup#<token>`, new optional config key, default `http://localhost:5173`); view and consume are `POST /auth/setup-link/view|consume` with the token in the body. 404 `link_invalid` for used, expired, replaced and unknown links; password refusals `password_too_short|password_common|password_contains_phone` (400). A new link for a set-up owner clears the password at once (and ends sessions), so an attacker holding it is out before the owner uses the link. An invitation link (existing phone) is viewable; consuming it answers 409 until A-01-04.
- **Platform API:** `GET/POST /platform/clinics`, `GET/PATCH /platform/clinics/:id`, `POST /platform/clinics/:id/owner/{setup-link,reset-mfa,end-sessions}`. Every call is one `withPlatformAdmin()` transaction with its audit row, lists and views included (`clinic.listed`, `clinic.viewed`, new events); `data` carries allowlisted words only (`linkPurpose`, `status`, `endDate: set|cleared`). Owner actions run their auth-path work (sessions, MFA, password) inside the platform callback: a failure there rolls back the link and the audit row; the two pools are not one transaction.
- **Same owner phone, first owner still pending** (OD-85, owner's decision in this session): creation answers 409 `owner_setup_pending` until the first owner has set up; then the second clinic gets an invitation.
- **After the reviews:** owner support writes its own `auth.*` row in the auth transaction (`auth.session_ended` `admin`, `auth.mfa_reset`, `auth.password_reset`), and `owner.*` rows carry `clinicId`; link use re-checks expiry with the API clock inside the update (admin links too); a seed run that stopped before `platform_admin` can be re-run; `CLINIC_WEB_URL` is required and https when `DEPLOYMENT_ENVIRONMENT` is staging or production, and the seed refuses there without `--allow-production`; recovery codes are HMACs with `AUTH_HMAC_KEY`; every response carries `Cache-Control: no-store`. Database (same unmerged migration): `shifa_platform` may insert a membership or owner role only into a clinic with no owner, and only owner/invitation links for the owner valid about 72 h; `shifa_app` can neither write nor turn a link into an `owner_setup` link; `shifa_auth` updates a membership only to bind it. A link never resets a super admin's password, and a reset ends the person's other sessions.
- **Accepted (security review L3, by the spec):** "reset MFA" keeps the owner's password (criterion 13: enrol again at the next sign-in); a super admin can, by design and audited, take over an owner (new link, MFA reset). L6: the `wa.me` share carries the token in its query string (the spec asks for the button). L9: the MFA lock does not escalate (5 tries per 15 min, as specified).
- **Dates:** `subscriptionEnd` is a `YYYY-MM-DD` string pattern, not `format: date`: the generated Dart client turned the format into a `DateTime` and wrote it back as a timestamp.
- **Database** (`/db-migration`): `20261123205524_a01_mfa_and_platform_admin` (generated: `platform_admin`, `session.mfa_verified_at`, `two_factor.last_used_step`) and `20261123205528_a01_owner_links_and_mfa_grants` (custom: grants and policies listed in the classification, each with its reason). Both **expand**. Rollback before real data: drop `platform_admin`, the two columns and the new policies/grants, and recreate `membership_auth_only_own` as `FOR SELECT USING (user_id = current_user_id())`; after real data, roll forward only.
- **Harness:** `testPlatformDb()` reopens after an app closes it (as `testAuthDb()`); `buildTestApp({ platformDb, clinicWebUrl })`; the route matrix takes async samples (fresh links, TOTP rows with a known key, an MFA state per call). The Dart client's size budget rose to 100 files / 3,800 lines (`scripts/drift.config.mjs`).
