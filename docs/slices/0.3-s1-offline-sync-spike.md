# 0.3-S1 Offline sync spike: PowerSync vs custom outbox

Status: Planned · Tier: T0 (tenancy, money, patient data on devices, auth, CI infrastructure) · Branch: `chore/0.3-s1-offline-sync-spike`
Spec: [0.3-S1 offline sync](../specs/spikes/0.3-s1-offline-sync.md) criteria 1–13 · Requirements: SCH-13, SCH-14, SCH-16, SCH-31, SCH-32, SCH-33, SCH-34, PAT-08, BIL-24, BIL-25, PLT-01, PLT-50

One slice for the whole spike (owner, 2026-11-15), under the ~4,000-line budget of [ADR-0032](../adr/0032-slice-size-budget-4000-lines.md). It is built in six checkpoints (A–F below); each ends green and committed, so a session can stop at any checkpoint and the next one resumes from "Stopped at".

## Goal
The owner reads one report with per-engine evidence from real network cuts and approves which engine reception (web) and the patient app (Flutter) use. Both engines upload through one server command handler that enforces idempotency, the three conflict rules and the offline cash limits; a throwaway reception prototype and a thin Flutter probe run on both; the scenario suite stays for Phase A.

## Layout
- `spikes/s1-offline/` is new and throwaway, except `scenarios/` (Phase A reuses it). `pnpm-workspace.yaml` gains `spikes/*/*`, so lint, the 400-line limit, typecheck and the server's DB tests run in `verify`; the Playwright suite and the Flutter probe do not (manual CI workflow).
- Packages: `server` (`@shifa-spike/s1-server`), `web` (`@shifa-spike/s1-web`), `scenarios` (`@shifa-spike/s1-scenarios`), `flutter_probe` (standalone Flutter package outside the pub workspace, own lockfile, run through `node scripts/dart.mjs flutter ...`).
- Spike tables live in their own PostgreSQL schema `s1`, created by `server/sql/schema.sql`, never in `packages/db/migrations` (migration drift and the `public` RLS presence check stay untouched). Each table still has `tenant_id`, ENABLE + FORCE RLS and policies on `current_tenant_id()`, and is reached only through `withTenant()` as `shifa_app`.

## Plan

### A. Server: tables, command handler, conflict rules (criteria 1–3, 10 server half)
1. **Contracts** (`server/src/commands.ts`, zod, local to the spike; not in `packages/contracts`): `Command = { id: uuid (idempotency key), deviceId, type, payload, clientTime }`, types `ticket.issue`, `ticket.status`, `appointment.book`, `appointment.cancel`, `cash.open`, `cash.move`. `CommandResult = { id, status: 'applied' | 'conflict' | 'refused', remap?: { provisional, real }, conflict?: { code, messageAr }, serverTime }`. A batch returns one result per command, in order.
2. **Database** (`server/sql/schema.sql`, applied as owner; `btree_gist`):
   - `appointment` (tenant, branch, practitioner, `tstzrange` slot, status, `updated_at`) with `EXCLUDE USING gist (tenant_id WITH =, practitioner_id WITH =, slot WITH &&) WHERE (status <> 'cancelled')`.
   - `queue_ticket` (tenant, branch, practitioner, `shift_date`, `provisional_number`, `device_id`, `real_number`, status, synthetic walk-in label, `updated_at`); unique `(tenant_id, branch_id, practitioner_id, shift_date, real_number)`. Real numbers are `max + 1` under `pg_advisory_xact_lock` on the shift key, in arrival order (SCH-16): no counter table.
   - `cash_session` (tenant, branch, opened online, `rates jsonb` captured at open, `closed_at`); `cash_movement` (session, `type` in `sale | refund | expense | deposit | float_adjust`, currency `SYP | TRY | USD`, `amount_minor bigint > 0`, `rate_used`, `offline boolean`, `refund_of`). `UPDATE`/`DELETE` revoked from `shifa_app` (append-only, BIL-25).
   - `offline_command` (tenant, command id, device id, type, stored `CommandResult jsonb`, `received_at`): the idempotency store and, for PowerSync, the result rows a device downloads.
3. **API** (`server/src/`, plain Fastify; `@shifa/db` `createDb` + `withTenant`):
   - Spike auth: `POST /auth/login` (synthetic receptionist from `@shifa/testing`) and `POST /auth/patient-login` (synthetic patient) issue ES256 JWTs (`sub`, `tenant_id`, `branch_id`, `exp`, PowerSync audience); TTL from config so the suite can force expiry; keys in memory; `GET /.well-known/jwks.json`. One receptionist role.
   - `POST /commands` (batch ≤ 200), per command in one transaction under `withTenant(token.tenant_id)`: stored result → return it (replay); else validate, apply, store. Server time on receipt; client time stored only as information.
   - Rules: `ticket.issue` assigns the real number, returns `remap` when it differs; `appointment.book` maps `23P01` to `conflict` with an Arabic message (SCH-14), never dropped; `cash.move` into an open session; offline only `sale` and `refund` at a rate of the session (last synced), others `refused` with an Arabic message (OD-29); a refund above its sale minus earlier refunds is refused; `cash.open` online only.
   - Forged tenant: ids outside the token's tenant are invisible under RLS → `refused`; log `{ tenantId, commandId, code }` only.
   - Redacting logger: no bodies, headers, names, phones or tokens. `GET /health`; the server also serves the built prototype.
4. **Tests first** (`server/test/`, Testcontainers via `@shifa/db/testing`: `ownerDb()` applies `schema.sql` to the worker database, the handler runs on `testDb()`):
   - `idempotency.test.ts`: same command twice, same batch twice, two concurrent posts of one id → one row, identical result (1, SCH-13).
   - `queue-numbers.test.ts`: two devices' interleaved batches with clashing provisional numbers → real numbers 1..n, no duplicate, arrival order, every differing one a `remap` (2a).
   - `appointments.test.ts`: overlap → `conflict` with Arabic message, no row; cancelled slot rebookable (2b).
   - `cash.test.ts`: offline sale/refund accepted; offline expense, deposit, float adjustment, close and open refused in Arabic; refund above sale refused; `UPDATE`/`DELETE` as `shifa_app` fail; per-currency totals = sum (2c, 3).
   - `tenancy.test.ts`: tenant A token with tenant B ids → `refused`, nothing written, log has ids and a code only; every `s1` table has FORCE RLS and policies (10).
   - `auth.test.ts`: expired or wrong-key token → 401, nothing applied; JWKS has the public key only.

### B. Custom outbox engine and reception web prototype (criteria 5, 8, 9 client side, 10 pull)
1. `GET /sync/pull?cursor=`: under `withTenant()`, branch and today only (patient tokens: own rows only); snapshot for an empty cursor, else rows changed since (`updated_at` + id tiebreak).
2. `SyncEngine` interface (`web/src/engine.ts`): `start(token)`, `enqueue(command)`, `today()`, `pendingCount()`, `status()` (`online | offline | needs-login`, `offlineSince`), `events` (`remap`, `conflict`, `refused`), `wipe()`.
3. Outbox engine (`web/src/outbox/`): IndexedDB via `idb` (chosen over SQLite WASM: smaller bundle, no OPFS or cross-origin-isolation headers; PowerSync's SDK gives the SQLite data point). Stores `commands`, `results`, `rows`, `meta` (cursor, last synced rates, offline since). Flush in order; network error → back off, retry the same ids; 401 → keep the queue, `needs-login` (9); apply remaps and conflicts, raise events, then pull. Logout wipes.
4. Screens (`web/src/ui/`, Vite + TypeScript, Arabic RTL, strings inline: throwaway, not in `packages/i18n`): login; queue with walk-in form and status buttons; printable ticket with provisional number and device id, real number beside it after sync (SCH-32); appointment booking; cash panel (sale, refund of a listed sale; other types disabled offline with the OD-29 message); receipt with rate used and an "offline" mark; banner with time offline and pending count (SCH-33); list of remaps and conflicts. A small service worker caches the app shell so a reload or restart opens offline.
5. **Tests first:** `web/test/outbox.test.ts` (Vitest + `fake-indexeddb`, fetch stubbed): queue survives a new engine instance; mid-flight failure retried with the same ids; 401 keeps the queue; remap keeps the provisional number; pending count reaches zero (8, 9). `web/test/cash-rules.test.ts`: UI rules match the server. `server/test/pull.test.ts`: snapshot then changes; tenant A never gets tenant B rows; branch filter holds (10, outbox half).

### C. Scenario suite with real cuts, on the outbox (criteria 6–9; checklist for 12)
1. `scenarios/global-setup.ts` (Testcontainers, every image `name:tag@sha256:…`, at least 24 hours old): its own PostgreSQL 18 with `wal_level=logical`, roles from `packages/db/sql/roles.sql`, then `s1` schema; the server in-process, exposed with `TestContainers.exposeHostPorts`; Toxiproxy (`@testcontainers/toxiproxy`) with one proxy per device. `ENGINE=outbox | powersync` picks the prototype build.
2. Specs (two browser contexts = two devices, `page.clock` fake clock, seeded `@shifa/testing` data):
   - `two-hours-offline.spec.ts`: log in, sync, open a cash session online, cut both proxies; over 2 simulated hours 40 walk-ins, 60 status changes, 50 sales and 5 refunds in SYP, TRY and USD, 2 overlapping bookings; reconnect. Server read API: commands received = issued, real numbers unique and gap-free per shift, every remap and the double booking shown on the device that made it, per-currency cash totals = sum of commands; banner time offline and pending count reaching zero (6, 8).
   - `degraded-links.spec.ts`: same script with 30% loss, 2 s latency, and a reset in the middle of an upload; no duplicate (7).
   - `session-expiry.spec.ts`: TTL below the outage; nothing syncs until re-login, then everything once (9).
   - `restart.spec.ts`: close the context mid-outage, reopen offline; records which commands survive (report's eviction note).
3. **Tests first:** the specs fail against two stub engines (one drops a command, one replays without an idempotency key), proving the counters catch loss and duplicates. Harness test: images are digest-pinned.
4. CI: `.github/workflows/s1-offline.yml`, `workflow_dispatch` only, inputs `engine` (`outbox | powersync | both`) and `flutter` (bool); pinned actions; artefacts: Playwright report and a counts-only JSON summary. `scenarios/package.json` has a `scenario` script and no `test` script (not in `verify`).
5. `docs/spikes/s1-manual-checklist.md`: owner script for two real devices on a clinic-like LAN, Wi-Fi off 2 real hours, the same counts by hand, browser restarted and laptop asleep once; a results table per engine (12).

### D. PowerSync engine (criteria 4, 6–10 on engine a)
1. Spike container only (`scenarios/sql/powersync.sql`): replication role `s1_powersync` (`REPLICATION`, `SELECT` on `s1`), a publication for the `s1` tables, bucket storage database `s1_powersync_storage` (PostgreSQL, no MongoDB). Never in `roles.sql` or migrations.
2. `scenarios/powersync/`: service image, latest stable, tag + digest; `config.yaml` with PostgreSQL replication and storage, JWKS from the server, sync streams (or sync rules if streams are not stable in that version; record which) with `tenant_id = auth.parameter('tenant_id') AND branch_id = auth.parameter('branch_id')`, today only; `offline_command` also by device; patient streams by `sub`. The harness asserts the running version.
3. Server `POST /powersync/upload`: the connector's CRUD batch → the same command handler (no second write path).
4. `web/src/powersync/`: `SyncEngine` on the PowerSync web SDK (latest stable, pinned): schema, connector (`fetchCredentials`, `uploadData` retrying on network error, stopping on 401), status from the connection state, pending from the upload queue, `wipe()` = `disconnectAndClear()`. Build flag picks the engine.
5. **Tests first:** `scenarios/tests/tenant-scoping.spec.ts` (both engines): tenant A and B devices sync; A's local store holds no B row; the PowerSync sync endpoint with A's token returns nothing of B; a forged upload is refused and logged by id only (10). Then the C specs with `ENGINE=powersync` (4, 6–9). Record setup and operating load as you go.

### E. Flutter probe (criterion 11)
1. `flutter_probe/` (pinned toolchain, `very_good_analysis`): outbox engine on drift with SQLCipher (`sqlite3` SQLCipher build), tables for appointments, ticket, pending commands; PowerSync engine on the Flutter SDK's SQLCipher variant, drift integration if usable on the pinned Flutter (record it); one screen: my appointments, my ticket, cancel, pending badge.
2. Integration against the C global setup; "airplane mode" = the device's proxy disabled. The `s1-offline` workflow gains the `flutter` job.
3. **Tests first** (`flutter test` on the desktop host, each engine): `cache_offline_test.dart` (sync, cut, restart → readable); `encryption_test.dart` (no key → open fails, no plaintext of a known synthetic value, `PRAGMA cipher_version` set); `cancel_sync_test.dart` (offline cancel + retry → one cancellation on the server); `logout_test.dart` (database file deleted).
