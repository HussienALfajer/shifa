# 0.3-S5a WhatsApp spike: pinned WAHA, fake WAHA, sending controls

Status: Planned (owner approved the plan, 2026-11-17) · Tier: T0 (infrastructure, patient phone numbers, tenant-scoped opt-in state; throwaway code, no real-schema migration) · Branch: `chore/0.3-s5a-whatsapp-stack-and-sending`
Spec: [0.3-S5 WhatsApp](../specs/spikes/0.3-s5-whatsapp.md) criteria 1–8 · Requirements: MSG-01, MSG-02, MSG-07, MSG-10, MSG-11, MSG-13, MSG-14, MSG-15, MSG-16, MSG-17, MSG-18, MSG-19 (variants), MSG-32 · Decisions: ADR-0003 (pg-boss), ADR-0017, ADR-0023, ADR-0026, OD-12 (stays open), OD-23, OD-31, OD-45, OD-46

The spike is split in three by the ~4,000-line budget of [ADR-0032](../adr/0032-slice-size-budget-4000-lines.md) and by the owner's manual day: this slice builds the pinned WAHA stack, the fake WAHA and every sending control, all proven without a phone; [0.3-S5b](0.3-s5b-whatsapp-verification-and-tooling.md) adds reverse verification, tenant and role separation and the manual-run tooling; [0.3-S5c](0.3-s5c-whatsapp-manual-day-and-result.md) holds the owner's day on real WhatsApp, fixture replay, the report and ADR-0036. Built in five checkpoints (A–E); each ends green and committed, and "Stopped at" names the last one.

## Goal
A developer starts, with one command, a pinned WAHA (GOWS, PostgreSQL session storage, API key, HMAC webhooks) next to a throwaway messaging service, or the same service against a fake WAHA that can inject every failure the spec names. Every message goes through `sendWhatsApp(clinicId, patientId, templateKey, vars)`, which refuses non-opted-in patients and non-allowlisted numbers, paces sends per session, honours quiet hours, the rolling hourly cap and opt-out, trips the circuit breaker into inbox records and manual-send tasks, and tracks acks and session health.

## Choices made by this plan
- **No real WhatsApp in this slice or in CI (spec, OD-45).** The real WAHA container is started and checked (version, auth, storage, webhook signing config, OpenAPI) but no session is started, because starting one contacts WhatsApp. If the pinned docs confirm that creating a session with `start: false` makes no outbound connection, the boundary test creates one to prove storage wiring; otherwise storage is proven in 0.3-S5c's restart step. Sessions on real WhatsApp happen only in 0.3-S5c.
- **WAHA storage model:** WAHA creates its own databases (`waha_<namespace>` plus one per session) and needs a role allowed to create them. Each WAHA container gets its own namespace and its own role with `CREATEDB`, on a PostgreSQL 18 container separate from the one holding `s5_messaging`, so WAHA's rights never reach spike state. Exact env names are taken from the pinned version's docs and recorded here.
- **WAHA hardening (asserted in tests):** `WAHA_PRINT_QR=False` (the default prints the QR to the console), dashboard off, log level `warn`, JSON logs, API key per run. Swagger stays off in the stack; the pinned image's OpenAPI document is fetched once at checkpoint A from a throwaway container and committed under `fake-waha/openapi/` with the image digest it came from.
- **Fake WAHA fidelity:** the fake serves only methods and paths present in the committed OpenAPI document (test). Webhook payloads follow WAHA's documented events for the pinned version: `message`, `message.ack`, `message.edited`, `message.revoked`, `message.reaction`, `session.status`. 0.3-S5c checks them again against real captures.
- **Ban signals are not invented:** the fake injects the forms recorded in RN-10 (send errors 463 and 475, as described on WAHA's "how to avoid blocking" page) in two shapes, an HTTP error on send and a later `message.ack` with status `ERROR`; the list of warning events is "as documented by the pinned version", confirmed at checkpoint B and refined by the manual day.
- **Per-session FIFO pacing with pg-boss:** pg-boss (ADR-0003; latest release at least 24 hours old) with one send queue using the per-key strict FIFO policy keyed by session (one active job per session, later jobs wait) if the pinned release has it; otherwise a per-session tick job that takes the oldest `queued` row with `FOR UPDATE SKIP LOCKED`. The next allowed time is a pure function `nextSendAt(state, now, random, config)` (gap, rolling 60-minute cap, quiet hours in the clinic's IANA time zone, deferral spread). Valkey is not used; the report (0.3-S5c) says whether it would be needed.
- **At most once:** `retryLimit: 0` and an expiry longer than the longest send; the handler commits `sending` in its own transaction before the WAHA call and records the outcome in another; a job that finds an attempt already `sending` marks it `unknown` and never calls WAHA. `unknown` becomes a manual task marked "maybe sent" (criterion 6).
- **Breaker and fallback (OD-46):** 463, 475 or a ban warning pause the session for 24 h; after that it stays paused until the clinic admin confirms resumption. Gateway down, timeouts, `FAILED`/`STOPPED` move pending messages to the fallback without the 24 h pause; sending resumes when the session is `WORKING` again. The hourly cap is a rolling 60 minutes.
- **Webhook integrity:** each WAHA container has its own HMAC key and webhook path; the service routes by (container, session) and refuses a session that does not belong to the container that posted it. WAHA's HMAC covers the body only, so the service drops duplicate events by (event, message id) and applies opt-in and opt-out only when the message timestamp is newer than the stored one.
- **Time:** the service takes a clock and a seeded random source; the simulated-day test drives the pure scheduler with a fake clock; a compressed-config integration test (gap 200–600 ms, cap 6 per rolling 6 s, quiet window of 2 s) proves the rules through real pg-boss. The 5-minute health job's handler is called directly in tests (cron cannot run every few seconds).
- **Spike state** in database `s5_messaging` (schema `s5`), created by the harness, never in `packages/db/migrations`; tables carry `clinic_id` but no RLS, as in 0.3-S4.
- **Allowlist (MSG-32):** E.164 list from an env var; in tests synthetic numbers only (`isSyntheticPhone` from `@shifa/testing`). Every outbound, the platform's replies included (0.3-S5b), passes it. Dropped sends log `allowlist_drop` with clinic id and template key, no number.
- **Opt-out keywords:** compared after digit folding, tashkeel removal and whitespace collapsing, lower-cased: `إيقاف`, `ايقاف`, `stop`. The rules are copied into `messaging/src/keywords.ts` from the ADR-0034 normaliser (no import from another throwaway spike).

## Layout
- `spikes/s5-whatsapp/stack/` (`@shifa-spike/s5-stack`): Testcontainers harness (`src/images.ts`, `src/stack.ts`, `src/waha.ts`), networks `messaging` (internal) and `edge`; WAHA has no published port.
- `spikes/s5-whatsapp/fake-waha/` (`@shifa-spike/s5-fake-waha`, kept for Phase A): Fastify server, committed OpenAPI document, fault injection API (`POST /__fake/...`, only in the fake), webhook emitter with HMAC.
- `spikes/s5-whatsapp/messaging/` (`@shifa-spike/s5-messaging`): Fastify service: `src/send.ts` (`sendWhatsApp`), `src/allowlist.ts`, `src/optin.ts`, `src/keywords.ts`, `src/scheduler.ts` (pure), `src/queue.ts` (pg-boss), `src/breaker.ts`, `src/fallback.ts`, `src/health.ts`, `src/acks.ts`, `src/webhook.ts` (HMAC, router by container and session, dedupe), `src/templates.ts` (3–5 Arabic variants per MSG-03 type, fixed placeholders), `src/db.ts` (`pg`, schema SQL).
- Suites are `test:spike` only (OD-31); typecheck and lint run in `verify`.
- `.github/workflows/s5-whatsapp.yml`: `workflow_dispatch` only, `permissions: {}`, actions pinned by SHA like `s4-imaging.yml`; job `fake` runs every `test:spike` suite; no secrets.

## Plan

### A. Pinned WAHA stack (criterion 1)
1. `src/images.ts`: `devlikeapro/waha` (latest 2026.x free image, at least 24 hours old) and `postgres:18.x` (two containers), each `name:version@sha256:<digest>`. Record the licence files found in the image and the repository, GOWS included (spec question; an unclear GOWS licence is noted for the report, not a stop).
2. `src/waha.ts`: GOWS default engine, PostgreSQL session storage with its own namespace and role, API key, hardening env, webhook URL and HMAC key per container, the six events above.
3. Two containers, `waha-platform` and `waha-clinics` (MSG-09, MSG-10). Fetch and commit the OpenAPI document.

### B. Fake WAHA (criterion 2, first half)
1. Endpoints from the OpenAPI document: session create/start/stop/status, QR, send text, send seen, start/stop typing, LID → phone lookup; API-key check; per-session state machine `STARTING → SCAN_QR → WORKING → FAILED|STOPPED`.
2. Faults: 463/475 as HTTP error and as later ack `ERROR`; documented warning events; forced state; delayed or dropped response (timeout); duplicate and reordered webhooks; replayed old events; `@lid` sender with and without a resolvable phone; edits, revokes, reactions.
3. Webhooks signed as WAHA signs them (SHA-512 HMAC header, per the pinned docs).

### C. Send path, allowlist, opt-in and opt-out (criteria 3–4)
1. `sendWhatsApp` validates template key and placeholders, resolves the number, checks allowlist and opt-in, writes `delivery_attempt(queued)` and enqueues; refusals write a reason code, never the number.
2. Inbound router: container key + HMAC, session ownership, dedupe, `@lid` resolution through the receiving container, timestamp-ordered opt-in upsert, keyword opt-out with one confirmation; groups, broadcasts and status replies ignored; edits, revokes, media and reactions count as inbound.

### D. Pacing, breaker, fallbacks (criteria 5–6)
1. Scheduler and queue as above; seen, then typing (duration grows with length, capped), then send; variant chosen by seeded random.
2. Breaker and fallback per OD-46: inbox record + manual-send task (prefilled `wa.me/<patient>?text=` link), one `admin_alert`; no re-pair call exists in the code; admin "resume" endpoint after the 24 h.

### E. Health, acks, workflow (criteria 7–8)
1. Health handler maps states to `linked | needs_qr | paused | down`, alerts once per transition; "phone not seen" from the last successful send or inbound (the WAHA signal, if any, is added in 0.3-S5c).
2. Acks only move forward (`sent → delivered → read`); duplicates and reordering ignored; `ERROR` after `SERVER`/`DEVICE` trips the breaker when it carries a ban code.
3. Workflow file; "Stopped at" and Evidence in this file.

## Tests written first
- `stack/test/images.test.ts` (1): digests pinned; WAHA reports the pinned version, GOWS default, QR printing, dashboard and Swagger off, JSON logs.
- `stack/test/waha-boundary.test.ts` (1): no published port; unreachable from `edge`; 401 without API key; WAHA's role cannot connect to `s5_messaging`; WAHA config database exists in its own namespace.
- `fake-waha/test/openapi-parity.test.ts` (2): every method + path the fake serves is in the committed document; the document's recorded digest equals the pinned image's.
- `messaging/test/webhook.test.ts` (1): unsigned, wrong-key and other-container-key webhooks refused with no side effect; a session posted by the wrong container refused; an exact replay is a no-op; an old inbound arriving after "إيقاف" does not opt back in.
- `messaging/test/allowlist.test.ts` (3, MSG-32): non-allowlisted number dropped; log line has no digit run of 8 or more.
- `messaging/test/optin.test.ts` (4, MSG-13, MSG-14): send without inbound refused before queueing; each keyword form opts out; the next queued message is dropped; exactly one confirmation; a later inbound opts back in; edits, revokes and reactions count as inbound; `@lid` resolved first; group/broadcast ignored.
- `messaging/test/scheduler-day.test.ts` (5): pure scheduler, fake clock, 200 messages over a day: no gap under 20 s; no rolling 60 minutes over the cap; nothing 21:00–08:00 in `Asia/Damascus`; morning backlog spread; variants used.
- `messaging/test/queue.test.ts` (5, MSG-10): compressed config through real pg-boss with two worker processes: no overlap within a session, FIFO order kept, seen → typing → send order, typing longer for longer text; two sessions on two fake instances progress in parallel.
- `messaging/test/breaker.test.ts` (6, MSG-01, MSG-16, OD-46): 463, 475 (both shapes) and a warning pause 24 h, then stay paused until admin resume; pending → inbox + manual task, one alert, no re-pair call; gateway down and `FAILED` → fallback without the pause, sending resumes on `WORKING`; crash after `sending` committed and job expiry each end as `unknown`, never a second WAHA call, task says "maybe sent".
- `messaging/test/health.test.ts` (7, MSG-17): state mapping, one alert per transition, 10-day "not seen" warning.
- `messaging/test/acks.test.ts` (8, MSG-18): duplicate and out-of-order acks never move state backwards; `ERROR` after `DEVICE` handled.
- `messaging/test/no-secrets-in-logs.test.ts`: service, fake and real WAHA container logs contain no synthetic number, no body marker, no API or HMAC key.
