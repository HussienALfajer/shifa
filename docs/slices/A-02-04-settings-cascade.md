# A-02-04 Settings cascade with locks

Status: Built, in review · Tier: T0 · Branch: `claude/admiring-johnson-rxetti` (cloud session; planned as `feat/A-02-04-settings-cascade`)
Spec: [A-02](../specs/platform/A-02-settings-entitlements-console.md) criteria 8–10, 18 (setting events) · Requirements: PLT-22, PLT-23, PLT-24 · Decisions: ADR-0007; A-01a criterion 9, OD-77, OD-87 · From A-02-01: criteria 9 (amended)

Contract: delivers the rows of the [A-02 screen contract](../specs/platform/A-02-screen-contract.md) that name this slice, each proven by a contract test (ADR-0047); a change forced during the build updates the row and its drawing here and is reported to the owner.

## Goal
Settings are declared in code and resolved nearest-scope-wins with locks and schema checks; every admin read says where a value comes from; the clinic's idle sign-out is the first key, `session.idle_minutes`, and keeps working.

## Plan
1. **Contracts** — `SettingView` (key, effective value, source scope and label, locked, lockedBy scope, overridable here), `ClinicSettingsView` (list), `SetSettingRequest`, `LockSettingRequest`; codes `setting_locked`, `setting_scope_refused`, `setting_value_invalid`. `GET|PATCH /clinic/settings` keep their shape for `idleMinutes` and add `source` and `locked` (additive).
2. **Database** (`/db-migration`, `/rls-policy`; **expand + migrate**)
   - `setting_value` (tenant_id, scope `organization | branch | practitioner | user`, scope id, key, value jsonb, locked, set_by, set_at): FORCE RLS; `shifa_app` writes its own tenant's non-locked rows of the scopes a route allows; lock columns written by `shifa_platform` only (column grant, approved at `/db-migration`).
   - `platform_setting_value` (scope `platform | plan`, plan id, key, value, locked): platform table, `shifa_app` SELECT.
   - Migrate: backfill `session.idle_minutes` from `tenant.idle_minutes` for every clinic. The auth path (`shifa_auth`) reads the effective idle value (SELECT of that key only, restrictive policy). The **contract** step (drop `tenant.idle_minutes`) is in A-02-06's migration, after this one is deployed.
3. **API** (`modules/settings`)
   - `SETTING_DEFINITIONS` in code: key, JSON Schema (from zod), default, `overridable_by`, lockable, sensitivity; start-up check (unknown key, default not valid, scope unknown).
   - Resolver: platform → plan → specialty pack (empty source until A-11) → organization → branch → practitioner → user; a stored value that no longer validates is skipped; a lock stops every scope below; returns value and source.
   - Writes validated against the schema, refused outside `overridable_by` or under a lock.
   - `/clinic/settings` reads and writes through the cascade (owner, `clinic.settings.manage`); the session's idle limit comes from the resolver (sessions service and `tenantView`).
   - Platform: `GET /platform/clinics/:id/settings`, `PUT /platform/clinics/:id/settings/:key` (value), `POST …/:key/lock` and `/unlock`; audit `setting.set`, `setting.locked`, `setting.unlocked` (key, scope, before, after); the tenant event `clinic.settings_changed` keeps writing for the owner's change.
4. **Web, Flutter** — none (UI code slices A-02-08, A-02-10).
5. **End-to-end** — the A-01 idle journey stays green unchanged.

Tests written first: precedence across every scope with a test catalogue (8); lock at organization stops branch and user (9); `overridable_by` refusal (8); schema refusal on write and invalid stored value skipped (8); source label for each scope, including the default (9); idle regression: existing 15/30/60 values after the backfill, owner change applied on the next request, super-admin lock refuses the owner (10); audit rows (18); isolation case for `setting_value`; `shifa_app` cannot write lock columns.
Estimated hand-written lines: ~3,300 (contracts ~250, database ~500, definitions and resolver ~700, routes and auth-path read ~550, tests ~1,300). Re-estimated at A-02-01 checkpoint 3 (owner, 2026-11-27).

## As built (changes from the plan, reported to the owner)
- **Branch:** `claude/admiring-johnson-rxetti` (cloud session; planned as `feat/A-02-04-settings-cascade`).
- **Tables:** `setting_value` (tenant, FORCE RLS): `scope` `organization | branch | practitioner | user`, `scope_id` null for the organization (a clinic has one), unique `(tenant_id, scope, scope_id, key)` NULLS NOT DISTINCT, `set_by` null for the backfill. `platform_setting_value` (global): `scope` `platform | plan`, `plan_type` (the clinic type, as `plan_feature`) instead of a plan id.
- **Who writes what:** shifa_app inserts and deletes its own unlocked values and updates `value`, `set_by`, `set_at` only (column grant), never a locked row (restrictive policies). shifa_platform reads a clinic's values inside it in `setting.viewed|locked|unlocked`, writes only locked organization values in `setting.locked` and deletes only those in `setting.unlocked`. shifa_auth reads `tenant_id, scope, scope_id, key, value, locked` of the organization's `session.idle_minutes` in the person's own clinics (permissive + restrictive policy). platform_setting_value: SELECT for every role, writes by migrations only. The owner's change and the super admin's lock and unlock of one key in one clinic run one at a time (`pg_advisory_xact_lock` on `shifa.settings:<tenant>:<key>`).
- **Module:** `modules/settings` (catalogue, resolver, sources, idle reads, the clinic's own route moved here from `team`, the platform routes). Identity reads the idle limit through the module's index, per request, with no cache: `tenantView()` in the clinic (shifa_app) and the sessions list on the auth path (shifa_auth).
- **Resolver:** a clinic value counts only at a scope in `overridable_by`, except the super admin's lock at the organization, which holds whatever the key's scopes; platform and plan values always count; a stored value its schema refuses is skipped with its lock; `specialty_pack` has no source until A-11. `writeRefusal()` (scope, lock at or above the scope, schema) is what the owner's write uses.
- **Contract (rows `set` … `unlockAsk`, idle row):** `SettingView` gains `lockedBy` (the scope of the lock) and `choices` is null when the schema is no enum; `lockable` is false while a platform or plan lock holds. `ClinicSettings` gains `source` and `locked`; the PATCH body is its own schema `UpdateClinicSettingsRequest` (the request no longer shares the response's id). New codes `setting_locked` and `setting_not_lockable` (Arabic texts in `packages/i18n/src/locales/ar/errors.json`, for the owner's review). The setting value in the contract is a number (±10⁹), a text (≤ 500) or a boolean, inline (as `EntitlementValue`, for the Dart client and ajv). No drawing changes.
- **Decisions under the owner's overnight delegation (2026-11-27), pending confirmation:** OD-121 (unlock removes the locked organization value: the clinic inherits again), OD-122 (audit `setting.viewed`, `setting.locked`, `setting.unlocked` with key, scope and before and after effective values; the owner's change stays `clinic.settings_changed`, now also with key, scope, before and after; no `setting.set`, as the super admin never sets without a lock), OD-123 (409 `setting_not_lockable` while the platform or plan locks the key).
- **Start-up:** `main.ts` also refuses a stored platform or plan value whose key the catalogue does not declare (`settingKeysInUse()` in `@shifa/db`); the catalogue refuses a malformed, doubled or over-36-character key, an unknown scope and a default its schema refuses.
- **Backfill** runs as shifa_owner, which is NOBYPASSRLS while `tenant` is FORCE RLS: it reads `tenant` through a temporary owner policy `tenant_owner_backfill`, dropped in the same migration (security review B1; the first version copied nothing outside the superuser test). It writes every clinic's `tenant.idle_minutes` as its organization value, so every existing clinic shows source `organization` (even at 30); clinics created after it inherit the default (no row). `tenant.idle_minutes` stays, unread, until A-02-06.
- **Existing tests changed by the contract change:** `test/team/settings.test.ts` (answers with `source` and `locked`), `packages/contracts/test/account-platform.test.ts` (the PATCH declares 409), `test/identity/support.ts` `setIdleMinutes()` (writes the cascade), the table-access lists (`team` no longer reads or writes `tenant`), web-shell's screen-world fakes.
- **Migrations:** `20261127044024_a02_settings` (expand: two tables) and `20261127044029_a02_setting_policies` (migrate + expand: the backfill, then RLS, grants and policies). Rollback notes in the SQL header; the contract step (drop `tenant.idle_minutes`, its check, its column grant and the `tenant_app_settings` policy) is A-02-06's.
- **Deploy and rollback:** deploy the migration with no instance of the earlier API serving: that code writes `tenant.idle_minutes`, which the cascade no longer reads, so an owner's change through it would be lost. A rollback of the code reads `tenant.idle_minutes` again, which still holds every clinic's value as of the migration; changes made through the cascade since are not copied back.
- **`createClinic()`** no longer takes `idleMinutes` (it would have been ignored): a new clinic inherits the default; the column's check is tested by a raw insert.
- **`platform_setting_value`** is written by no role, the owner included (FORCE RLS, a SELECT policy only): a migration that seeds a value adds a temporary INSERT policy for shifa_owner and drops it, as the backfill does on `tenant` (documented in the migration header, the schema and the classification).
