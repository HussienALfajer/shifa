# 0.2-09c Backups and restore drill: pgBackRest on Garage, point-in-time restore, weekly CI drill

Status: In review · Tier: T0 (backups of patient data, encryption keys, RLS after restore, CI and infrastructure) · Branch: `feat/0.2-09c-backups-and-restore-drill`
Spec: [0.2-09c](../specs/foundation/0.2-09c-backups-and-restore-drill.md) (criteria 1–11) · Requirements: PLT-51, PLT-50 · Decisions: ADR-0029, ADR-0021 (Garage), ADR-0004 (RLS), ADR-0022 (proposed)
Depends on: 0.2-09a (WSL2 move). Kept as one slice by the owner (2026-11-11) although the estimate (~2,300 hand-written lines) is more than twice the ~1,000-line budget. Build in the order of the plan; the three checkpoints are natural PR boundaries if the owner later wants to split.

## Goal
`pnpm backup:up` starts a local PostgreSQL 18 that archives WAL with pgBackRest into an encrypted repository on Garage; `backup:full`, `backup:diff`, `backup:check` and `backup:restore --target-time` work against it; `pnpm backup:drill` proves that a restore to time T keeps exactly the data written before T, the migration journal and every tenant table's RLS; CI runs the drill and three fault self-tests every week; `docs/process/backup-restore.md` lets an operator restore production.

## Plan
1. **Contracts / database schema / API / web / Flutter.** None. No migration: the drill table lives in a `drill` schema the drill creates itself, never in `packages/db/migrations`.

### Part A — stack, configuration, backup and check (criteria 1–4)
2. **Images** `infra/backup/`:
   - `postgres/Dockerfile`: `FROM postgres:18.6-trixie@sha256:…` (the harness digest in `packages/db/test-harness/image.ts`), installs `pgbackrest=<exact version>` from the PGDG apt repository the official image already configures, `--no-install-recommends`, nothing else. Built by compose (`build:`), tagged `shifa/backup-postgres:<pg>-<pgbackrest>`.
   - Garage `dxflrs/garage:v<version>@sha256:…`, single node, `replication_factor = 1`.
   - TLS in front of Garage: pgBackRest's S3 driver is expected to talk HTTPS only (confirm first), so a pinned `caddy:<version>@sha256:…` terminates TLS with `tls internal` and proxies to Garage's S3 port on the compose network; `backup:up` copies its root certificate to `infra/backup/.state/ca.crt` (git-ignored) for `repo1-storage-ca-file`. Verification stays on. Keep TLS even if plain HTTP turns out possible (production parity).
3. **Compose** `infra/backup/compose.yml` (project `shifa-backup`): services `postgres`, `garage`, `garage-tls`; only PostgreSQL is published (`127.0.0.1:55432`); every `ports` entry starts with `127.0.0.1:`; every secret is `${VAR:?}` from `infra/backup/.env` (git-ignored by the root `.env` rule); named volumes `pgdata`, `pgspool`, `garage-meta`, `garage-data`, `caddy-data`; healthchecks so `up --wait` works.
4. **Configuration**:
   - `infra/backup/postgres/postgresql.backup.conf`: `wal_level=replica`, `archive_mode=on`, `archive_command='pgbackrest --stanza=shifa archive-push %p'`, `archive_timeout=60s`.
   - `infra/backup/pgbackrest/pgbackrest.conf.template`: stanza `shifa`; `repo1-type=s3`, endpoint, `repo1-s3-bucket=shifa-backup`, `repo1-s3-region=garage`, `repo1-s3-uri-style=path`, `repo1-storage-ca-file`; `repo1-cipher-type=aes-256-cbc`; `compress-type=zst`; `repo1-retention-full-type=time`, `repo1-retention-full=30`; `log-level-console=info`, `log-level-file=info`; `start-fast=y`. Key, secret and passphrase only from env (`PGBACKREST_REPO1_S3_KEY`, `PGBACKREST_REPO1_S3_KEY_SECRET`, `PGBACKREST_REPO1_CIPHER_PASS`). A commented `repo2-*` block marks the off-site repository (OD-01).
   - `infra/backup/schedule.json`: full weekly (Sun 02:00), diff daily (02:00), WAL continuous, `retentionDays: 30`, `maxBackupAgeHours: 26` — the one source for scripts, check and doc.
   - `infra/backup/garage/garage.toml.template`: `rpc_secret` and `admin_token` from env.
5. **Scripts** (Node ESM, `node:` built-ins, `spawn` with argument arrays, never shell strings; each file under 400 lines): `scripts/backup.mjs up|down|reset|full|diff|check|restore|drill` over pure cores `scripts/lib/backup-env.mjs`, `backup-stack.mjs`, `backup-check.mjs`, `backup-restore.mjs`, `backup-faults.mjs`. Reuse the `.env`, ACL and runner patterns of `scripts/lib/obs.mjs`.
   - `up`: on first run writes `infra/backup/.env` (mode `0600`; Windows ACL through `icacls`) with random Garage `rpc_secret`, admin token, PostgreSQL password and cipher passphrase (`crypto.randomBytes`, ≥ 32 bytes), never printed; an existing `.env` is never overwritten; values already in the environment (CI) win over generation. `docker compose … up -d --wait`; bootstraps Garage once (layout assign + apply, bucket `shifa-backup`, key `shifa-pgbackrest`, `bucket allow --read --write` on that bucket only, no `--owner`), stores key id and secret in `.env`; copies the CA; runs `stanza-create` once; prints the PostgreSQL port only.
   - `down` stops (volumes kept); `reset` refuses without `--yes`, then `down -v`, deletes `.env` and `.state/`.
   - `full` / `diff`: `pgbackrest --stanza=shifa --type=full|diff backup` in the PostgreSQL container; secrets passed as container env, never on a command line.
   - `check`: `pgbackrest check`, then `info --output=json`; exit 1 when `check` fails, there is no backup, or the newest backup's stop time is older than `maxBackupAgeHours`; prints backup labels (type, label, stop time) and the newest archived WAL segment with its time, nothing else.
   *Checkpoint A: stack up, a full backup and `check` green on Docker; count lines.*

### Part B — restore, drill, report (criteria 5–8)
6. **Restore** (`backup-restore.mjs`):
   - Valid range from `info --output=json`: oldest backup stop time … newest archived WAL time; `--target-time` outside it is refused with the range (exit 2). Default: latest.
   - New named volume and container `postgres-restore-<timestamp>`; refuses (exit 2) when the target data directory is not empty, before any restore call.
   - `pgbackrest --stanza=shifa restore --type=time --target=<T> --target-action=promote` (or `--type=default`) with the entrypoint overridden; then PostgreSQL starts on a free `127.0.0.1` port with `archive_mode=off` (it must never push a new timeline into the source's repository); waits for `pg_is_in_recovery() = false`; prints label, target, port and duration only. Never touches the source container or volumes.
7. **Drill** `packages/db/scripts/backup-drill.ts` (reuses the harness and `packages/db/test/architecture/rls-presence.ts`; `@shifa/db` gets a `backup-drill` script and a dev dependency on `@shifa/testing`). `backup.mjs drill` runs `reset --yes`, `up`, then the drill with connection details in the child env only.
   - `migrate(ownerUrl)` and `roles.sql`; `drill.rows (id uuid pk, batch text, payload jsonb, created_at timestamptz)` filled from seeded `@shifa/testing` primitives: baseline 500 rows.
   - `backup:full`; batch A (200 rows); T = database `now()` (not host clock), `pg_sleep(1)`; batch B (200 rows); `pg_switch_wal()` and wait until that segment is archived (poll `info`, timeout).
   - `backup:restore --target-time T`, then named checks: `rows.baseline_and_a` (count and `md5(string_agg(canonical row text ORDER BY id))` equal on source and restore); `rows.b_absent`; `migrations.journal` (`drizzle.__drizzle_migrations` hash and created_at identical); `rls.presence` (no violations from the 0.2-06b check on the restore); `roles.app_not_owner` (`shifa_app` not superuser, not `BYPASSRLS`, owns no table); `restore.duration` (< 15 min in CI, configurable locally).
   - Exit 1 when any check fails; containers removed unless `--keep`.
8. **Report** `packages/db/scripts/backup-drill-report.ts`: `.verify/backup-drill/report.json` and `report.md` — date, PostgreSQL and pgBackRest versions, backup label, target time, restore duration, restored size (MB), rate MB/min, each check's name, pass/fail and a short reason. No row values, no connection strings. Zod schema exported from the same file.
   *Checkpoint B: `backup:drill` green locally; count lines.*

### Part C — faults, weekly CI, runbook (criteria 9–11)
9. **Fault self-tests** `backup.mjs drill --self-test <wrong-passphrase|missing-wal|garage-down>`:
   - `wrong-passphrase`: restore with a different passphrase → `restore failed: repository passphrase rejected`.
   - `missing-wal`: delete one archived segment between the backup and T through the stack's own Garage key inside the stack → `restore failed: WAL segment <name> missing from the archive`.
   - `garage-down`: stop `garage-tls` before the restore → `repository unreachable at <endpoint>`.
   - A self-test exits 0 only when the fault was injected and the drill failed with its message; otherwise 1. Messages come from pgBackRest error codes (confirm the codes against the pinned version; unknown codes are passed through).
10. **CI** `.github/workflows/backup-drill.yml`: `schedule` (Monday 03:00 UTC) and `workflow_dispatch` only; `permissions: contents: read`; `ubuntu-24.04`; actions pinned by SHA; Node and pnpm as in `ci.yml`; `concurrency` group. All secrets generated by `backup:up` in the job (no repository secrets), each masked with `::add-mask::` before any step prints. Steps: drill, then the three self-tests as separate steps, then upload `.verify/backup-drill/` (`if: always()`, `retention-days: 90`). Not a required PR check; `verify:full` does not run it.
11. **Docs**: `docs/process/backup-restore.md` — architecture, schedule and retention (from `schedule.json`), start, back up, check, restore to a time, reading the drill report and checking the 4-hour RTO from the measured rate (production size ÷ MB/min + WAL replay margin < 4 h), rotating the passphrase, adding `repo2` off-site (blocked by OD-01), the quarterly production drill, losing the passphrase (Infisical later; offline copy with the owner), GitHub disabling schedules after 60 idle days, and what is not backed up yet (Garage attachments, Orthanc). Short `infra/backup/README.md`; root `CLAUDE.md` Commands line for `backup:*`; PLT-51 line in `docs/domain/platform-and-configuration.md` links the doc and slice; data handling §3 "Backups" links it; `docs/README.md` lists it.
12. **Digests and versions**: read with `docker buildx imagetools inspect <image>:<version>` and `apt-cache policy pgbackrest` in the base image, from a shell that reaches Docker (Windows fallback or the owner's WSL2 terminal, OD-24). Only values read from that output are written.

## Risks
- pgBackRest S3 and TLS: the Caddy `tls internal` CA and Garage path-style S3 must work with pgBackRest; prove it in the first `backup:up` before writing the check.
- Target time: T from the database clock with a 1 s gap; `--target` needs a time zone (`+00`). WAL lag: wait until the switch segment is archived, or batch A can be missing.
- A restored instance with the source's `archive_command` would write a new timeline into the same repository: `archive_mode=off` is tested.
- PGDG may drop the pinned pgBackRest version: the build fails loudly; bump the pin in a PR. Garage CLI output changes between versions: pin it; parse through a fixture.
- `rls-presence.ts` sits under `packages/db/test/`: importing it from `packages/db/scripts/` stays inside the package; confirm the 0.2-06d boundary lint allows it.
- `workflow_dispatch` only runs a workflow file present on the default branch: the manual run happens after merge, or with `gh workflow run --ref` on the branch once the file exists on `main`.
- One large T0 PR is harder to review line by line: the PR description lists the three parts and their files.
- Docker is blocked in the sandboxed WSL2 session (OD-24): build from the Windows fallback.

### Proven before building (pgBackRest 2.60.0, Garage v2.5.0, Caddy 2.11.9)
- pgBackRest's S3 driver over Caddy `tls internal` with `repo1-storage-ca-file` and Garage path-style URIs: `stanza-create`, `check`, `backup` and `restore` work; verification stays on.
- Fault output: wrong passphrase → `[FormatError] unable to load info file` then `ERROR: [075]`; Garage down → `[HostConnectError]`; missing archived segment → restore succeeds, recovery logs `unable to find <segment> in the archive`, then PostgreSQL `FATAL: recovery ended before configured recovery target was reached`. The `[075]` code is generic, so the messages map the error type names, not the code. Fixtures in `scripts/test/fixtures/backup/`.
- Recovery to T needs a commit after T in archived WAL (else the same FATAL); the drill commits batch B, switches WAL and waits for it.

### Deviations from the plan
- No `postgresql.backup.conf`: the archive settings are `-c` flags in the compose `command`, so a restored data directory never inherits them; the restored instance starts with `archive_mode=off`.
- `pgbackrest.conf` and `garage.toml` are plain files (no templates): pgBackRest and Garage read their secrets from the environment (`PGBACKREST_REPO1_*`, `GARAGE_RPC_SECRET`, `GARAGE_ADMIN_TOKEN`).
- No `pgspool` volume (archive-push is synchronous). Garage creates the S3 key (`key create`) instead of importing one, so the secret never appears in an argument; `up` starts Garage first with placeholders, bootstraps, then PostgreSQL.
- Restore runs pgBackRest in a separate `docker run` of the same image on the compose network, so it works while the source is down. Fault injection is an internal `backup.mjs fault` command used by the drill.
- The drill-checks DB test uses two pristine clones in the harness container (pool ids 9995, 9996) instead of two containers. `scripts/**` joined `allowRawDb` in `packages/db` (the drill compares its own containers as superuser). The runner of `obs.mjs` moved to `scripts/lib/stack-io.mjs`, shared with `backup.mjs`.
- The drill waits 2 s after the full backup: pgBackRest records the stop time in whole seconds, and a T within that second found no backup set (seen once in four runs).
- Size: ~3,000 added lines including tests and docs (plan estimate ~2,300), one slice by the owner's choice.
