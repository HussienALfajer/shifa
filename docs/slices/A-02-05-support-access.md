## Goal
A super admin opens time-boxed, reasoned, read-only access to one clinic and reads clinic web as its owner sees it; every owner sees it happening and can end it; every request is audited.

## Plan
### Checkpoint 1 — ADR and schema
- **ADR** (support grant mechanism): admin web and clinic web are different hosts and the session cookie is `__Host-` (no Domain), so opening clinic web needs a hand-off. Recommended: `POST /platform/clinics/:id/support` creates the grant and a one-time hand-off token (hashed, ~2 min, like setup links); the new tab opens clinic web with it; clinic web exchanges it for a separate **support session** (its own cookie, `support_grant_id`, expiry = grant end, the super admin's MFA state carried); the admin session is never reused in a tenant. Alternatives and threats (token leak, replay, fixation, cross-tab) in the ADR.
- **Database** (`/db-migration`, `/rls-policy`; expand only): `support_access_grant` (tenant_id, admin user id, reason, opened_at, expires_at, ended_at, ended_by, end_reason `admin | owner | expired`): FORCE RLS; `shifa_app` SELECT of its own tenant and UPDATE of `ended_at, ended_by, end_reason` only on an open row (column grant + restrictive policy, approved at `/db-migration`); `shifa_platform` INSERT and end; `shifa_auth` reads the grant behind a support session. Partial unique index: one open grant per super admin per clinic. Hand-off token table or columns. Isolation case.
### Checkpoint 2 — support principal and read-only enforcement
- Principal gains `support: { grantId, expiresAt } | undefined` (PrincipalSchema, refine: only with `platformAdmin` and a tenant); its roles are a synthesised tenant-wide `owner` for reads; `support.elevate` added to `PERMISSION_CATALOGUE`, granted to nobody.
- Guard: in a support session every route that is not GET/HEAD answers 403 `support_read_only` (before the handler), `@SignedIn` account writes included; `TenantDb.run()` opens the transaction `READ ONLY` for a support scope (second wall); suspended clinic still readable (criterion 14).
- Ends: expiry, the admin (`POST /platform/clinics/:id/support/end`), an owner (`POST /clinic/support-access/:id/end`); the next request answers 401 `session_expired` reason `support_ended`.
### Checkpoint 3 — owner side, console data, audit
- `GET /clinic/support-access` (owner, `clinic.settings.manage`): the open grant (admin's name, reason, end) for the banner, and every grant for the log. `GET /platform/clinics/:id/support` for admin web: open grant with time left and past grants; 409 `support_active`.
- Audit: `support.opened` (duration; reason only on the grant row), `support.ended` (by whom), `support.expired`, and one `support.request` row per request in a support session (route template, target id, no body, no query).
- Logs and spans carry the grant id only; reasons never.
4. **Web, Flutter** — none (admin side A-02-08; clinic web frame and banner A-02-10).
5. **End-to-end** — API journey: open → hand-off → owner read 200 → a write 403 → owner ends → 401 `support_ended`.

Tests written first: reason 10–500 and durations 30 min, 1, 2, 4 h only; second open grant 409 `support_active` (11); route matrix in a support session: every non-GET route 403 `support_read_only`, every owner GET 200 (12); a write forced past the guard fails on the read-only transaction (12); three ways to end, then 401 `support_ended` (12); owner banner and log data, another clinic's owner sees nothing (13); audit rows per event and per request without bodies (14); suspended clinic opens (14); hand-off token single-use and expiring; isolation case; leak test (no reason in logs).
Estimated hand-written lines: ~4,090 (ADR ~150, database ~500, principal and guard ~600, grants, hand-off and re-open ~780, owner and console routes ~380, contracts ~220, tests ~1,420). Re-estimated at A-02-01 checkpoint 3 (owner, 2026-11-27).

## As built (changes from the plan, reported to the owner)
- **Branch:** `claude/admiring-johnson-rxetti` (cloud session; planned as `feat/A-02-05-support-access`).
- **Migrations:** `20261127073300_a02_support_access` (expand: `support_access_grant`, `session.support_grant_id` nullable with an index) and `20261127073301_a02_support_policies` (expand: RLS, grants, policies; no data read or written). Rollback: drop the policies, disable RLS, revoke, drop the table and the column (nothing depends on them). No long lock: a nullable column without a default.
- **Table:** `support_access_grant` with `admin_name` and `ended_by_name` (snapshots, so neither shifa_app nor shifa_platform reads another person's account), `end_reason` `admin | owner | expiry` (the contract's `expiry`, not the plan's `expired`), `handoff_token_hash` and `handoff_expires_at` on the grant (no separate hand-off table). Partial unique index `(tenant_id, admin_user_id) where ended_at is null`.
- **Who does what:** shifa_app reads its clinic's grants (table SELECT, the hash included as for setup links: the isolation runner reads `ctid`, which a column grant cannot give; the API never selects it) and ends an open, unexpired one as `owner` by itself (`UPDATE (ended_at, ended_by, ended_by_name, end_reason)`, restrictive policy). shifa_platform: column SELECT without the hash; INSERT in `support.opened`; UPDATE by column in support actions (a hand-off on an open grant, its own end as `admin`, the close of an expired grant). shifa_auth: reads the grant of its hand-off hash (`withHandoff`) or of the signed-in super admin; clears the hash of an open grant once; closes its own expired grant. Every side-role policy is paired with a restrictive one and has its reason in the classification.
- **`@shifa/db`:** `withTenant({ …, readOnly: true })` opens the transaction READ ONLY; `createAuthDb().withHandoff(hash, fn, userId?)`; the isolation runner gained `withoutPrivilege: ['insert', 'delete']` for a read-write table the clinic only updates by column.
- **Routes (as the contract names them):** `GET|POST /platform/clinics/:id/support-grants`, `POST /platform/support-grants/:id/handoff`, `POST /platform/support-grants/:id/end`, `GET /clinic/support-grants`, `POST /clinic/support-grants/:id/end`, `POST /auth/support/end` (`@SignedIn` + `@SupportSessionWrite`), and the exchange `POST /auth/support/session` (public; new row in the screen contract). `support` on `GET /auth/session`.
- **Audit:** `support.listed`, `support.opened` (`minutes`, `grantId`), `support.handoff_issued`, `support.ended` (platform rows; the owner's in the clinic with `endedBy: owner`), `support.expired` (once per grant), `support.session_started`, and `support.request` (clinic row: `grantId`, `method`, route template; target the path's `:id`). Never the reason, a body or a query.
- **Module:** `apps/api/src/modules/support/` (grants, owner side, the guard's request audit through the `SUPPORT_AUDIT` port); the support session itself in `identity` (`support-sessions.ts`, `support-handoff.ts`, `support-session.controller.ts`, `support-directory.ts`).
- **Contract change (OD-126):** the 401 carries `supportEnded` (`endedBy`, `endedAt`, `ownerName`), not `details`; row updated in the screen contract.
- **After review (2026-11-27):** the support session row and cookie live 12 hours from the hand-off, beyond the grant (the end is decided by the grant; the row is deleted after those 12 hours), so `endedExpiry` reaches the tab on every request; the answer reporting the end and the tab's own end clear the cookie; a support cookie without its row answers `session_expired` (`ended`) unless `__Host-shifa.sid` is present. `GET /clinic/subscription` and `GET /clinic/support-grants` carry `@NotInSupportSession` (403 in a support session, the spec's Permissions table). `withPlatformAdmin()` sets `app.user_id` to the actor (no other policy for shifa_platform reads it), and the platform's support policies are tied to it; the open is bounded by the database's clock (opened within 5 minutes of now, at most 4 hours, a hand-off at most 5 minutes ahead; a few minutes of skew allowed for the API's clock); support.opened only inserts; ended_by and ended_by_name are null while open (check); the owner's end is never by the grant's admin and is stamped now (±2 minutes); shifa_auth never re-opens an ended grant even with a tenant set. `@SupportSessionWrite` is refused at start-up on any handler but `SupportEndController.end`. Audit targets are lower-cased UUIDs; a refused hand-off logs its grant id and reason. closeExpired uses the API's clock, bounded by the database's. The isolation case seeds an open grant too (runner option `updateRefused`).
