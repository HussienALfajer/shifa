# 0.3-S2a PgBouncer in the test harness, pooled isolation suite

Status: Built · Tier: T0 (tenant context, RLS, test infrastructure and CI) · Branch: `chore/0.3-s2a-pgbouncer-harness`
Spec: [0.3-S2 tenant isolation](../specs/spikes/0.3-s2-tenant-isolation.md) criteria 1–3 · Requirements: PLT-01, PLT-50

## Goal
Every DB test run starts PgBouncer (transaction mode, tiny server pool) next to PostgreSQL. `pooledTestDb()` gives the same `createDb()` view as `testDb()` but through PgBouncer, and the cross-tenant isolation suite runs in both modes. Slices 0.3-S2b and 0.3-S2c build their leak tests and measurements on this.

## Plan
1. **Contracts:** none (no API surface).
2. **Database harness** (`packages/db/test-harness/`):
   - `image.ts`: add `PGBOUNCER_IMAGE`, the latest stable PgBouncer, tag + digest, image at least 24 hours old. Choose a maintained image whose tag names the PgBouncer version; configure it only through our own mounted `pgbouncer.ini` and `userlist.txt` (no image-specific env vars), so the image can be swapped. Record the choice and why in the slice's "As built".
   - `container.ts`: start a Testcontainers `Network`; PostgreSQL joins it with an alias; PgBouncer starts on it after roles are applied. `pgbouncer.ini` is built in code: `pool_mode = transaction`, `default_pool_size = 2`, `max_prepared_statements = 200` (> 0), `auth_type = scram-sha-256`, `server_reset_query` left at the transaction-mode default (empty; S2b decides on `server_reset_query_always`), `ignore_startup_parameters` only as needed by `pg`, a wildcard `[databases] * = host=<alias> port=5432`, and one explicit entry with `pool_size = 1` for a fixed pooling database (`shifa_test_9996`, cloned like the pristine `9997`) that S2b uses to force reuse of one server connection. `userlist.txt` is generated per run from the random harness passwords (`shifa_app`, `shifa_owner` for the negative role test) and copied into the container; never written to disk in the repo or logged.
   - `context.ts` / `guard.ts`: `HarnessInfo` gains the pooler address; `urlFor(info, role, db, { via: 'direct' | 'pooler' })`; `assertTestTarget` accepts exactly the PostgreSQL address or the PgBouncer address the harness created, and nothing else (`OWN_DATABASE` unchanged).
   - `index.ts`: `pooledTestDb(options?)` (shared per file like `testDb()`), `rawPooledAppDb()` (negative tests only), `pooledHarnessUrl(role)`. Same closers, same reset.
   - `vitest.db.config.ts`: nothing new; one container pair per run.
3. **Isolation suite:** `isolation.test.ts` loops over `[['direct', testDb], ['pgbouncer', pooledTestDb]]` and runs the coverage test and every case in each mode (cases are empty today, so the probe proof below matters). `runner-gaps.test.ts` keeps its direct run and adds the pooled run for the uncovered-table and leaky-table cases.
4. **CI:** `.github/workflows/ci.yml` "Pull database test images" expects 3 digest-pinned images and its regex accepts the PgBouncer image name.
5. **Docs:** `packages/db/CLAUDE.md` Tests section: `pooledTestDb()`, `rawPooledAppDb()`, the pooling database; image pins line.
6. **Web / Flutter / end-to-end:** not applicable.

## As built
- **Image:** `edoburu/pgbouncer:v1.26.1-p0` (PgBouncer 1.26.1, released 2026-10-14; image built 2026-10-19), pinned by its multi-arch index digest (linux/amd64 + linux/arm64). Source: github.com/edoburu/docker-pgbouncer (single-maintainer community image; fine for the throw-away harness, not carried into production by default: ADR-0030 chooses there). Chosen because it is maintained, tracks PgBouncer releases within days and its tag names the PgBouncer version. The harness uses only the `pgbouncer` binary: entrypoint bypassed (`withEntrypoint(['pgbouncer'])`), no image env vars, our own `pgbouncer.ini` and `userlist.txt` copied into `/etc/pgbouncer/`. Any image with `pgbouncer` on its PATH and an unprivileged default user drops in.
- **Config** (`test-harness/pgbouncer.ts`): `pool_mode = transaction`, `default_pool_size = 2`, `min_pool_size = 0`, `reserve_pool_size = 0` (pool sizes are exact), `max_prepared_statements = 200`, `auth_type = scram-sha-256`, `stats_users = shifa_pooler_stats` (read-only console; no `admin_users`), `max_client_conn = 1000` (shared by every worker; the default 100 would cap S2b concurrency), `unix_socket_dir =` (TCP only), `[databases] * = host=shifa-postgres port=5432` plus `shifa_test_9994 … pool_size=1`. `server_reset_query` is not set: its default (`DISCARD ALL`) is not used in transaction mode, and `server_reset_query_always = 0` is asserted (S2b decides). `ignore_startup_parameters` was not needed: `pg` sends only parameters PgBouncer tracks.
- **Deviation: pooling database is `shifa_test_9994`, not `9996`.** `backup-drill-checks.test.ts` already reserves 9995 and 9996 (with 9997 rls-presence, 9998 hardening, 9999 harness). Exported as `POOLING_DATABASE`; `startHarnessContainer()` clones it from the template before PgBouncer starts; `setup.ts` never truncates it (its tests clean up after themselves).
- **Userlist:** generated per run in memory from the random harness passwords (`shifa_app`, `shifa_owner`) plus a random password for `shifa_pooler_stats`, which exists only in PgBouncer (`stats_users`: `SHOW` only; a `SET` is refused with "admin access needed", tested). A first version copied PostgreSQL's SCRAM secrets instead (no plain password in the container). It failed once `roles.test.ts` ran `applyRolesSql()`: `ALTER ROLE … PASSWORD` re-salts the stored secret, and the copied secret no longer matched. PgBouncer now runs SCRAM with the client and, separately, with PostgreSQL.
- **Guard:** `assertTestTarget` accepts exactly the PostgreSQL pair or the PgBouncer pair (host *and* port), so "pooler host + PostgreSQL port" is refused. `OWN_DATABASE` is unchanged for direct URLs. Through the pooler only `shifa_test_<n>` and the console database `pgbouncer` are accepted: an idle pooled server connection on `shifa_template` would block every later clone.
- **Network:** a Testcontainers `Network`; PostgreSQL joins with alias `shifa-postgres`; PgBouncer starts after roles and the template migration. Stop order: PgBouncer, PostgreSQL, network. `startHarnessContainer()` (also used by the API boot check and `apps/api/scripts/obs-smoke.ts`) always starts PgBouncer.
- **API** (`@shifa/db/testing`): `pooledTestDb(options?)` (shared per file like `testDb()`), `rawPooledAppDb(database?)`, `pooledHarnessUrl(role, database?)`, `showPooler('CONFIG' | 'DATABASES' | 'POOLS' | 'SERVERS' | 'CLIENTS')` (runtime allowlist), `rawPoolerConsole(text)` (negative tests only), `POOLING_DATABASE`. `urlFor(info, role, db, { via: 'direct' | 'pooler' })`.
- **Pooler-path proof:** the plan's `inet_server_port()` would be 5432 on both paths (the in-container port), so it proves nothing. The test instead reads `pg_backend_pid()` inside `withTenant()` and finds that pid as `remote_pid` in PgBouncer's `SHOW SERVERS` (user `shifa_app`, this worker's database).
- **Isolation suite:** `test/isolation/modes.ts` (`DB_MODES`); `isolation.test.ts` and all of `runner-gaps.test.ts` (M2, N1, M4, M3 `using (true)`, N2, plus an uncovered-table coverage check) run under `describe.each(DB_MODES)`, and so does `runner.test.ts` (the isolated probe must return `[]`, the `using (true)` probe is reported). `ISOLATION_CASES` is still empty, so the pooled evidence today is the runner probes. `test/pgbouncer-routing.test.ts` proves per mode that the backend pid is in `SHOW SERVERS` only for `pgbouncer` (so `['pgbouncer', () => testDb()]` fails), and the same for `rawPooledAppDb()` vs `rawAppDb()`.
- **Locked test change (owner-approved, 2026-11-12):** `pgbouncer.test.ts` line 51 `String(path)` → `path` (lint only, no behaviour change).
