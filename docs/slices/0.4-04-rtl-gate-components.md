# 0.4-04 RTL gate: eight components on UI SDK, and the `/ui-component` skill

Status: Done (PR open) · Tier: T1 · Branch: `feat/0.4-04-rtl-gate`
Spec: [0.4 Design system foundations](../specs/design-system/0.4-design-system-foundations.md) criteria 7, 8 and 9 (these eight), 11 (`/ui-component`) · Requirements: none · Decisions: ADR-0039 (RTL gate, Base UI fallback), OD-20, OD-61

After [0.4-03](0.4-03-ui-scaffold-storybook-lint.md). Eight checkpoints, one per component, then the skill. The result decides whether the rest of the set is built on UI SDK.

## Goal
Select, Combobox, Menu, Dialog, Popover, Tabs, Date Picker and Number Input exist in `packages/ui`, styled with the chosen design language, and each has passed or failed the Arabic RTL gate with evidence. A failed component works anyway, on Base UI behind the same API.

## Choices made by this plan
- **Design sheet first (ADR-0040):** one sheet in the proposals canvas shows the eight components (closed and open, all states, light and dark, RTL and LTR, both densities); the owner approves it before the first component is coded. After the gate, the real components are synced to the design system and the sheet is marked superseded. A component that falls back to Base UI keeps its approved look.
- **Order:** Tabs, Dialog, Popover, Menu, Select, Combobox, Number Input, Date Picker (simplest behaviour first, so the helpers are proven before the hard ones).
- **What "pass" means, per component, in Arabic RTL and English LTR:** arrow keys move in reading direction (Left = next in RTL for horizontal sets); the popup opens on the logical side and aligns to the logical start; focus is trapped where it must be and returns to the trigger; typeahead finds an item by Arabic letters; a number or date field accepts Arabic-Indic and Western digits and shows the clinic's style; axe is clean. Checks that do not apply to a component are marked "n/a" with the reason.
- **Fail path:** one attempt to fix by configuration or a wrapper inside `packages/ui`. If it still fails: build on `@base-ui/react` (exact pin, added only then) with Base UI's `DirectionProvider`, same exported API and the same tests; add a row to the design doc ("component, upstream issue, date"). For Date Picker the fallback is react-day-picker (ADR-0039).
- **Stop rule:** if four or more of the eight fail, stop after the gate and report to the owner before 0.4-05: that result questions ADR-0039.
- **Dates:** Gregorian with Arabic locale formatting; no Hijri calendar (UI SDK has none; not in the spec).
- **`/ui-component` skill:** written last, from what the eight taught: API conventions, the story matrix, the test list, the fallback procedure, and the best component to copy for each kind (field, popup, list). Also `.claude/rules/ui.md` (path-scoped to `packages/ui`).

### Differences from the sheet (explained, not fixed)
- A disabled tab or menu item is reachable by the arrows and announced as disabled, as UI SDK and the APG patterns do; the sheet's notes said "skipped". It still never selects or runs, and the menu item says why. The tests were written to that before they were locked.
- Floating panels (popover, menu, lists, calendar) fade in without the 4–8 px rise, so their place is final from the first frame; the dialog keeps its rise.
- The tab underline sits just above the list's line, not over it (no negative margin in the token scale).
- Panel padding is 8 px (the nearest token step) where the sheet drew 6.

### Owner decisions during the build
- The Arabic typeahead checks of Menu and Select were locked with `userEvent.keyboard`, which sends no key events for an Arabic letter outside a text field, so they could not pass whatever the component did. With the owner's approval (2026-11-20), they use a new helper `pressKeys` (Chromium's input protocol, a real `keydown`), and six lint findings in the locked files were fixed at the same time. No check was weakened.
