# 0.2-06b RLS presence check and cross-tenant isolation suite

Status: In review · Tier: T0 (RLS and tenant context) · Branch: `chore/0.2-06b-rls-isolation-suite`
Spec: none (foundation tooling; [ADR-0004](../adr/0004-postgresql-pooled-tenancy-rls.md) "CI runs a cross-tenant isolation suite", [platform-and-configuration](../domain/platform-and-configuration.md) §verification) · Requirements: PLT-01

## Goal
Before the first product table lands, CI fails when any table is unclassified, when a tenant table lacks `tenant_id`, RLS, FORCE RLS or a policy on `current_tenant_id()`, or when a tenant table has no isolation case. The isolation suite seeds two tenants and runs every registered read and write path as `shifa_app`, asserting zero foreign rows. Independent of 0.2-06a (only `packages/db` and docs change), so it can run in parallel.

## Plan
1. **Table classification** (`packages/db/src/schema/classification.ts`): every table in `public` is listed exactly once as `tenant` (RLS required), `global` (no tenant data, reason required, e.g. `tenant_deployment` later) or `system` (drizzle migrations table). The schema has no product tables yet, so the list starts empty except `system`.
2. **RLS presence test** (`packages/db/test/architecture/rls-presence.test.ts`, catalog queries as owner): for each table in `pg_class`/`pg_namespace` `public`:
   - not in the classification → fail with the table name and the fix;
   - `tenant`: has `tenant_id uuid not null`; `relrowsecurity` and `relforcerowsecurity` true; at least one policy for each of SELECT/INSERT/UPDATE/DELETE (or `ALL`) whose `qual` and `with_check` reference `current_tenant_id()`; every index on it except the primary key leads with `tenant_id` (ADR-0004); no grant to `PUBLIC`;
   - `global`: no `tenant_id` column (a `tenant_id` on a global table is a misclassification);
   - `shifa_app` owns nothing and has no `BYPASSRLS` (repeats 0.2-05 at catalog level, cheap).
   Views and materialized views in `public` must be `security_invoker` or fail.
3. **Isolation suite** (`packages/db/test/isolation/`): `defineIsolationCase({ table, seed(tx, tenant), paths: { name: (tx) => rows } })` registry, one file per table later. Runner: seeds tenants A and B through `withTenant` as `shifa_app` (owner never seeds tenant data, so `WITH CHECK` is exercised), then for every path runs it in A and asserts no row has B's `tenant_id`; inserts/updates with B's `tenant_id` inside A are rejected; `UPDATE`/`DELETE` without `WHERE` inside A leaves B's rows unchanged (checked by owner count). Coverage test: every `tenant` table in the classification has a case, else fail. A test-only `rls_probe_isolation` table (created in the test, classified test-only) proves the runner, plus a deliberately broken probe (policy `using (true)`) that the runner must flag.
4. **Skill and rules.** `/rls-policy` (`.claude/skills/rls-policy/`): SQL template for the four policies on `current_tenant_id()`, FORCE RLS, classification entry, isolation case; referenced from `/db-migration` and `.claude/rules/db.md`. Update `packages/db/CLAUDE.md` (isolation case required per tenant table), roadmap checklist.
5. **CI.** No new job: tests run in the existing DB project inside `verify`. Suite runtime recorded in the PR.

## As built (deviations from the plan)
- The classification starts fully empty: Drizzle's migration history is in the `drizzle` schema, not `public`, so there is no `system` entry yet. Relations in any schema other than `public`/`drizzle` fail the check.
- The presence check reads a pristine clone (`shifa_test_9997`), because other test files leave probe tables in the worker database. The harness now serialises creation of shared clones (advisory lock).
- B's rows after A's unrestricted UPDATE/DELETE are read as `shifa_app` in tenant B (row ids via `ctid`), not by the owner: FORCE RLS binds the owner too.
- Materialized views always fail (they cannot be `security_invoker`).
- After review: a policy must be exactly the tenant filter or a top-level AND led by it; foreign keys to tenant tables and non-uuid primary keys must lead with `tenant_id`; the runner adds its own unfiltered select, requires own rows from every path, also runs every path and the forged insert without a tenant context (`withPlatformAdmin`), and accepts only an RLS refusal for the case's own table.
