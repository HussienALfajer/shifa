# 0.3-S7a Push spike: probe app, spike receiver with inbox, FCM sender, key-leak check

Status: Done (PR open) · Tier: T1 (Firebase config and service-account key handling in a public repository; no patient data, no schema, throwaway code). The key-leak check and the sender's auth also get a `security-reviewer` pass. · Branch: `chore/0.3-s7a-push-probe-and-sender`
Spec: [0.3-S7 Push](../specs/spikes/0.3-s7-push.md) criteria 1, 2, 3 (code and tests; real evidence in 0.3-S7b) · Requirements: MSG-01 (steps 1–2), MSG-26, MSG-27, MSG-29, MSG-30, PAT-20 (push part), PAT-21, PAT-29 · Decisions: ADR-0017, ADR-0012, ADR-0023, ADR-0026, OD-31, OD-52

First of two slices. This slice builds everything CI can prove without Firebase: the Flutter probe against a fake push client, the receiver and the sender against a fake FCM and a fake token endpoint. [0.3-S7b](0.3-s7b-push-runs-and-result.md) brings the owner's Firebase set-up, the emulator scenario runner, the state matrix, the one-day run, the analysis, the report and ADR-0038. About 3,600 hand-written lines, in five checkpoints (A–E); each ends green and committed.

## Goal
A developer can run the spike receiver on `127.0.0.1`, build the probe app with an untracked `google-services.json`, and send visible high-priority appointment pushes (collapse key, TTL, `s7_` label) whose inbox record is written first; the probe sets up its channels, asks for notification permission only after "book", reports token, permission and channel state on every open, logs and dedupes each message and shows the inbox fetched on open and polled while open. CI proves all of it with fakes and never calls FCM.

## Choices made by this plan

### Probe app (criterion 1)
- **Standalone Flutter app** `spikes/s7-push/probe/` (like the S1 probe: not in the pub workspace, no `package.json`; Flutter from `.fvmrc` through `node scripts/dart.mjs`). Pinned `firebase_core`, `firebase_messaging`, `flutter_local_notifications`, `http`, `path_provider`, latest stable at build time, versions recorded in the report.
- **Package id:** `dev.shifa.spike.s7push` (spike only, never the real app's id); a second flavor `noshow` (`dev.shifa.spike.s7push.noshow`) for criterion 5. The owner may change the id before registering it in 0.3-S7b.
- **Firebase config:** `android/app/google-services.json` is untracked and git-ignored; the Gradle plugin is applied only when the file exists, so `flutter test` and `flutter analyze` run without it. All Firebase calls sit behind a `PushClient` interface; tests use a fake.
- **Channels:** created at first launch with `flutter_local_notifications`: `appointments` named "مواعيد" (importance high) and `general` named "عام" (default). Foreground messages are shown by the probe on the channel named in the message (FCM does not show them in the foreground).
- **Permission (MSG-26):** never at launch. A "احجز موعداً" button creates a synthetic appointment, then explains "لنذكّرك بموعدك" and calls `requestPermission()` on Android 13+; denial is recorded and the button shows "التنبيهات متوقفة" with a link to settings.
- **Device state (PAT-21):** on every open and token refresh the probe posts `{installId, tokenHash, token, permission, channels: {appointments, general}: importance, appVersion, sdkInt, model}` to the receiver. `installId` is a random id kept in app storage; the token goes only to the local receiver, never to logs or reports (short SHA-256 prefix there).
- **Message log:** every message carries `s7id` (sender's id) and `sentAt` in its data; the probe appends `{s7id, fcmMessageId, label, sentAt, receivedAt, appState, path}` (path = foreground / background handler / opened from tray) to a local JSONL file and posts it to the receiver, retrying from a small outbox when offline. Duplicates by `s7id` are dropped (edge case "arrives twice").
- **Inbox (PAT-29, MSG-30):** "صندوق الإشعارات" lists the receiver's inbox for this `installId`, fetched on open and on resume, polled every 10 s while in the foreground; the last fetch is cached so the view works offline. A synthetic live-queue line ("دورك بعد ٣") comes from the same poll, not from push.
- **Clock:** on each open the probe calls the receiver's `/time` three times and records the offset with the lowest round trip; logged with every receipt.
- **Arabic UI:** RTL, Arabic labels, synthetic clinic "عيادة تجريبية" and synthetic names only.

### Spike receiver (criteria 1, 3)
- **Node HTTP server** `spikes/s7-push/receiver/` (`@shifa-spike/s7-receiver`), `node:http` only, bound to `127.0.0.1` (the emulator reaches it at `10.0.2.2`); state in append-only JSONL files under `spikes/s7-push/.out/` (git-ignored).
- **Endpoints:** `POST /devices` (state report), `POST /receipts`, `GET /inbox?installId&since`, `GET /time`, `GET /queue`; plus a library API the sender uses: `writeInbox(record)` before every send, `markDead(installId)`.
- **"Lost" is computable:** every send id has an inbox record written before the FCM call, so the analysis in 0.3-S7b can join sends, receipts and inbox fetches.

### Sender (criterion 2)
- **Package** `spikes/s7-push/sender/` (`@shifa-spike/s7-sender`), CLI `send --kind <reminder|turn-near|call-in|sync> --appointment <id> --to <installId|all> [--count n] [--no-collapse] [--ttl-to <iso>]`.
- **Auth without a Google SDK:** an RS256 JWT signed with `node:crypto` from the service-account key, exchanged at the token URL for an access token (cached until 60 s before expiry). Token and FCM base URLs are configurable so tests point them at fakes. The key file path comes from `.env.local` (`S7_SERVICE_ACCOUNT_FILE`); the key is never logged.
- **Payload rules:** appointment events (`reminder`, `turn-near`, `call-in`) are visible notification messages with `android.priority: HIGH`, `android.notification.channel_id: appointments`, Arabic title and body with no diagnosis or specialty, `collapse_key: appt_<id>` (unless `--no-collapse`), `ttl` = appointment time − now (minimum 0 s; capped at FCM's 28 days), `fcm_options.analytics_label: s7_<kind>`; `sync` is data-only with `priority: NORMAL`. Data always holds `s7id`, `sentAt`, `appointmentId`, `kind`.
- **Order and records:** inbox record → FCM call → send log line `{s7id, installId, sentAt, fcmName | error, httpStatus, durationMs}`. `UNREGISTERED` (404) and `INVALID_ARGUMENT` on the token mark the device dead and skip it next time; `429`/`5xx` retried with backoff up to 3 times, the same `s7id` kept.
- **Validation:** label must match FCM's `^[a-zA-Z0-9-_.~%]{1,50}$` and start with `s7_`; refuses to send to a dead device.

### Key-leak check
- `sender/scripts/check-no-secrets.ts` fails if any tracked or untracked-but-not-ignored file under `spikes/s7-push/`, or any file in `.out/` logs and `docs/spikes/s7-*`, contains a private-key block, a service-account object (`type` = `service_account`), a Firebase API key pattern (`AIza[0-9A-Za-z_-]{35}`), a `google-services.json` body (`"project_info"`), or a full FCM token pattern; it also fails if `google-services.json` or the key file is tracked. Run in the workflow and by the owner before each commit in 0.3-S7b.

## Tests written first

- `receiver/test/devices.test.ts` (1): a state report is stored with permission and channel importance; a later report replaces it; the full token is never written to the request log.
- `sender/test/payload.test.ts` (2): appointment kinds are visible, `HIGH`, channel `appointments`, collapse key per appointment, TTL ends at the appointment time (0 s when past), label `s7_<kind>`; `sync` is data-only `NORMAL`; `--no-collapse` drops the key; body holds no field outside the allowed synthetic set.
- `sender/test/send.test.ts` (2, 3): against the fake FCM the inbox record exists before the FCM request arrives; send log has id, time, response; `UNREGISTERED` marks dead and the next send skips it; `429` then `200` retries with the same `s7id`; `400` on the label is not retried.
- `sender/test/auth.test.ts` (2): the JWT has the FCM scope, `aud` = token URL, 1 h expiry, verifies with the fake key's public half; the token is cached and refreshed before expiry; the key never appears in logs or errors.
- `sender/test/check-no-secrets.test.ts`: each planted pattern fails the check; a clean tree passes; a tracked `google-services.json` fails.
- `probe/test/channels_test.dart` (1): first launch creates both channels with the right names and importance; a second launch does not recreate them.
- `probe/test/permission_flow_test.dart` (1, MSG-26): no permission request at launch; "book" shows the explanation, then requests; denial is recorded and shown.
- `probe/test/device_state_test.dart` (1): every open and token refresh posts token, permission and channel state; offline report is queued and sent on reconnect.
- `probe/test/message_log_test.dart` (1, edge case): a message is logged once per `s7id` across foreground and tray-open paths; app state recorded; offline receipts reach the receiver later.
- `probe/test/inbox_test.dart` (3): inbox fetched on open and resume, polled every 10 s in the foreground only; cached inbox shown offline.

## Deviations from the plan
- Size: about 5,100 added lines (including the generated Android scaffold, about 650 lines of review-fix code and tests), not ~3,600.
- Extra probe files: `store.dart` (file and memory store, serial queue) and `receiver_api.dart`; `device_info_plus` and `crypto` added to read the SDK level and model and hash the token.
- The sender's CLI takes `--at <iso>` for the synthetic appointment time (default now + 2 h), which sets the TTL end.
- firebase_messaging 17 deprecates `getToken`/`onTokenRefresh` for an Installation-ID direct-send path; the probe keeps them (documented ignores) because FCM HTTP v1 `message.token` needs the registration token. The FID path is untested.
- Locked tests: only Biome import reordering; lint-only ESLint overrides for three of them (template parts that keep secret patterns out of the source, a number in a template, a `let` read by a callback).
- The key-leak check also runs in the sender's `lint` (so `verify` and PR CI run it), covers `docs/slices/0.3-s7*` and ADR-0038, decodes UTF-16, and fails on archives, files over 64 MiB and Google OAuth access tokens (security review).
- The receiver refuses requests with an `Origin`, a non-local `Host` or a non-JSON body; URL overrides must be `https` (plain `http` only to loopback).
- APK not built here: this machine lacks Android SDK platform 37 and cannot reach Google Maven; Gradle configuration passed (flavors, conditional Google Services plugin 4.4.4, desugaring). Building the APK is the first step of 0.3-S7b.
