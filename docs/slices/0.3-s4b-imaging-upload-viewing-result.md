## What changed against the plan
- **Edge checks (owner decision, 2026-11-16):** C-STORE into the edge rewrites the DICOM file meta group (group 0002); the dataset after it arrives byte for byte. Edge-path tests compare the cloud copy with the edge copy byte for byte and with the source by SHA-256 of the dataset (`datasetSha256`).
- **Transfers routes:** the plugin (1.7) has no `/transfers/info`; the gateway allows `POST /transfers/push`, `PUT /transfers/push/{id}/{n}`, `POST …/commit`, `DELETE …/{id}` for an edge credential, which may live 12 hours (Orthanc's peer header is fixed at start). One audit row per commit.
- **Push job lost on restart:** with `SaveJobs` on, Orthanc 26.11 does not reload a Transfers push job after `docker restart`; the harness reports it as failed and pushes the study again; the scenario records "resubmitted", not "resumed".
- **OHIF at the origin root:** the release image's webpack public path is `/`, so the gateway proxies OHIF's own `/viewer` route and a strict pattern of its static files at the root, cookie-gated, instead of a `/viewer/` prefix. Pixel data by frames (bulk data URIs off).
- **Test browser:** full Chromium (not the headless shell, which ignores the flag) launched with the gateway origin marked trustworthy, so the `Secure` viewer cookie works over the spike's plain HTTP.
- **Line drops (review B1, owner decision):** a netem cut only stalls TCP and no request failed; scheduled P1 cuts now also end open connections, and the chunked and STOW scenarios assert at least one interruption. Interruptions are counted per interruption (`path#n`), the bound being one chunk re-sent per interruption.
- **Transfers buckets:** the edge uses 512 KB buckets, two at a time; 4 MB buckets, four in parallel, never arrived whole between P1 drops.
- **Cookie name:** `s4_viewer` in the spike (Chromium refuses `__Host-` from plain HTTP); `__Host-` with TLS in production.
- **Generator:** `manifest.json` moved beside the study folder (`<key>/study/`), so the selected folder holds only the study's files.

## Goal
On the P1 profile, an assistant's browser uploads a 300 MB CBCT folder (many files or one multi-frame file) that survives cuts and a page reload without re-sending finished files, and an edge Orthanc pushes the same studies through the gateway with the Transfers plugin, surviving cuts and a restart. A doctor opens the panoramic and the CBCT in an unmodified OHIF through the gateway on P1–P3 and on the edge LAN, first image and MPR. The report answers every spec question with numbers, and ADR-0035 records the decisions.

## Choices made by this plan
- **Browser upload protocols compared:** (1) STOW-RS per instance with retry, the DICOMweb baseline; (2) **our own chunked resumable upload**, chosen over tus. The spec needs server-side state per study, not per file (folder manifest, DICOMDIR filtering, "already complete" no-op, two tabs ending in one copy, resume after a reload with only the folder re-selected). tus (`@tus/server` + `tus-js-client`) resumes one file's bytes and would still need that study manifest beside it, plus its own store and a second protocol to secure at the gateway. Our protocol is four routes on the gateway, so the comparison measures the protocol, not a library.
- **Chunked protocol (throwaway, for the comparison):**
  - `POST /uploads` (role `uploader`) with a manifest `{ files: [{ path, size, sha256 }] }` → `{ uploadId, chunkSize, files: [{ index, received, done }] }`. The upload id is derived from tenant + manifest hash, so a reload or a second tab with the same folder gets the same session and its server-side offsets.
  - `PUT /uploads/{id}/files/{index}` with `Content-Range: bytes a-b/size` and `Digest: sha-256=…` per chunk; the gateway appends only at the current offset (anything else → `409` with the offset), writes to a per-session temp directory and fsyncs before answering.
  - When a file is complete and its SHA-256 matches, the gateway STOWs it to the tenant's Orthanc (internal, unshaped) and marks it `done`; a non-DICOM file fails STOW and is reported as skipped.
  - `GET /uploads/{id}` returns state; `POST /uploads/{id}/finish` verifies every non-skipped file is `done`.
  - Chunk size 1 MiB (8.4 s of P1 uplink, so a cut re-sends at most one chunk per interrupted file); the bench also runs 256 KiB and 4 MiB once.
  - Session rows in `s4.upload_session` / `s4.upload_file` (gateway database from 0.3-S4a), keyed by tenant from the token; temp files deleted on finish.
- **Browser side:** a throwaway page `spikes/s4-imaging/upload-web/` (Vite, vanilla TypeScript) served by the gateway at `/upload/`: folder picker (`webkitdirectory`), DICOMDIR handling with `dicom-parser` (MIT): when a DICOMDIR is present only the files it references are uploaded, others listed as skipped; non-DICOM files (no `DICM` preamble) skipped and listed. SHA-256 per file computed incrementally with `hash-wasm` (MIT) so the 300 MB single file is never held in memory. STOW mode reads SOP Instance UIDs with `dicom-parser` and, after a reload, asks QIDO which instances exist. No state in browser storage (spec: server state only).
- **Edge box:** an edge Orthanc (same official image, SQLite index, `SaveJobs: true`, DicomServer on, DICOMweb on for LAN viewing) on the `clinic` network; studies arrive by `storescu` from the dcmtk container; a peer `cloud` points at the link's gateway frontend with `HttpHeaders: { Authorization: Bearer <edge token> }`; the push is `POST /transfers/push` on the edge (job). The gateway allows, for role `edge` only: `GET /transfers/info`, `POST /transfers/push`, `PUT /transfers/push/{id}/{n}`, `POST /transfers/push/{id}/commit`, `DELETE /transfers/push/{id}` — mapped to the edge token's tenant's Orthanc, audited, and refused for every other role.
- **Viewer:** the official OHIF v3 release image, unmodified; its `app-config.js` and nginx conf mounted (configuration). The gateway serves OHIF under `/viewer/` by proxying the OHIF container and the DICOMweb data source at `/dicomweb` on the same origin. `GET /viewer/session?code=…` exchanges a one-time code (minted by the test as the "application") for the viewer token as an `HttpOnly; Secure; SameSite=Strict; Path=/` cookie; the gateway accepts the cookie for `GET` DICOMweb routes only (STOW and Transfers need the bearer header). For edge LAN viewing a second OHIF container on `clinic` points at the edge Orthanc through its nginx (no gateway, no shaping).

## Plan

### A. Chunked upload on the gateway (criterion 8, server half)
1. `gateway/src/uploads.ts`: the four routes above; offsets in PostgreSQL, bytes on a gateway volume; per-chunk digest check; idempotent re-PUT of an already received range → `200` with the offset; concurrent PUTs on the same file serialised by a row lock (two tabs).
2. Limits: chunk ≤ 4 MiB; manifest ≤ 20,000 files; total ≤ 2 GiB; paths are display-only (never used as file-system paths).
3. Allowlist and audit rows for the new routes (one audit row per finished file, action `upload`).

### B. Upload page and P1 scenarios (criterion 8)
1. `upload-web/src/`: `manifest.ts` (folder → files, DICOMDIR, skip list, hashes), `chunked.ts`, `stow.ts` (per instance, exponential backoff with jitter, max 6 parallel), a status view; built by Vite, copied into the gateway image.
2. `scenarios/` (`@shifa-spike/s4-scenarios`, Playwright `test:spike`): the browser from the `clinic` container (0.3-S4a), `setInputFiles` on the folder input.
3. Two run lengths: `test:spike` uses the 20 MB studies on P1 with cuts every 60 s (fast correctness, about 10 min); `test:spike:long` uses the 300 MB studies on P1 with the spec's cuts (30 s every 5 min; about 45 min per study) and is the evidence for criterion 8.

### C. Edge box (criterion 9)
1. `stack/src/edge.ts`: edge Orthanc and dcmtk containers; `storescu` of a study folder; `pushToCloud(study)` and `jobState()` through the edge's REST API from the test (clinic side, LAN).
2. Restart mid-job: `docker restart` of the edge Orthanc at ~40 % of the job; the job resumes (SaveJobs) or is resubmitted by the test, and the report says which.
3. Byte counters at the link for the push (Transfers gzip) vs the study size.

### D. OHIF viewing (criterion 10)
1. `stack/src/ohif.ts`: OHIF container, mounted config with `dicomWebServer` data source at `/dicomweb`, `supportsWildoc`, `enableStudyLazyLoad`, image loader thumbnails off.
2. Gateway: `/viewer/*` proxy, session exchange, cookie auth on GET routes.
3. `scenarios/viewer.spec.ts`: open `/viewer/viewer?StudyInstanceUIDs=…` for `pano` and `cbct-300-multi`; first image = the viewport canvas has non-background pixels; MPR = switch to the MPR layout (`hangingProtocolId=mpr`) and all three viewports render non-background pixels; timings recorded; on P1, P2, P3 and edge LAN.

### E. Bench (criterion 11)
1. `scenarios/bench/` (`bench:s4`): per profile × study × method (chunked, STOW, edge push): wall time, effective throughput vs link rate, bytes on the wire (link counters) vs study bytes, bytes re-sent after cuts, viewer time to first image and to MPR ready; encryption overhead (same study stored and retrieved with encryption on vs off, unshaped); peak memory of Orthanc and the gateway from the Docker stats stream. The 1 GB study on P1 and P3 at least. Output `.verify/s4/bench.json` (versions, machine, no tags or names). No thresholds.
2. `s4-imaging.yml`: jobs `scenarios` (fast suite) and `bench` (input `profiles`, `studies`; `timeout-minutes: 360`); artifacts `.verify/s4/`.
3. The bench is run once locally on Windows and once by manual CI dispatch after merge (as in 0.3-S2c); P1 × 1 GB alone is about 2.5 hours.

### F. Report, ADR-0035, docs (criterion 12)
1. `docs/spikes/s4-imaging.md`: answer per spec question and per criterion 1–12 with test names and run ids; versions of Orthanc and each plugin, Garage, PostgreSQL, OHIF, Playwright, kernel (netem); the public CBCT's DOI and attribution; tables per profile; STOW vs chunked; Transfers compression; viewer timings; what broke and the workarounds; recommendation on browser upload vs edge box for CBCT clinics.
2. `docs/adr/0035-imaging-storage-upload-and-edge-push.md` (Proposed; Accepted on owner approval): Garage use and version policy, bucket per tenant (or the evidence-backed alternative), object encryption and key handling, the browser upload protocol, Transfers through the gateway with an edge credential. ADR-0019: only its `Status:` line gains `· Amended by ADR-0035`. ADR index.
3. OD-18 gets the bandwidth evidence (stays open for hardware); roadmap S4 row and phase table; `docs/domain/imaging.md` (IMG-02 bucket layout, IMG-14 protocol, IMG-17 Transfers path), `docs/README.md` map if needed.
4. Contracts, real database, API, Flutter: not applicable.
