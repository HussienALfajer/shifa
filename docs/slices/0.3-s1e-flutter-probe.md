# 0.3-S1e Flutter probe for the offline sync spike

Status: In review · Tier: T0 (patient data on devices, encryption at rest, CI infrastructure) · Branch: `chore/0.3-s1e-flutter-probe`
Spec: [0.3-S1 offline sync](../specs/spikes/0.3-s1-offline-sync.md) criterion 11 (verification: Flutter integration test on the pinned toolchain, both engines) · Requirements: PAT-08 · Decisions: [ADR-0012](../adr/0012-flutter-patient-app.md), [ADR-0031](../adr/0031-offline-sync-custom-outbox.md) (Proposed)
Split from [0.3-S1](0.3-s1-offline-sync-spike.md) checkpoint E: 0.3-S1 reached ~5,400 hand-written lines before E (budget ~4,000, [ADR-0032](../adr/0032-slice-size-budget-4000-lines.md)), and its plan named the Flutter probe as the piece to split out. One slice: the estimate below is well under the budget.

## Goal
A thin Flutter probe proves, on both engines, that a patient's cached appointments and ticket are readable in airplane mode, that the local store is encrypted with SQLCipher, that an offline cancellation syncs exactly once, and that logout deletes the store and its key. Its results fill the criterion 11 row of `docs/spikes/s1-offline-sync.md` and confirm or change the patient-app half of ADR-0031 before the owner accepts it.

## Builds on (merged with 0.3-S1, #45)
- Spike server (`spikes/s1-offline/server`): `POST /auth/patient-login` (synthetic patient, device id bound into the token), `GET /sync/pull` (patient tokens: own appointments and tickets of today only), `POST /commands` and `POST /powersync/upload` (a patient may only `appointment.cancel` their own appointment), `GET /report?devices=` (counts only).
- Scenario stack (`spikes/s1-offline/scenarios/harness/stack.ts`): PostgreSQL 18 (`wal_level=logical`), the server in-process, the PowerSync service for `ENGINE=powersync`, Toxiproxy with one proxy per device ("airplane mode" = the device's proxies disabled; with PowerSync a second proxy per device for the sync stream).
- Sync streams (`scenarios/powersync/sync-config.yaml`): `patient_appointments` by `auth.user_id()`. There is **no patient ticket stream** yet, and `ticket.issue` has no `patientId`, so nothing can create a patient's ticket today (see plan, layer 1–2).

## Layout
- `spikes/s1-offline/flutter_probe/`: standalone Flutter package, **not** in the root pub workspace and with no `package.json` (so neither Turborepo nor `verify` runs it; the manual `s1-offline` workflow does). Own `pubspec.lock` (committed), own `analysis_options.yaml` (`very_good_analysis`), tools only through `node scripts/dart.mjs flutter ...` on the `.fvmrc` Flutter. Dependencies at least 24 hours old. The repository-wide 400-line check still covers its `.dart` files.
- Throwaway like the rest of the spike; strings inline in Arabic (RTL), not in `packages/i18n`.

## Plan
1. **Contracts** (spike-local, `server/src/commands.ts`): `ticket.issue` gains optional `patientId` (mirrors `appointment.book`), so a patient's ticket can be issued through the one command handler instead of a direct insert. No change to `packages/contracts`.
2. **Database / sync config** (spike containers only, no migration): the `s1.queue_ticket.patient_id` column already exists; the handler writes it. `sync-config.yaml` gains `patient_tickets` (`tenant_id`, `patient_id = auth.user_id()`, `shift_date = auth.parameter('day')`, `role = 'patient'`), and the `tenant-scoping` spec gains one assertion that patient A's token downloads no ticket or appointment of patient B (same tenant) or of tenant B.
3. **API**: no new routes. `handler/rules.ts` stores `patientId` on `ticket.issue`; a patient token still may not issue tickets (only `appointment.cancel`).
4. **Web**: none.
5. **Flutter** (`flutter_probe/lib/`, each file < 400 lines):
   - `engine.dart`: `ProbeEngine` interface: `open(token)`, `appointments()`, `ticket()` (streams), `cancel(appointmentId)`, `pendingCount()`, `status()` (`online | offline | needs-login`), `close()`, `logout()` (close, delete database files, delete key).
   - `key_store.dart`: `KeyStore` interface; `SecureKeyStore` on `flutter_secure_storage` for the app, `MemoryKeyStore` for host tests. 32 random bytes per install, never logged.
   - `outbox/`: drift database on `sqlite3` built with SQLCipher (the `sqlite3` package's SQLCipher source through build hooks, or `sqlcipher_flutter_libs` if hooks are not usable on Flutter 3.47.9; record which). `PRAGMA key` before any statement; tables `appointment`, `ticket`, `pending_command`, `meta` (cursor). Pull through `/sync/pull?cursor=`; cancel = local status change + queued `appointment.cancel` with a client UUID; flush in order, retry the same ids on network error, keep the queue and report `needs-login` on 401.
   - `powersync/`: `powersync_sqlcipher` with the same key; schema for `appointment` and `ticket`; connector (`fetchCredentials` = patient login, `uploadData` → `/powersync/upload`, retry on network error, stop on 401); drift through `drift_sqlite_async` if it works on the pinned Flutter, else plain `sqlite_async` queries (record which and why). `logout()` = `disconnectAndClear()`, close, delete files and key.
   - `main.dart` + `probe_screen.dart`: one Arabic RTL screen: my appointments (cancel button), my ticket (number, status), pending badge, offline banner. Engine chosen by `--dart-define=S1_ENGINE`.
   - No logging of tokens, ids beyond counts, or row values (console included).
6. **Launcher and CI** (`scenarios/harness/probe.ts`, script `probe` in `@shifa-spike/s1-scenarios`):
   - Starts the stack for one engine without building the web prototype (`startStack` gains a `{ prototype: false }` option), adds proxies `probe-a` (and `probe-a-ps`), seeds through `POST /commands` with the synthetic receptionist: two of today's appointments and one ticket for one synthetic patient, plus one appointment and one ticket for a second patient (must never reach the device).
   - Runs `node scripts/dart.mjs flutter test` in `flutter_probe/` with `--dart-define`s: engine, proxied server URL, proxied PowerSync URL, Toxiproxy API URL, direct server URL (for `/report`), patient id, second patient's appointment id, device id. Exits with Flutter's code; stops the stack always.
   - `s1-offline.yml`: the `flutter` job (input `flutter: true`, matrix `outbox | powersync`, respects the `engine` input), installs the pinned Flutter the way `ci.yml` does (`FLUTTER_VERSION` + `FLUTTER_SHA256`, no SDK cache, OD-35), pinned actions, `permissions: contents: read`, uploads a counts-only summary.
7. **End-to-end**: the four tests below run against the real stack on both engines; the owner's manual checklist is not extended (the probe has no manual run in the spec).

## Tests written first (red before the engines exist)
`flutter_probe/test/`, each one run for the engine named by `S1_ENGINE`, against the launcher's stack:
- `cache_offline_test.dart` — log in, sync, both appointments and the ticket visible; cut the device's proxies; close the engine and open a new one with the same key (restart) → same appointments and ticket readable, status `offline`; the second patient's rows are absent (criterion 11, PAT-08, criterion 10 on the device).
- `encryption_test.dart` — after a sync: opening the file with no key or a wrong key fails; the raw file bytes contain no known synthetic value (the ticket's walk-in label and an appointment id); `PRAGMA cipher_version` returns a version (criterion 11).
- `cancel_sync_test.dart` — offline: cancel one appointment → shown cancelled, pending 1; one failed flush while still cut; reconnect → pending 0; `/report` for the device shows exactly 1 command, 1 applied; a fresh pull shows the appointment cancelled; cancelling the second patient's appointment id is `refused` and changes nothing (criterion 11, SCH-13).
- `logout_test.dart` — logout → database file (and `-wal`/`-shm`) gone, key gone from the `KeyStore`; a new engine starts empty.
- Launcher (`scenarios/tests/harness.spec.ts`, extended): every image still digest-pinned; `startStack({ prototype: false })` builds nothing.
- Server (`server/test/queue-numbers.test.ts` or a new `patient-ticket.test.ts`): `ticket.issue` with `patientId` stores it; a patient token issuing a ticket is `refused`.

Red proof: a stub engine that stores plain SQLite (no key) fails `encryption_test`; one that drops the queue on restart fails `cancel_sync_test`.
