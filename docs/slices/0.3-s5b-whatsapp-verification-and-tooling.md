# 0.3-S5b WhatsApp spike: reverse verification, separation, manual-run tooling

Status: Built (in review) · Tier: T0 (phone verification is authentication; tenant and role separation of inbound messages) · Branch: `claude/whatsapp-verification-tooling-docs-ar2pd7` (cloud session branch, `docs/process/cloud-sessions.md` §4; planned as `chore/0.3-s5b-whatsapp-verification-and-tooling`)
Spec: [0.3-S5 WhatsApp](../specs/spikes/0.3-s5-whatsapp.md) criteria 9, 10, 11 (tooling) · Requirements: MSG-08, MSG-09, MSG-12, MSG-20, MSG-22, MSG-24 (rate limits), MSG-32 · Decisions: ADR-0016, ADR-0017, ADR-0023, ADR-0026, OD-23, OD-31, OD-45, OD-46
After [0.3-S5a](0.3-s5a-whatsapp-stack-and-sending.md); before [0.3-S5c](0.3-s5c-whatsapp-manual-day-and-result.md). Built in three checkpoints (A–C).

## Goal
A patient's phone is verified only by a code the patient sends to the platform number, never by a code sent to them; inbound messages never cross clinics or roles; and the owner has a page, a script and a checklist to run one day on real WhatsApp safely.

## Choices made by this plan
- **Code:** 6 characters from an alphabet without look-alikes (no `0/O`, `1/I/L`), after a fixed Arabic phrase in the prefilled text (`رمز التحقق في شفاء: K7Q4MX`); matching takes the first code-shaped token after folding digits and case, so extra text and Arabic-Indic digits pass (changed after the security review: the code must follow the phrase, see "As built"). The lookup key is `HMAC(serverKey, normalisedCode)`; the plain code is never stored.
- **Nonce:** id of at least 128 random bits, bound to `deviceId` and the claimed E.164 number; returned with a device secret that `GET /verify/:nonceId` requires; 10-minute TTL; single use. A code from a sender other than the claimed number is refused (`sender_mismatch`) and does not consume the nonce. Edits, revokes and reactions never count as a code.
- **Rate limits:** 5 nonce requests and 5 failed matches per device and per number per hour, kept in the spike database. The per-number limit lets a stranger block a victim's number for an hour; the report states this trade-off.
- **Platform never initiates:** the platform session's only send function takes `replyTo: inboundMessageId` whose inbound arrived within 10 minutes on that session, and replies only on a successful verification (strangers cannot make it send); replies pass the MSG-32 allowlist. A test checks every outbound recorded on the platform session.
- **Forwarded-link attack:** a victim could be tricked into sending an attacker's prefilled code; the fixed phrase names Shifa and the action. The report and ADR-0036 record the residual risk.
- **Unresolvable `@lid`:** verification fails closed (`lid_unresolved`), resolved only through the container that received the event.
- **Device side:** `messaging/scripts/device.ts` plays the app: requests a nonce, prints the `wa.me` link (in tests, the fake delivers the message), polls until verified, refused or expired. No websocket in the spike.
- **Manual-run tooling:** a local admin page served on `127.0.0.1` only (QR proxied from WAHA on request, never written to disk or logs; session state; buttons for the checklist steps; "resume" after a breaker pause), plus `scripts/manual-run.ts` for the paced batch. The owner's two numbers live in git-ignored `spikes/s5-whatsapp/.env.local` and form the allowlist. During the run, raw webhook bodies and headers go only to git-ignored `.cache/s5/raw/`; `scripts/scrub-fixtures.ts` maps every number, LID, JID, message id, push name and body to stable placeholders, keeps a recomputed signature check result per fixture, writes `spikes/s5-whatsapp/fixtures/*.json`, and deletes the raw files. A check fails on any digit run of 8 or more in committed fixtures that is not a synthetic number.

## Plan

### A. Reverse verification (criterion 9)
1. `messaging/src/verify.ts`: `POST /verify/nonce {deviceId, phone}` → `{nonceId, deviceSecret, waLink, expiresAt}`; platform inbound handler matches code + sender, marks verified, replies "تم التحقق" in the same chat; `GET /verify/:nonceId` for polling.
2. Failure reasons (`expired`, `wrong_device`, `sender_mismatch`, `reused`, `rate_limited`, `lid_unresolved`) recorded per attempt without the number.

### B. Tenant and role separation (criterion 10)
1. Platform session in `waha-platform`, clinic sessions in `waha-clinics`; (container, session) → role and clinic is the only routing key.
2. A code sent to a clinic number is an ordinary inbound (opt-in for that clinic) and never verifies; inbound on clinic A never touches clinic B.

### C. Manual-run tooling and checklist (criterion 11, preparation)
1. Admin page, `manual-run.ts`, raw capture, scrubber and fixture check.
2. `docs/spikes/s5-manual-checklist.md`: the owner's steps with expected results and blanks for timestamps and error codes: link G as platform; P verifies (once plain, once with extra text and Arabic-Indic digits); unlink, link G as clinic; P opts in; 20–40 messages over the day with all controls on (real gaps, cap 30 per rolling hour, quiet hours); acks; P sends "إيقاف", then a normal message; restart `waha-clinics` with no new QR; G's phone offline for an hour while sending; unlink and re-link G; record any 463/475/warning; grep both WAHA containers' logs for G, P, codes and the QR before the scrub; run the scrub.

## As built
- `messaging/src/verify.ts` (nonce, polling, matching), `verify-code.ts` (code, HMAC keys, link), `platform-reply.ts` (the platform's only send), `topology.ts` (config refuses a platform session sharing a container with clinics, a platform session with a clinic, a clinic session without one, two platform sessions), `device.ts`, `raw-capture.ts`, `scrub.ts`, `env-local.ts`; schema tables `verify_nonce`, `verify_attempt`, `platform_inbound`, `platform_outbound`.
- Codes: alphabet `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (31 symbols, about 29.7 bits for 6 characters). **Changed after the security review (owner, 2026-11-17):** a code counts only right after the fixed phrase (folded: case, Arabic-Indic digits, tashkeel; extra text around it passes), so a disguised message such as `أؤكد موعدي رقم K7Q4MX` never verifies; the success reply names the action and tells a patient who did not ask to contact the clinic. An unknown code after the phrase is recorded as `no_match` (needed for the failure limit; not in the plan's list). Failed matches count against the sender's key (or its chat when an `@lid` is unresolved), the nonce's claimed number and its device, serialised per sender; `rate_limited` itself does not count, so a refused retry does not extend the lock.
- The platform reply goes to the chat that wrote (an `@lid` chat stays `@lid`) with WAHA `reply_to`; a valid code from a number not on the allowlist verifies but gets no reply (MSG-32, recorded as `refused: allowlist`).
- The admin page lives in `messaging/tools/` (re-exported by `src/admin-page.ts`): 0.3-S5a's `breaker.test.ts` keeps `src/` free of any start, QR or logout call, and only the owner starts, links or fetches a QR, from this page. Served on `127.0.0.1` with a per-run token (URL fragment, `x-admin-token` header), a Host check, `no-store` and a CSP; the QR is proxied (`format=raw` JSON or `format=image`) and never stored.
- `messaging.listen(port, host)` can bind the address the run's WAHA containers reach; an empty or unspecified address (`''`, `0`, `0.0.0.0`, `::`) is refused, and `.env.local` treats empty values as unset.
- Start-up refuses session rows in a kept database that differ from the configuration, and container keys that are not distinct.
- `manual-run.ts serve` registers P (`c-run`/`p-owner`) at start, so P's first message records the opt-in; the admin page's start creates the session when WAHA does not know it, and the page shows opt-in and alert counts.
- Scrubber (rewritten after the security review): an allow-list of structural fields keeps its shape with numbers, LIDs, groups and message keys mapped; every other string becomes `text-N`, other numbers 0, and `_data`, vCards, location, media and quotes are dropped. The check refuses non-synthetic 8+ digit runs (spaces, dashes and Arabic-Indic digits included, ISO times excepted), non-placeholder strings outside structural fields and long numbers outside named time fields, and never prints the digits it found. It runs in the manual `s5-whatsapp` workflow and after every scrub; not in `verify`, because OD-31 keeps spike suites out of it (`scripts/test` refuses a `test` script in a spike package). A raw capture that cannot be written no longer fails the webhook.
- `breaker.test.ts` (0.3-S5a) now also checks that only `src/admin-page.ts` reaches `tools/` and that `index.ts` does not export it.
- The fake records `reply_to` of `sendText`; `s5-whatsapp.yml` names the new suites and runs `scripts/check-fixtures.ts`.
- Checklist: `docs/spikes/s5-manual-checklist.md`. Step 4 tests expiry instead of a third sender: the owner has two numbers and G cannot write to itself; the third-number case stays with the suites. Step 17: the owner reads every fixture before it is committed.
- Not fixed here (in `docs/backlog.md`): raw capture before the signature check (pinned by the locked scrubber test), the per-number lockout and client-chosen device ids (Phase A, ADR-0036), raw captures inside the tree, plain numbers in `platform_inbound`.
