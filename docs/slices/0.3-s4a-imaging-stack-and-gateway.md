# 0.3-S4a Imaging spike: stack, encrypted Garage storage, link shaper, test data, gateway isolation

Status: Built (in review) · Tier: T0 (tenant isolation at the imaging gateway, encryption at rest, infrastructure; throwaway code, no real-schema migration) · Branch: `chore/0.3-s4a-imaging-stack-and-gateway`
Spec: [0.3-S4 Imaging](../specs/spikes/0.3-s4-imaging.md) criteria 1–7 · Requirements: IMG-01, IMG-02, IMG-03, IMG-04, IMG-06, IMG-25 · Decisions: ADR-0019, ADR-0021, ADR-0023, ADR-0026, OD-31, OD-44

The spike is split in two by the ~4,000-line budget of [ADR-0032](../adr/0032-slice-size-budget-4000-lines.md): this slice builds everything the measurements stand on (pinned stack, storage, the link shaper, the data generator, the gateway's isolation); [0.3-S4b](0.3-s4b-imaging-upload-viewing-result.md) adds upload over the link, the edge box, OHIF, the bench, the report and ADR-0035. Built in six checkpoints (A–F); each ends green and committed, and "Stopped at" names the last one.

## Goal
A developer starts, with one command, a pinned imaging stack on Testcontainers: two tenants, each with its own unmodified Orthanc writing encrypted objects to its own Garage bucket, reachable only through a throwaway gateway that refuses by default, checks short-lived tokens, keeps tenants apart and audits every access. A link-shaper container applies the P1–P3 profiles to every clinic-side byte. A generator writes realistic-size synthetic CBCT and panoramic studies, and a pinned script fetches one public de-identified dental CBCT. Every claim of ADR-0019 that does not need the slow link is proven by a test.

## Choices made by this plan
- **Link shaper: `tc netem` + `tbf` in a "link" container, not Toxiproxy.** Toxiproxy (used in 0.3-S1) shapes bandwidth per TCP connection, so a browser with six connections would get six times the profile's uplink, and it has no packet loss. The link container (`alpine` pinned by digest + `iproute2` + `haproxy`, `NET_ADMIN` capability only on this container) sits on both the `clinic` and the `cloud` Docker networks; clinic-side clients connect to it and HAProxy (TCP mode) forwards to the gateway. Egress shaping on the cloud-side interface is the uplink, on the clinic-side interface the downlink, so the rate limits are aggregate across connections. Loss and jitter come from `netem`; a cut is `netem loss 100%` for 30 s (connections stall as on a real line drop), and a separate "reset" cut restarts HAProxy (connections die, as on a mobile handover). Byte counters per direction come from `/sys/class/net/<if>/statistics`. Checkpoint B starts with a gate test that `sch_netem` and `sch_tbf` load in Docker Desktop's and the CI runner's kernel; if either is missing the session stops and asks the owner (fallback: Toxiproxy with one connection per client, recorded as a limit).
- **Browser placement:** the browser runs in a pinned `mcr.microsoft.com/playwright` container on the `clinic` network (`playwright run-server`; tests use `chromium.connect()` with the same Playwright version as the workspace), so its only route to the cloud is the link container. Used from 0.3-S4b; the container and a smoke test land here.
- **Public CBCT (OD-44):** the adult dental CBCT dataset for missing-teeth detection on Science Data Bank, DOI `10.57760/sciencedb.26465` (158 de-identified cases, DICOM per patient folder, data licence CC BY 4.0 in the article's Data Availability statement; the article itself is CC BY-NC-ND 4.0, which does not govern the data). One case (smallest KaVo or NewTom volume that is still a full arch) is fetched by `scripts/fetch-public-cbct.ts`, each file pinned by SHA-256, into the git-ignored `.cache/s4/public-cbct/`, never committed. Checkpoint D first confirms on the record page that the licence shown is CC BY 4.0 and that one case downloads without an account; if either fails, stop and ask the owner (do not pick another dataset alone). Attribution goes into the report.
- **Gateway in a container:** Orthanc must have no published port, so the gateway (`node:24-slim` pinned, running the TypeScript sources with Node's type stripping) runs on the `cloud` and `orthanc` networks. Orthanc, PostgreSQL and Garage are only on the internal `orthanc` network.
- **Token:** HS256 JWT signed by a per-run key (`jose`), claims `sub`, `tenant`, `role` (`viewer` | `uploader` | `edge`), `exp` ≤ 5 min; the viewer gets it as an `HttpOnly; Secure; SameSite=Strict` cookie through a one-time exchange in 0.3-S4b and as a bearer header in tests.
- **Mounts into Orthanc (criterion 2):** configuration JSON and the storage master-key files only (keys are data, not code); the check refuses every other file, every `.py`/`.lua`/`.so`, and any `ORTHANC__PYTHON_*`, `LUA_SCRIPTS` or extra plugin path in the environment.

## Layout
- `spikes/s4-imaging/stack/` (`@shifa-spike/s4-stack`): Testcontainers harness (`src/stack.ts`, `src/images.ts`, `src/garage.ts`, `src/orthanc.ts`, `src/link.ts`, `src/networks.ts`) and the storage tests. Suites are `test:spike` only (OD-31); typecheck and lint run in `verify`.
- `spikes/s4-imaging/link/` (kept for Phase D): `Dockerfile`, `haproxy.cfg`, `profiles.json` (P1–P3 exactly as the spec table), `apply-profile.sh`.
- `spikes/s4-imaging/generator/` (`@shifa-spike/s4-generator`, kept for Phase D): DICOM writer and CLI.
- `spikes/s4-imaging/gateway/` (`@shifa-spike/s4-gateway`): Fastify 5 + `undici` proxy, `Dockerfile`.
- Spike state (audit lines, later upload sessions) in its own database `s4_gateway` on the stack's PostgreSQL, schema `s4`, created by the harness, never in `packages/db/migrations`. The gateway is its only client; every query takes the tenant from the verified token. These tables are not reached through `withTenant()`, so they carry `tenant_id` but no RLS; the report records that the Phase D design puts imaging audit into the main audit log (IMG-25).
- `.github/workflows/s4-imaging.yml`: `workflow_dispatch` only, `permissions: {}`, actions pinned by SHA like `s3-arabic-output.yml`; job `stack` runs `test:spike` for stack, generator and gateway.

## Plan

### A. Pinned stack and network boundary (criteria 1–2)
1. `src/images.ts`: every image `name:version@sha256:<digest>`, each release at least 24 hours old: `orthancteam/orthanc` (latest stable; must contain the PostgreSQL index, AWS S3 object-storage, DICOMweb, Transfers and GDCM plugins, checked at start through `/plugins` from the gateway network), `postgres:18.x`, `dxflrs/garage:v2.x`, `ohifviewer`/`ohif/app` v3 release (used in S4b), `mcr.microsoft.com/playwright:v1.65.1-noble`, `alpine` (link base), `node:24-slim` (gateway base), a `dcmtk` image built from `debian:trixie-slim` pinned (used by S4b's `storescu`).
2. `src/networks.ts`: three networks `clinic`, `cloud`, `orthanc` (`internal: true`). `src/stack.ts` `startStack({ tenants: ['a','b'], profile })` starts PostgreSQL (databases `orthanc_a`, `orthanc_b`, `s4_gateway`, one role per database), Garage, one Orthanc per tenant, the gateway and the link; returns URLs as seen from the clinic side and a teardown that also deletes per-run keys.
3. Orthanc configuration is generated per tenant as JSON (`src/orthanc.ts`): PostgreSQL index and storage-less (`EnableStorage: false`), `AwsS3Storage` with the tenant's bucket, endpoint, `VirtualAddressing: false`, per-tenant credentials and `StorageEncryption` (master key ids and files), `DicomWeb` enabled, `Transfers` enabled, `RemoteAccessAllowed` with HTTP basic auth (per-run password known only to the gateway), `DicomServerEnabled: false` in the cloud.
4. Logs: Orthanc `--verbose` off; gateway logs route, status, tenant, timing; never tags, tokens or keys.

### B. Link shaper (profiles P1–P3; used by 0.3-S4b criteria 8–11)
1. `link/Dockerfile` + `haproxy.cfg` (TCP mode, `timeout tunnel 1h`, one frontend per forwarded service: gateway, later edge peer target).
2. `apply-profile.sh <profile>`: `tc qdisc replace dev <cloud-if> root handle 1: tbf rate <up> burst … latency …` + child `netem delay <rtt/2> <jitter/2> loss <loss>`; the same on the clinic interface with the down rate; P2 and P3 without loss. RTT is split evenly per direction.
3. `src/link.ts`: `applyProfile(p)`, `cut(seconds)`, `reset()`, `counters() → { upBytes, downBytes }`, `schedule(P1 cuts: 30 s every 5 min, starting offset configurable)`; the profile and every cut are logged with timestamps for the report.

### C. Garage and Orthanc storage (criteria 3–5)
1. `src/garage.ts`: per run, `garage layout assign` + `apply`, then per tenant `bucket create s4-<tenant>`, `key create`, `bucket allow --read --write --owner`; credentials held in memory only.
2. Tests through each tenant's Orthanc (from the gateway network, as the gateway would): store a generated study, read every instance back, delete the study, list the bucket.
3. Shared-bucket variant (recorded, not adopted): one bucket, two keys, prefixes `a/` and `b/` via the plugin's `RootPath`; the test shows whether Garage can restrict a key to a prefix (Garage grants per bucket, so the expected result is "no", which the report states with the test as evidence).

### D. Test data (criterion 7)
1. `generator/src/dicom.ts`: writes DICOM Part 10 with `dcmjs` (MIT): Explicit VR Little Endian, uncompressed, 16-bit signed CT/CBCT, patient and study tags from `@shifa/testing` synthetic Arabic names with a fixed marker in `PatientName` (e.g. the prefix `S4SYN^`) for the log scan; a deterministic phantom (skull-like ellipses, teeth-like dense cylinders) plus seeded Gaussian noise so compression ratios are realistic.
2. Studies: `cbct-300-multi` (≈ 300 MB, one file per slice, e.g. 512 × 512 × 576), `cbct-1g-multi` (≈ 1 GB, e.g. 800 × 800 × 800), `cbct-300-single` (one Enhanced CT multi-frame file ≈ 300 MB), `pano` (one DX image ≈ 3000 × 1500, 16-bit); every file listed in `manifest.json` with SHA-256 and SOP Instance UID. A small `cbct-20-multi` and `cbct-20-single` (≈ 20 MB) feed fast tests here and in 0.3-S4b. A `with-dicomdir` variant adds a DICOMDIR (dcmjs or `dcmmkdir` from the dcmtk image) and one non-DICOM file. Output under the git-ignored `.cache/s4/studies/`; the generator is deterministic (same seed → same SHA-256).
3. `scripts/fetch-public-cbct.ts`: downloads the pinned files, verifies each SHA-256, refuses on mismatch, writes `.cache/s4/public-cbct/` and a `SOURCE.md` (DOI, licence, attribution).
4. PHI check: every file of the public case parsed with `dcmjs`; each tag in the patient/study identity set (Patient's Name, ID, Birth Date, Sex is allowed, Other Patient IDs, Address, Telephone, Institution, Referring Physician, Accession Number, Study/Series dates when they look real, device serial numbers) must be empty, absent or a recognised placeholder; the test fails and lists tag keywords (not values) otherwise.

### E. Gateway isolation and audit (criterion 6)
1. `gateway/src/server.ts`: Fastify; routes only from an allowlist table: QIDO-RS (`GET /dicomweb/studies`, `/studies/{s}/series`, `/…/instances`), WADO-RS (`GET` study/series/instance/frames/metadata/rendered), STOW-RS (`POST /dicomweb/studies`, role `uploader`); everything else 404 before any upstream call. Tenant → upstream map from the token's `tenant` claim only; URL tenant hints are ignored. Upstream path rewrite `/dicomweb/*` → `/dicom-web/*` with Orthanc basic auth added by the gateway; responses streamed (no buffering of WADO frames).
2. `gateway/src/auth.ts`: `jose` verify (`HS256`, algorithm pinned, `exp` required, clock skew ≤ 30 s), roles per route.
3. `gateway/src/audit.ts`: one row per allowed request in `s4.audit(id, at, actor, tenant_id, study_uid, action, route_class, status)`; `study_uid` parsed from the path or, for STOW, from the response; nothing for refused requests beyond a counter.
4. Request body limits: STOW up to the largest generated instance + margin; no other route takes a body.

### F. Workflow and checkpoint report
1. `.github/workflows/s4-imaging.yml` job `stack` (from S4a), with `timeout-minutes` and a disk-space step (the 1 GB study is not generated in this job).
2. "As built", "Stopped at" and Evidence in this file; the generator and link profiles described in `docs/domain/imaging.md` under a short "Spike tooling" note for Phase D.

## Tests written first
- `stack/test/images.test.ts` (1): every image constant matches `name:version@sha256:<64 hex>`; each running container reports its pinned version; Orthanc `/plugins` (from the gateway network) lists exactly the five required plugins plus the official image's defaults that are disabled.
- `stack/test/network.test.ts` (1): from a container on `clinic` (the browser container), TCP connects to every Orthanc's 8042 and 4242, PostgreSQL 5432 and Garage 3900/3901/3903 by service name and by IP all fail; the gateway through the link succeeds.
- `stack/test/licence-boundary.test.ts` (2): container inspect of every Orthanc: mounts are only `*.json` config and key files; no `.py`, `.lua`, `.so`; no scripting or extra-plugin env; a deliberately added `extra.lua` mount makes the check fail (negative evidence, in the test).
- `stack/test/garage-roundtrip.test.ts` (3, IMG-06): store `cbct-20-multi` and `pano`, retrieve each instance by WADO (from the gateway network), SHA-256 equals the manifest; delete the study → bucket listing has no object of it; Orthanc storage statistics back to zero.
- `stack/test/encryption.test.ts` (4): every object in the bucket lacks `DICM` at offset 128 and anywhere, and lacks a 64-byte pixel run copied from the source; an Orthanc restarted with a different master key fails to read the instance (error, not wrong bytes); restarted with the right key reads it.
- `stack/test/tenant-buckets.test.ts` (5, IMG-02): tenant A's key gets `AccessDenied` on list/get/put to `s4-b`; the shared-bucket prefix variant result is written to `.verify/s4/bucket-layout.json`.
- `stack/test/link.test.ts`: `sch_netem`/`sch_tbf` load (gate); with P2, a 5 MB upload through the link takes 5 MB / 3 Mbps ± 15 %, and six parallel uploads together take about six times as long (aggregate shaping); RTT measured within ± 20 % of the profile; a 30 s cut stalls and then resumes a transfer; counters match bytes sent ± 2 %.
- `generator/test/generator.test.ts` (7): sizes within ± 5 % of target, frame counts, 16-bit signed, tags valid (dcmjs round-trip), synthetic name marker present, same seed → same hashes, DICOMDIR references exactly the image files.
- `generator/test/public-cbct.test.ts` (7): SHA-256 pin of each file; PHI tag check passes on the sample and fails on a generated file with a filled `PatientBirthDate` (negative evidence).
- `gateway/test/isolation.test.ts` (6, IMG-03): the same generated study (same UIDs) STOWed by A and by B → two studies, one per Orthanc; with A's viewer token: QIDO lists only A's, WADO on B's UIDs is 404 (same answer as for an unknown UID), STOW lands in A; tokens: expired, wrong key, `alg: none`, missing `tenant`, unknown tenant, wrong role for STOW → 401/403 with no upstream call (upstream request counter unchanged).
- `gateway/test/denylist.test.ts` (6): `/tools/*`, `/system`, `/instances`, `/plugins`, `/jobs`, `/patients`, `/studies` (Orthanc REST), `/dicom-web/*` (upstream spelling), path traversal (`/dicomweb/../system`, encoded `%2e%2e`), `OPTIONS`/`DELETE`/`PUT` on allowed paths → refused, no upstream call.
- `gateway/test/audit.test.ts` (6, IMG-25): every allowed call writes exactly one audit row with actor, tenant, study, action; refused calls write none.
- `gateway/test/no-phi-in-logs.test.ts`: after the suites, gateway and Orthanc container logs contain no `S4SYN` marker, no token prefix (`eyJ`) and no key material.

## As built (differences from the plan)
- **Gates (2026-11-16):** `sch_tbf` + `sch_netem` load on Docker Desktop's WSL2 kernel 6.6.87.2 (the CI runner's kernel is checked by the workflow's first step and by `link.test.ts`). The Science Data Bank record shows **CC BY 4.0** and downloads need no account; but the DICOM is one 23.5 GB ZIP (`Dataset_repaired.zip`), not per-case files. The server honours HTTP ranges, so `fetch-public-cbct.ts` reads the ZIP64 central directory once (`--pin`) and then only the chosen case's entries (local header + data, inflated); each file is pinned in `generator/public-cbct.lock.json` with its SHA-256 and ZIP offset, and the total ZIP size is checked on every range. Case: **NewTom N09** (510 slices, 268 MB), the smallest NewTom case (KaVo cases are ≥ 328 MB). A request per entry tripped the server's rate limit (HTTP 429): the case is read as one contiguous span in 32 MB ranges. Its real dates are replaced with `19000101` in place (`generator/src/deidentify.ts`, owner decision under OD-44); the lock pins both the published and the cleared SHA-256.
- **Harness on the docker CLI, not Testcontainers:** Testcontainers cannot create `--internal` networks or start a container on several networks; the CLI can. Every container and network carries the label `shifa.s4.run=<id>`; `S4_KEEP=1` keeps a failed run for `docker logs`. Secrets reach containers as `-e NAME` with the value only in the CLI's environment.
- **Test access to the cloud side:** an opt-in `ops` container (the link image with another HAProxy config) on the internal `orthanc` network and its own bridge, publishing Orthanc A/B, Garage S3 and PostgreSQL on `127.0.0.1` only. "From the gateway network" in the plan means this. `network.test.ts` runs without it.
- **Orthanc plugins:** `/plugins` lists `AWS S3 Storage`, `dicom-web`, `gdcm`, `postgresql-index`, `transfers`, plus `postgresql-storage` (the image loads both libraries of the PostgreSQL plugin; `EnableStorage: false`) and `explorer.js` (the core's explorer entry, not a plugin). OrthancExplorer2 off. `IndexConnectionsCount: 10` per tenant (the default pool exhausted PostgreSQL's 100 slots); PostgreSQL runs with `max_connections=200`.
- **Licence check** also reads each mounted JSON and refuses `PythonScript`, `LuaScripts`, `Plugins`; the image's own `PYTHONUTF8` is not a scripting variable.
- **Garage keys** get `--read --write` on their bucket, not `--owner` (Orthanc never manages buckets).
- **Gateway:** upstream error bodies are replaced by fixed ones (Orthanc's 404 names the UID); an empty QIDO answer becomes `204 No Content` (PS3.18 allows it), so another tenant's study and an unknown one answer alike on every route. Every forwarded request is audited with its upstream status, not only the 2xx ones. The image is built from the sources plus a flattened copy of the production dependencies (`stack/src/build.ts`): pnpm's links do not survive a Docker build context on Windows.
- **Link:** loss applies per direction; jitter uses `distribution normal`. The counters test allows payload … payload × 1.06 (TCP/IP and Ethernet framing), not ± 2 %. Six parallel 1 MB uploads are compared with the rate for 6 MB (aggregate shaping) to keep the suite short.
- **Generator:** the PHI check covers the plan's tag set (not `StudyID`); synthetic files pass through the `S4SYN` marker. The 300 MB and 1 GB studies are checked by plan (pixel bytes) here; 0.3-S4b generates them for the bench.
