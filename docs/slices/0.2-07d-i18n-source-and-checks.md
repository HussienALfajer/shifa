## Goal
`packages/i18n` is the one translation source for web (i18next with ICU) and Flutter (ARB generated from it). CI fails when a message is not valid ICU, when an error code has no Arabic message, when locales disagree on keys, or when the generated ARB and typed keys are stale.

## Plan
1. **Contracts.** Read-only: `ErrorCode` from `packages/contracts`.
2. **Package** (`packages/i18n`):
   - Source: `src/locales/ar/<namespace>.json` (ICU MessageFormat), namespaces `common` and `errors` to start. Arabic is the only locale now; the checks already handle more (Turkish is OD-16, after Release 1).
   - `errors.json` has one key per `ErrorCode` with a short Arabic message (synthetic copy, reviewed by the owner in the PR).
   - Generator `scripts/generate.ts` writes `generated/keys.ts` (typed key union per namespace, for i18next typing later) and `generated/arb/app_ar.arb` (Flutter `gen-l10n` input; ICU plural/select kept, placeholders declared). Registered with the drift runner as `i18n`.
3. **Checks** (`test/`, part of the package's `test` task):
   - every message parses with `@formatjs/icu-messageformat-parser` (pin ≥ 24 h old);
   - Arabic plurals: a message with `plural` must cover `zero one two few many other` (Arabic CLDR categories);
   - every `ErrorCode` has `errors.<code>`, and no `errors.*` key lacks a code;
   - key parity and identical placeholder sets across locales (exercised with a fixture second locale);
   - no empty strings, no Latin-only Arabic values (heuristic: an `ar` value must contain an Arabic letter, except keys listed in an allow-list such as brand names).
4. **API / database / web / Flutter.** None (consumers arrive with the first web app and the patient app).
5. **Instructions.** `packages/i18n/CLAUDE.md` (where keys go, ICU rules, never hard-code UI strings); `.claude/rules` path rule if one exists for UI code by then.
