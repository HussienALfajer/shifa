## Goal
The probe has run on two Android emulators (API 33 and the newest stable API) against the production Firebase project's spike Android app; every state of criterion 4 has 20 measured sends, the deprioritisation and pending-limit runs are recorded, and the one-day run is done. An analysis script computes the OD-52 pass mark from the logs. The report `docs/spikes/s7-push.md` answers the four spec questions with versions and numbers and carries the battery guide draft; ADR-0038 records the send policy, device-state reporting, inbox rule and pass mark.

## Choices made by this plan

### Measuring "shown"
- **Source of truth:** a host-side watcher polls `adb shell dumpsys notification --noredact` every second and records each posted notification of the probe's package with its `postTime` and the `s7id` from the notification extras; this works in every app state, including those where no app code runs. The probe's own log (0.3-S7a) is the second source and is used for app state and the inbox join.
- **One clock:** latency = shown (emulator clock) − sent (host clock), corrected by the skew measured with `adb shell date +%s%N` against the host before and after each run (both recorded; a drift over 50 ms in a run is flagged).
- **Lost:** a send with neither a shown record nor an inbox fetch that contains it after the run's reconnect window.

### Scenario runner (criteria 4–6)
- `spikes/s7-push/scenarios/` (`@shifa-spike/s7-scenarios`): `run --state <name> --serial <emulator> [--count 20] [--gap-s 30]`; each state is a small module with `setup`, `between`, `teardown` written as `adb` commands (for example `dumpsys deviceidle force-idle`, `am set-standby-bucket <pkg> rare|restricted`, `am force-stop`, `svc wifi disable` and `svc data disable`, `cmd notification` channel changes or the app-settings path, `pm revoke … POST_NOTIFICATIONS`, reboot with `adb wait-for-device` and no app launch).
- **Network:** offline states use `svc wifi/data`; the slow link uses the emulator console (`network speed` and `network delay`) with one recorded profile (default `gsm` speed and `edge` delay, the closest built-in profiles to a weak Syrian mobile link; values recorded).
- **Offline 10 minutes:** two variants, TTL longer than the outage and TTL ending inside it; both with collapse on (expect one shown per appointment) and the second also with collapse off.
- **Deprioritisation (criterion 5):** the `noshow` flavor receives high-priority data-only messages it never displays, on its own emulator, for the same schedule as the compliant instance; delivery of a later visible message is compared. Result recorded, not graded.
- **Pending limit (criterion 6):** 120 non-collapsible messages to an offline emulator, reconnect, record what arrives and whether FCM signals deleted messages (`onDeletedMessages`, logged by the probe); then the collapsed variant.
- **Fake `adb`:** tests run the runner against a recorded-command fake, so CI checks the commands without an emulator.

### One-day run (criterion 7)
- `scenarios/run-day.ts` sends one push every 15 minutes from 08:00 to 21:00 local time (53 sends) to both emulators, forcing Doze (`deviceidle force-idle`) between sends and stepping out of it only by the push; the machine must not sleep (owner keeps it awake). Emulator images: API 33 and the newest stable API, system image versions recorded.
- **Aggregated Delivery Data:** pulled once before the report closes through the FCM Data API (`fcmdata.googleapis.com`, `androidApps/<id>/deliveryData`) with the owner's own `gcloud` token, not the send-only service account; an empty answer is recorded as such (the data lags up to 5 days).
- **Network and country:** the owner states the machine's network and country; recorded as given.

### Analysis (criteria 7, 8)
- `spikes/s7-push/analysis/` (`@shifa-spike/s7-analysis`): `analyse --run <dir…>` joins send log, watcher log, probe receipts and inbox fetches; per state: n, shown, shown within 60 s (%), latency p50/p95/max, collapsed, expired, lost (listed); excluded states per OD-52 (force-stopped, `restricted`, permission denied, channel off) are reported but not graded; for those it checks that the last device-state report shows the cause (permission, channel) or that the state is one only "last seen" can reveal (force-stopped, `restricted`).
- **Pass mark in code:** pass if every graded state and the one-day run have ≥ 95% shown within 60 s and zero lost. Outputs `analysis.md` and `analysis.json`, committed with the logs (tokens hashed).

### Firebase set-up (owner)
- **Checklist** `docs/spikes/s7-manual-checklist.md` (like the S5 and S6 ones): each step with what to click or run and what to send back.
- Register `dev.shifa.spike.s7push` and `…noshow` as Android apps in the production project (OD-52); download `google-services.json` into the untracked path; no paid product enabled.
- Service account with a role that only creates messages (`cloudmessaging.messages.create`: the "Firebase Cloud Messaging API Admin" role or a custom role holding that permission); key JSON stored outside the repository, path in `.env.local`; `check-no-secrets` passes before every commit.
- After the result: the owner removes both spike apps and the key from the project; the date is recorded in the report.

### Battery guide (criterion 9)
- Short Arabic steps per brand (Samsung, Xiaomi/Redmi/POCO, Oppo/Realme, Tecno/Infinix, Huawei) to keep a medical app's notifications alive (exclude from battery optimisation, allow autostart or background activity, lock in recents), from public sources (vendor help pages, dontkillmyapp.com), each with link and access date, marked "غير مُتحقَّق منه حتى تجربة الهواتف الحقيقية" (OD-52). Quotes stay under 15 words.

### ADR-0038
- "Push delivery policy: visible high priority, device state, inbox first": Proposed, Accepted on the owner's approval. Records: visible high-priority only for appointment events, normal for sync; one collapse key per appointment; TTL to appointment time; `analyticsLabel` per kind; inbox record before every push and inbox fetched on open; device state reported on every open (token, permission, channel importance, last seen) and the fallback trigger it enables; the OD-52 pass mark and the real-phone run before the first pilot. ADR-0017 changes only its `Status:` line (`· Amended by ADR-0038`).

## Tests written first
- `scenarios/test/watcher.test.ts` (4): the parser finds the probe's notifications and their `s7id` and `postTime` in recorded `dumpsys` output of both API levels; other packages ignored; a notification replaced by collapse counts once.
- `scenarios/test/skew.test.ts` (4, edge case): skew from fixed `date` samples; drift over 50 ms flagged.
- `scenarios/test/states.test.ts` (4–6): each state issues the expected `adb` and console commands in order on the fake and restores the emulator in teardown (Doze off, bucket `active`, network on, permission and channel back); reboot waits for the device and never launches the app.
- `scenarios/test/day.test.ts` (7): 53 send times from 08:00 to 21:00 every 15 minutes; Doze forced between sends; a missed slot is logged, not sent late.
- `analysis/test/rule.test.ts` (8): fixtures for a pass; 94% within 60 s fails; one lost message fails at 100% on time; excluded states not graded; an inbox-only message is not lost.
- `analysis/test/analyse.test.ts` (4, 7, 8): the CLI on a fixed run set prints the expected Markdown (snapshot) and JSON, including p50/p95/max and the excluded-state detectability column.
- `analysis/test/runs-commit.test.ts` (10; added at checkpoint F): rerunning the analysis on the committed runs reproduces the committed `analysis.json`, so the reviewer can check the report against it.
